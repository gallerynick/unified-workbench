### 开发内容详述

#### 1. 根因：刷新令牌与会话行脱钩

用户报障：日志 126 部署并强制刷新两个标签页后，F1 从「不更新」变成「彻底不显示」。

排查路径（全部有实测数据）：

- nginx 访问日志：两个标签页**确实**在按 10s 轮询 `/api/v1/me/concurrent`，referer 分别是 `https://localhost/settings/customization` 与 `https://192.168.123.8/`，**全部 200 OK**，响应体恒为 **94 字节**，即 `{"code":0,"msg":"","data":{"other_session_count":0,"other_ip_count":0,"other_device_count":0}}`。前端阈值 `other_ip_count >= 1 || other_device_count >= 1` 自然不提示——后端返回的就是全 0。
- 数据库：`user_session` 共 191 行，**全部 `is_revoked = true`**，无一活跃。
- 反查浏览器日志里出现过的 4 个 jti（`42656727…`、`719dafef…`、`b611ae27…`、`5d82d877…`）在 `user_session` 中**完全不存在**。
- nginx 日志 24 小时内**没有任何来自浏览器的 `/auth/login`**：两个标签页是 2026-08-27 前后登录的，靠 refresh 一直续命至今。

根因链：

1. `create_access_token` 每次生成全新的随机 `jti`；`create_refresh_token` 的 payload 不带 jti。
2. `refresh_access_token` 只校验 refresh token 的 `type` 与用户状态，**不查会话行**，直接换发新 access token（新 jti）。
3. 于是「一次登录」的会话行只对应**第一次**那个 access token 的 jti；30 分钟后刷新一次，令牌就与会话行脱钩，且再也回不来。
4. `get_current_user` 在 jti 查不到行时**退回按 `sub` 查用户并放行** → 请求继续 200 OK。
5. `session_activity.get_current_session` 按 jti 查不到当前会话 → `current=None` → 不做自我排除，统计失真（当前表现为全 0，因为没有未撤销行可数）。

第 4 步同时打开了一个安全缺口：登出只把 `is_revoked` 置 true，被登出或被「仅允许一处登录」踢下的设备只要拿 refresh token 调一次 `/auth/refresh` 就能拿到新 jti 的 access token，其 jti 在库里查不到、又被 `sub` 兜底放行——`is_revoked` 形同虚设。

#### 2. 修复：一次登录 = 一条会话行 = 一个 jti

`core/security.py`

- `create_access_token(user_id, role, jti=None)`：新增可选 `jti` 参数，缺省生成新 UUID（首次登录），传入则复用。
- `create_refresh_token(user_id, jti)`：refresh token 携带它所属会话行的 jti。

`services/auth.py`

- `_issue_tokens`：先出 access token 并取出 jti，再用**同一个 jti** 造 refresh token，随后按原逻辑落会话行。
- `refresh_access_token`：改为三件事——拒绝不带 jti 的历史刷新令牌（401「请重新登录」）；按 jti 校验会话行存在且 `is_revoked == False`（否则 401「会话已失效，请重新登录」）；用同一 jti 换发新的 access token 与 refresh token。

`core/deps.py`

- `get_current_user`：jti 有值但查不到任何行时直接 401「会话已失效，请重新登录」，不再退回 `sub` 兜底。无 jti 的历史令牌仍保留原兜底路径（测试夹具 `conftest.py` 直接造 token、不落会话行，依赖该路径）。

为什么复用 jti，而不是新建会话行或更新 `jti` 列：

- 新建行会让一次登录变成 N 条行，设备终端管理列表与 F1 并发计数都会重复计；
- 更新 `jti` 列需要写库，且该列有唯一约束，轮换期间新旧令牌短暂共存会留下窗口；
- 复用 jti 零额外写，会话行仍是「一次登录」的唯一标识，登出与单设备下线按行生效即可覆盖整个令牌生命周期。

#### 3. 顺带确认：容器部署下 `other_ip_count` 恒为 0

nginx 访问日志里两个标签页的 remote address 都是 `192.168.65.1`（网桥 IP）——Nginx 本身是容器时，`$remote_addr` 是网桥地址，`X-Real-IP` 由它写入，所以所有浏览器会话的 `ip_address` 记成同一个值。F1 在这个部署形态下完全依赖 `other_device_count`（`X-Device-Token` 来自 `localStorage`，按 origin 隔离，`localhost` 与局域网 IP 各一个），阈值里的 `||` 仍然成立，行为正确。已把这一约束写进《状态指示设计规格》。

#### 4. 对现有用户的影响

老 refresh token 不带 jti → 刷新返回 401「请重新登录」；老 access token 的 jti 在库里无对应行 → 401「会话已失效，请重新登录」。**所有终端需要重新登录一次**，之后会话行正常建立，F1 恢复。这是本次修复的必要代价，也是为什么 F1 之前一直是「彻底不显示」。

### 遇到的问题与解决
- `start.sh` 用 `cd "$(dirname "$0")"` 定位自身目录，从仓库根目录执行 `bash 项目文件/start.sh` 时 $0 为 `项目文件/start.sh`，拼出 `项目文件/项目文件/scripts/docker-detect.sh` 直接失败（line 9）。改为 `cd 项目文件 && bash start.sh` 后正常。
- 排查早期的错误方向：一度怀疑 `_client_ip` 取不到真实来源 IP，实测确认那是容器部署的固有约束（见第 3 节），不是本次故障的原因；真正的故障点是 jti 脱钩。
- 手工构造无 jti 的遗留 refresh token 需要容器内的 `jose` 与 `SECRET_KEY`，直接 `docker exec -i <容器> python -` 注入脚本，避免把密钥落到宿主机。

### 遗留 / 后续
- `api/ws.py` 只校验 JWT 签名，不查会话行：被登出的设备仍能维持 WebSocket 连接（只接收通知，无数据读取能力）。若要完全一致，可在 `manager.connect` 前按 jti 校验会话状态。
- `/auth/refresh` 目前只做 SELECT，不刷新 `last_active_at`。刷新本身即活跃行为，若需要更精确的活跃时间，可在端点内复用 `deps.py` 的节流逻辑。
- 容器部署下 `other_ip_count` 恒为 0（见第 3 节）。若需要「不同 IP 登录」在内网穿透场景生效，需让 Nginx 拿到真实客户端 IP。
