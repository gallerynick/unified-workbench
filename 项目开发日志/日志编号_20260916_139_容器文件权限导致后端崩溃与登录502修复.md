### 开发内容详述

**故障现象**

`curl https://localhost/api/v1/health/` 返回 nginx 502 Bad Gateway；前端可打开但
登录无任何响应。`docker ps` 显示 backend / celery / celery-beat 三个容器处于
`Restarting` 循环，nginx 标记 unhealthy。

**根因定位**

`docker logs unified-workbench-backend-1` 尾部反复出现同一条异常：

    PermissionError: [Errno 13] Permission denied: '/app/app/models/note_draft.py'
    File "/app/app/startup_migrate.py", line 32, in <module>
      from app.models import *
    File "/app/app/models/__init__.py", line 13, in <module>
      from app.models.note_draft import NoteDraft

链条是：`app/startup_migrate.py`（Dockerfile CMD 每次启动执行）第 32 行 `from
app.models import *` → 触发 `models/__init__.py` 导入 `note_draft` → Python 读取该
.py 文件被操作系统拒绝 → 进程退出 → docker restart 策略重试 → 无限循环。
backend 从未完成 uvicorn 绑定，因此 nginx 转发 API 一律 502。

本地 `ls -l` 比对直接暴露了问题：

    -rw------- 1 501 staff 1614  app/models/note_draft.py    ← 新建文件
    -rw-r--r-- 1 501 staff 2855  app/models/user.py          ← 仓库惯例

而 `backend/Dockerfile` 第 33/39 行明确以非 root 用户运行：

    RUN groupadd -r workbench && useradd -r -g workbench -d /app ... workbench
    USER workbench

文件属主是宿主机 uid 501 且模式为 600，容器内 `workbench` 用户既不是属主也不在
属主组，任何读操作都被拒绝。凡是用文件写入工具新建的源文件都带了 600 权限位，
本次累计 67 个（含 P1/P2/P3 新建的后端与前端文件，以及并行工作流新建的文件）。
此前 P1/P2 阶段从未跑过 `start.sh` 冒烟（当时环境无 docker CLI 可见），所以问题
一直潜伏到 P3 完成后的首次部署才暴露。

**修复动作**

1. 把 67 个 600 权限的源文件统一 `chmod 644`，与仓库既有惯例一致。
   内容零改动，仅权限位。排除规则：node_modules / .venv / __pycache__ / dist /
   .docker-local 不进镜像或不受影响；`nginx/ssl/selfsigned.key` 是私钥必须保持
   600，按文件名排除（已确认仍为 -rw-------）。
2. `bash start.sh` 重新构建并启动：28 秒完成，所有容器 healthy，
   「入口校验通过（前端 200 / 后端 /api/v1/health 200）」，
   后端日志出现 `[startup_migrate] 建表与增量迁移完成`，无 traceback。
3. 在 start.sh 步骤 1（环境检查）末尾新增 `normalize_source_modes()`：
   构建前扫描 backend / frontend / nginx / scripts 下所有 600 源文件并改为 644，
   有变更则 warn 明示数量、无变更则 ok 静默通过，私钥按名排除。
   这样即使后续任何人再写入 600 文件，也会在部署时被自动纠正并显式提示，
   而不是等服务起来后全线 502 才被发现。

**为什么不在 Dockerfile 里修**

在 Dockerfile 加 `RUN chmod -R a+r /app` 也能修，但代价是每次构建都全树 chmod、
且把「宿主机写文件权限不当」的问题藏进镜像，掩盖了真实根因。放在 start.sh 更贴近
问题发生的时机（部署前），并且会把数量打印出来，让人能回头去查是谁写了 600 文件。

### 遇到的问题与解决

- 问题：`docker: command not found`
  解决方案：Docker Desktop 的 CLI 位于
  `/Applications/Docker.app/Contents/Resources/bin/docker`，未进 PATH。
  `scripts/docker-detect.sh` 已能自动探测到该路径，`start.sh` 内部调用正常；
  手工排查时把该目录加入 PATH 即可直接使用。

- 问题：本会话前几次误判「docker 不可用」从而跳过了 P4.4 冒烟
  解决方案：日志 138 已记录该限制；本次实测 Docker Desktop 一直在运行，
  只是 CLI 不在 PATH。P4.4 冒烟实际上是可以且必须做的，属于此前验证不足。

- 问题：`/api/v1/health/` 返回 307
  解决方案：非故障。该路由注册为无尾斜杠形式，带尾斜杠的请求被 FastAPI
  `redirect_slashes` 307 到 `/api/v1/health`。浏览器 fetch 会自动跟随并保留
  方法与请求体；curl 需加 `-L` 才看到最终 200。本次登录验证直接用
  `/api/v1/auth/login`（无尾斜杠）确认返回 401 业务错误。
