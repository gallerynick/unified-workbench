### 开发内容详述

**一、根因**

原先的判定是这样写的：

    const draftDiffers = useMemo(() => {
      if (!existingDraft || !note) return false;
      const draftBody = existingDraft.body ?? {};
      return JSON.stringify(draftBody) !== JSON.stringify(body);
    }, [existingDraft, body, note]);

它拿服务端草稿去比**实时编辑器内容**（body 状态），而该提示要回答的问题是
「服务器上有没有一份比已发布内容更新的草稿值得恢复」——比较对象应该是
**刚载入的已发布内容**，不是正在被打字的内容。比较对象选错了，于是出现：

  1. 用户敲一个字 → body 变化 → 与草稿不同 → 提示立刻弹出
  2. 自动保存（debounce 1.5s）触发 → 草稿被写成当前内容
     → useNoteDraft 内 persist() 又 setExistingDraft(res.data)
     → 草稿等于当前内容 → 提示消失
  3. 用户继续打字 → 重复 1、2

表现为提示在输入过程中反复闪现，且每次停顿超过 1.5s 再输入就一定会出现
一次——正是用户描述的现象。此时草稿就是本人正在写的内容，提示毫无意义。

**二、修法**

把「是否有待恢复草稿」改成**只在载入笔记那一刻判定一次**，结果存入
pendingDraft 状态，此后不再随编辑内容变化重新判定：

  1. 新增 pendingDraft 状态。载入 effect 内调用
     loadExisting().then(...) 拿到草稿后，与刚载入的已发布内容比较，
     有差异才 setPendingDraft(draft)，否则 setPendingDraft(null)。
  2. 删除 draftDiffers 这个随 body 变化的 useMemo——它就是这个误报的
     直接来源。
  3. 提示的渲染条件、描述文案、恢复按钮全部改用 pendingDraft。
  4. 三个出口都清空 pendingDraft：恢复草稿后（草稿内容即当前内容，
     基线随之对齐）、丢弃草稿后、发布成功后。
  5. 顺带修掉一个潜伏的误报源：比较改用新增的 stableStringify（递归排序
     对象键后再 stringify），避免 Tiptap JSON 在不同写入路径下键序不同、
     内容实际相同却被判为「已改动」。
  6. 比较范围同时覆盖标题（原先只比正文，只改标题的旧草稿会被漏报）。

**三、行为对照**

  打开一篇笔记，服务器上有比已发布内容更新的旧草稿 → 载入即提示，可恢复/丢弃
  打开一篇笔记，无草稿或与已发布内容一致 → 不提示
  开始编辑（无论怎么敲、停顿多久、自动保存触发多少次）→ 全程不提示
  编辑后点保存 → 草稿删除、提示清空，不会残留
  切换到别的笔记再切回 → 重新按该笔记的草稿判定，互不干扰

### 遇到的问题与解决

- 问题：误报触发条件不明显，初看代码像「没有草稿就不提示」，很难看出问题。
  解决方案：顺着 existingDraft 的所有写入点排查——loadExisting、persist、
  clear、noteId 变化时的重置——发现 persist() 在每次自动保存后都会把草稿
  更新为当前内容，与「用户正在打字」交替进行，才定位到比较对象选错。
  教训是判断类逻辑要同时检查它依赖的状态由哪些路径写入，而不只看读取处。

- 问题：正文与草稿的比较直接用 JSON.stringify。
  原因：Tiptap JSON 的键序取决于写入路径，同内容可能不同串。
  解决：新增 stableStringify 递归排序对象键后再序列化。
