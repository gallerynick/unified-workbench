### 开发内容详述

#### 1. 数据模型
- `user_totp`：一用户多行（多设备绑定）；`secret_encrypted` 存 AES-256-GCM 加密后的 TOTP 密钥（复用 core/encryption.py + ENCRYPTION_MASTER_KEY，与密钥保险箱同套），`is_active` 区分待绑定/已激活，`label` 设备名，`last_used_at` 最后使用。
- `user_recovery_code`：`code_hash` bcrypt 哈希（存规范化形式 XXXX-XXXX-XXXX 去横线大写），`used_at` 非空即已用。

#### 2. 登录两步式（核心改动）
- 密码验证通过后，若用户已绑定激活设备 → 签发短期 `pending_2fa` 令牌（默认 5 分钟，无访问权限），不创建会话，返回 `{pending_2fa: true, pending_token}`。
- 新接口 `POST /auth/verify-2fa`：凭 pending 令牌 + 动态码（遍历所有激活设备校验，容忍 ±1 时间窗）或恢复码（一次性，命中即标记 used）→ 通过后创建会话并签发正式 access/refresh 令牌。
- 未启用 2FA 时登录行为不变（直接返回正式令牌）。
- 锁定界面（LockPage）走的是本地密码解锁，不经 /auth/login，天然不受 2FA 影响，符合「锁定后无需二次验证」。

#### 3. 2FA 管理接口（全部需登录；敏感操作需二次密码验证）
- `GET /auth/2fa/status`：enabled / device_count / recovery_codes_remaining
- `GET /auth/2fa/devices`：列出已绑定设备（绝不返回密钥）
- `POST /auth/2fa/setup`（验密码）：创建待绑定设备，返回 device_id + 明文密钥 + otpauth URI（仅此一次）
- `POST /auth/2fa/activate`：动态码激活
- `POST /auth/2fa/devices/{id}/remove`（验密码）：解绑（重绑定的基础）
- `POST /auth/2fa/recovery-codes`（验密码）：重新生成一批（作废旧批），明文仅展示一次
- `POST /auth/2fa/disable`（验密码）：关闭 2FA（删全部设备+恢复码）

#### 4. 前端
- **安全设置页**（`/settings/security`，菜单置于「设备终端」后、管理员「系统设置」之前，即个人设置区）：标题栏仅保留标题；状态用顶部彩色状态条表达（未开启=蓝色提示 / 已开启=绿色成功）；「认证器设备」卡片内列表 + 唯一入口按钮（未开启=「开启双因素认证」主按钮，已开启=「添加认证器」）；「恢复码」卡片内说明 + 「生成 / 查看恢复码」+「关闭双因素认证」（危险色）。按钮区与文字/列表保持间距，敏感操作统一走密码确认弹窗。
- 登录页：密码通过后若返回 pending_2fa，切换二次验证步骤（动态码/恢复码 Segmented 切换 + 输入 + 返回上一步）。
- UI 规范修复（按 《项目基定/UI设计规范.md》：标题栏不放控件、一个功能一个入口、按钮不与文字粘连；参考「用户个性化」页布局）。
- 深浅色模式：新页面使用 CSS 变量（--card-bg 等）适配；图标全部使用 @ant-design/icons，无 emoji。

### 遇到的问题与解决
- 问题：测试 fixture 用 `session.begin()` 包裹，接口内 `db.commit()` 会关闭该事务，导致多请求+commit 的测试（登录后刷新、2FA 绑定流程）报「closed transaction」。
  - 解决方案：conftest.py 的 db fixture 改为**连接级事务**（engine.connect + connection.begin，结尾整体 rollback），既支持内部 commit，又保持测试隔离。该修复同时解决了既有 `test_refresh_token_success` 的失败。
- 问题：恢复码校验 401。
  - 解决方案：生成时哈希规范化形式（去横线大写）与校验一致化，避免带/不带横线不一致。
- 问题：前端 JSX 属性 `description=...` 误加尾逗号导致 TS 解析错误。
  - 解决方案：移除 JSX 属性间多余逗号。
- 问题：部署时 Docker buildx 写 `~/.docker/buildx/activity` 被沙箱拦截（operation not permitted）。
  - 解决方案：构建时设置 `BUILDX_CONFIG` 指向可写临时目录（`/tmp/bxconfig`）绕过。
- 问题：backend 容器启动报 `PermissionError: 'app/models/user_recovery_code.py'` —— 沙箱新写入文件权限为 600，容器内 workbench 非 root 用户读不了。
  - 解决方案：将本次新增代码文件 chmod 644 后重新部署。
- 问题：验证期间 Postgres 出现「too many clients already」（连接被占满，psql 都进不去）。
  - 解决方案：重启 backend/celery 容器释放连接后恢复；根因未深究（与本次改动无关的既有行为）。
- 遗留问题：仓库存在若干与 2FA 无关的既有失败测试（test_content/test_secrets/test_templates/test_users 等的 307/JSONDecode/Operational 错误），经 git stash 基线对比确认非本次改动引入，未在本次范围内修复。
