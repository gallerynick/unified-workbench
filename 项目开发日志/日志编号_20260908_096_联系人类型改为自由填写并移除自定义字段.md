### 开发内容详述

#### 1. 数据库：contact_type 由枚举改为 VARCHAR(100)

原实现是 PostgreSQL 原生枚举类型 contacttype（customer/supplier/partner/other），
列定义 Enum(ContactType, create_type=False)。枚举值固定，无法承载自由输入的类型，
这是「其他 + 自定义字段」这种绕路设计的根因。

迁移 045_contact_type_to_string.py：

```python
op.alter_column(
    "contact", "contact_type",
    existing_type=sa.Enum("customer", "supplier", "partner", "other",
                          name="contacttype", create_type=False),
    type_=sa.String(100),
    existing_nullable=False,
    existing_server_default=sa.text("'customer'::contacttype"),
    server_default="customer",
    postgresql_using="contact_type::text",
)
op.execute("DROP TYPE IF EXISTS contacttype")
```

关键点：
- 用 ALTER COLUMN ... TYPE ... USING contact_type::text 而非「drop 再 add」，
  既有 customer/supplier/partner/other 值原样转为文本，**不丢数据**
- 枚举类型不再被任何列引用后删除，避免遗留无用类型
- downgrade 用 DO 块 + duplicate_object 异常捕获重建枚举（PostgreSQL 15 的
  CREATE TYPE 不支持 IF NOT EXISTS），并把无法映射的自由文本归入 other

注意：本仓库部署采用 **create_all 优先**（见《数据库演进与迁移》），
alembic upgrade head 不会在启动时自动执行，且 create_all 不会修改已存在列的类型。
因此同步在 backend/Dockerfile 的启动 CMD 中追加了幂等 inline SQL：

```
ALTER TABLE contact ALTER COLUMN contact_type TYPE VARCHAR(100) USING contact_type::text
ALTER TABLE contact ALTER COLUMN contact_type SET DEFAULT 'customer'
DROP TYPE IF EXISTS contacttype
```

三条语句均可重复执行（已是 VARCHAR 时再 ALTER 为等值转换；DROP TYPE 带 IF EXISTS）。

补充：ALTER COLUMN ... TYPE 会连带转换默认值表达式，实测把 'customer'::contacttype
默认值清掉了，而该列是 NOT NULL。因此显式补 SET DEFAULT 'customer'，并把模型层改为
default="customer", server_default="customer" 双默认，保证新库（create_all）与旧库
（inline SQL）行为一致。用 pg_get_expr 复核得到 'customer'::character varying。

#### 迁移通路的改写（重要）
对方把 Dockerfile 的 inline 迁移重构成了 `app/startup_migrate.py` 的三层体系：
第一层从模型元数据动态派生 PG 枚举类型、第二层按元数据动态补列、
第三层放手工特例。**因此本次不再改 Dockerfile**，而是把列类型转换写进第三层：

```python
# 迁移 045：contact.contact_type 枚举 → VARCHAR(100)
contact_cols = _actual_columns(conn, "contact")
if "contact_type" in contact_cols:
    ct_type = conn.execute(sa.text(
        "SELECT data_type FROM information_schema.columns "
        "WHERE table_schema = 'public' AND table_name = 'contact' "
        "AND column_name = 'contact_type'"
    )).scalar()
    if ct_type != "character varying":
        conn.execute(sa.text(
            "ALTER TABLE contact ALTER COLUMN contact_type "
            "TYPE VARCHAR(100) USING contact_type::text"))
        conn.execute(sa.text(
            "ALTER TABLE contact ALTER COLUMN contact_type SET DEFAULT 'customer'"))
    conn.execute(sa.text("DROP TYPE IF EXISTS contacttype"))
```

选择第三层的理由：第二层只做「补列」不做「改型」，列类型变更属于它明确声明
无法表达的部分，与同层已有的 046（列改名）、047（存量回填）同类。
枚举清理无需手工列出——模型里删掉 Enum 后第一层就不会再建该类型，
这里只负责删掉旧库的残留。

新库路径同样成立：create_all 直接按模型建出 VARCHAR(100) 列，第三层的
`ct_type != "character varying"` 分支被跳过，`DROP TYPE IF EXISTS` 空转。

### 第三轮追加（同日）：补上联系人可见性写入通路

#### 结论修正
上一轮把联系人可见性列为「需先确定权限语义再改」的独立修复项——这个判断是错的，
过度保守。核查后发现权限语义早已在项目里定死：8 个模块（content / task / note /
form / vote / topology / meeting_record / note_folder）统一遵循同一约定：

- Create：`visibility: Visibility = Visibility.PRIVATE`，`restricted_users: list[str] | None = None`
- Update：`visibility: Visibility | None = None`，`restricted_users: list[str] | None = None`
- Response：`visibility: Visibility`，`restricted_users: list[str] | None = None`

即「owner 可自行设置自己内容的可见范围、默认私有」是既有产品决策，不是待议事项。
联系人只是漏了两处代码，照抄既有约定即可，无需任何决策。

#### 缺陷实况
读侧链路其实完整且正常：
- `_visibility_get_check` 用 `item.visibility` 判定单条访问权限
- `list_contacts` 用 `build_visibility_filter(Contact, user_id)` 做列表过滤
- `_admin_can_manage_own_designated` 用 `item.visibility` 判定管理员管理权限

断在写侧：
- `ContactCreate` / `ContactUpdate` 没有 visibility / restricted_users 字段，
  Pydantic 默认忽略前端传来的值 → 浮窗的可见性选择被**静默丢弃**
- `create_contact` 构造 Contact 时未赋值 → 落库永远是列默认值 'private'
- `update_contact` 无对应赋值分支 → 无法修改可见性
- `ContactResponse` 也没有 → 列表页拿不到字段，无法回显

净效果：联系人被强制私有，浮窗里的可见性控件是个假的。不报错，但功能无效，
典型的静默失效。

#### 修改
照 content.py 逐字对齐，不引入任何新语义：

- schemas/contact.py：ContactCreate 加 `visibility: Visibility = Visibility.PRIVATE`
  与 `restricted_users`；ContactUpdate 加同名可空字段；ContactResponse 加两字段；
  导入 `from app.core.visibility import Visibility`
- services/contact.py：create_contact 构造时传 `visibility=request.visibility,
  restricted_users=request.restricted_users`；update_contact 加两个
  `if request.X is not None:` 赋值分支

`None` 表示「不变更」而非「清空」，与 content.py 的分量更新语义一致。因此把
visibility 从 restricted 改回 public 时 restricted_users 不会被清——无害（public
判定优先），也与既有模块行为一致。

数据库列不用动：模型本来就有 visibility（server_default='private'）与
restricted_users 两列。
