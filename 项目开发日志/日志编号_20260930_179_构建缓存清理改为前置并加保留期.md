### 开发内容详述

**1. 先更正日志 176 的错误结论**

日志 176 把缓存清理定性为「无风险」，依据是 `docker system df` 的 Local Volumes 始终 7 个 / 5.325GB 不变。**这个依据只能证明没碰卷，不能证明没碰构建缓存依赖。**

`prune-cache.sh` 初版第 16-18 行还写着一条断言：

> 不加 -a / --all：那会连现有镜像仍在引用的缓存层一起清掉，下次 --build 失去缓存命中

实测推翻：`docker buildx du` 显示 **Reclaimable 5.277GB / Total 5.328GB（98.9%）**，说明**不带 `-a` 同样会把重建需要的层清光**。该断言是假保证，本次一并删除并改写为「历史教训」段落。

**2. 根因链（实测）**

| 时间 | 事件 |
|---|---|
| 23 小时前 | 并发会话改 `backend/Dockerfile`（加 pgdg + postgresql-client-15）→ 该 apt 层层缓存键失效 |
| 13 小时前 | 构建重新执行 apt 层 → 走网络 → 成功 → 结果写回 buildx 缓存 |
| 该次 `start.sh` 末尾 | 旧版 `prune-cache.sh` 无保留期执行 `builder prune -f` → **刚写回的 apt 层被删掉** |
| 本次部署 | apt 层缓存未命中（构建日志中 `#5-8 CACHED` 而 `#10/#11` 重新执行）→ 走网络 → 404 → 后端镜像构建失败 |

**3. 缓存清理改为【前置】**

清理会销毁当时存在的可回收层。放在构建之后，本次构建刚写入的层会被自己这次清理抹掉；放在构建之前，本次构建产生的层能完整保留到下次运行。

> 需要说明：**单靠「前置」并不解决问题**——只是把销毁从本次末尾挪到下次开头，紧随其后的构建照样拿不到缓存。真正起作用的是保留期，前置是配合语义与「先腾空间再构建」。

`start.sh` 步骤由：
```
[1/6] 环境检查  [2/6] 前端构建  [3/6] 启动服务  [4/6] 健康检查  [5/6] 缓存清理  [6/6] 汇总
```
改为：
```
[1/6] 环境检查  [2/6] 缓存清理  [3/6] 前端构建  [4/6] 启动服务  [5/6] 健康检查  [6/6] 汇总
```
`start.bat` 同步改为 `[1/4] 环境检查 → [2/4] 缓存清理 → [3/4] 前端构建 → [4/4] 启动服务`。

顺带修正了 `start.sh` 中残留的旧横幅（`[1/5]`/`[2/5]`/`[3/5]`/`[4/5]` 与 `[5/6]`/`[6/6]` 混用），统一为 6 步编号。

**4. 加入 72 小时保留期**

```sh
dw builder prune -f --filter until=72h
```

默认 72h，可用 `PRUNE_CACHE_RETENTION` 环境变量覆盖。`image prune -f`（悬空镜像）保持无过滤——它清的是无 tag 镜像，不参与构建缓存复用。

实测验证：当前缓存条目创建于 2026-09-29 06:53（**33 小时前**），落在 72h 内 → `until=72h` 清理结果 `Total: 0B`，缓存 5.328GB 完整保留。对照无过滤时 Reclaimable 为 5.277GB，**证明 `--filter` 确实生效、未被忽略**。

**5. 脚本改为双模式，保持单一来源**

`prune-cache.sh` 同时支持：

```sh
# 模式 1：被 start.sh source，在构建前调用（前置清理）
source "$(dirname "$0")/scripts/prune-cache.sh"
prune_build_cache

# 模式 2：独立直接执行
sh scripts/prune-cache.sh
sh scripts/prune-cache.sh --skip-prune
sh scripts/prune-cache.sh --help
```

实现方式：文件末尾以 `if [ "${BASH_SOURCE[0]:-$0}" = "$0" ]` 判定是被 source 还是被直接执行；直接执行时才作为入口，并在 `dw` 未定义时自行 source `docker-detect.sh` 完成 docker 探测。这样启动脚本与独立脚本共用同一份清理逻辑，改一处即两处生效。

`prune-cache.bat` 同样处理：`DOCKER_BIN` 未设置时自行 `call docker-detect.bat`。

### 遇到的问题与解决

**问题 1：保留期修复并未解除部署阻塞。**

改完跑 `start.sh`，后端镜像**仍然失败**，报错与修复前完全一致。定位发现：apt 层本来就不在缓存中（`#30/#31` 重新执行），保留期只能「保住已有的层」，不能「凭空变出没有的层」。缓存修复与镜像源问题是**两个独立缺陷**。缓存修复本身已通过 `--filter` 生效性验证，但不足以恢复可部署性。

**问题 2：部署失败的真实原因不是阿里云镜像站。**

持续排查后推翻了我先前的三个猜测：

| 猜测 | 实测结论 |
|---|---|
| 基础镜像 `python:3.11-slim` 从 bookworm 漂移到 trixie | ❌ 镜像中该层为 **4 周前**，未发生漂移 |
| 阿里云镜像站同步不完整 | ❌ 清华、中科大、**官方 deb.debian.org 同样 404** |
| HTTP 代理干扰（报错 IP `198.18.0.60` 属 198.18.0.0/15 保留段） | ❌ 改用 HTTPS 请求官方源，同样 404 |

**实际结论**：Debian 13 trixie 的 Release 文件声明了未压缩索引 `main/binary-arm64/Packages`（56MB，md5 `83dce223…` / sha256 `f9701126…`），但该文件在**所有镜像站（含官方源）均不存在**，只有 `.gz`（13MB）与 `.xz`（9.6MB）可下载。apt 请求了未压缩版本，收到 404 后视为致命错误（`E: Failed to fetch`）并终止构建。仅影响 arm64。

这是 Debian 仓库侧的发布/镜像不一致，不在本项目可控范围内，需单独处理。

**问题 3：写入被只读沙箱拦截。**

首次写 `prune-cache.sh` 返回 `[sandbox: file access denied under read-only mode]`。按提示提权重试时策略已切换为 `danger-full-access`，遂去掉提权参数正常写入。
