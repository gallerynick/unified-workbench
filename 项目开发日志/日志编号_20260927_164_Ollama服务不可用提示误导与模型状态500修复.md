### 开发内容详述

#### 一、先说结论：容器没挂，提示是假的，但暴露了两个真 bug

排查第一步是确认服务状态，结果全部正常：

- `unified-workbench-ollama-1` 已运行 20 小时，容器内 `OLLAMA_HOST=0.0.0.0:11434`
- 容器内 `GET /api/tags` 直连返回 200，4 个模型
- 后端 `GET /config/ollama/health` 连续 5 次全部 `status: ok`，耗时 15~24ms

所以「Ollama 服务不可用 / 请确保 Ollama 容器已启动」那句提示是**误导**的——
它把「无法确认」和「确认挂了」混成了一句。但顺着这条线往下查，找到了两个真 bug。

#### 二、真 bug 1：`/models/{name}/status` 直接 500，导致「模型未下载」判断永远失效

`ModelStatusResponse.size` 声明成 `str | None`，但 Ollama 返回的是**字节数（int）**：

```python
class ModelStatusResponse(BaseModel):
    size: str | None = None          # ← Ollama 给的是 3389983735
```

`/api/tags` 里 `qwen3.5:4b` 的 `size` 是 `3389983735`，一旦模型已下载，
Pydantic 校验就抛 `ValidationError`，整个接口返回 500：

```
{"code":500,"msg":"ValidationError: 1 validation error for ModelStatusResponse
size
  Input should be a valid string [type=string_type, input_value=3389983735, input_type=int]"}
```

前端是这样用的：

```tsx
if (healthRes.code === 0 && healthRes.data?.status === 'ok') {
  setOllamaHealth('ok');
  const modelRes = await getOllamaModelStatus(PRESET_AI_MODEL.ollamaName);
  if (modelRes.code === 0 && modelRes.data?.downloaded) {   // ← 500，code 不是 0
    setAiModelStatus('downloaded');
  } else if (!downloadTaskId) {
    setAiModelStatus('not_downloaded');                      // ← 模型明明下好了，却报未下载
  }
}
```

**后果**：只要模型真的下载成功了，这个接口就 500，前端就永远判成 `not_downloaded`，
用户看到「模型未下载」然后点「下载模型」，结果重复下载。
`/models` 列表接口有同样的问题，只是前端目前没调用它。

修法：`size` 改成 `int | None`，`modified_at` 的默认值从 `""` 改成省略（`None`），
类型一致后校验通过。

#### 三、真 bug 2：健康检查的失败原因被吞掉，提示不可操作

原实现把所有失败都压成一句：

```python
except HTTPException:
    return UnifiedResponse(data={"status": "error", "message": "Ollama 服务不可用"})
```

但 `_ollama_request` 其实分三种情况：`ConnectError`（连不上）、`TimeoutException`（超时）、
`HTTPStatusError`（API 报错）。ollama 在忙于加载模型或处理请求时 `/api/tags` 会超时——
这时候容器明明在跑，提示却是「请确保 Ollama 容器已启动」，完全误导。

现在把 `status_code` 翻译回具体原因，前端按原因展示：

| reason | message |
|---|---|
| `timeout` | Ollama 响应超时，服务可能正忙于其他请求 |
| `unreachable` | 无法连接到 Ollama 服务 |
| `api_error` | Ollama API 返回错误：<detail> |

AI 连接测试里那句硬编码的「Ollama 服务不可用」也一并改成了带上 HTTP 状态码的具体描述。

#### 四、前端：重试 + 手动重新检查

原来只查一次，一次失败就永久红屏，而且没有任何恢复手段（ollama 重启后还得刷新整页）。现在：

- 失败重试 2 次，每次间隔 1 秒——扛过短暂抖动
- 区分两种失败：**后端没连上**（页面到后端这一跳断了）和**后端说 ollama 异常**，文案不同
- Alert 加「重新检查」按钮，点了直接重跑 `checkOllamaStatus()`

#### 五、顺手让体积显示变成真数据

前端原来显示 `约 2.5 GB`（写死的字符串），而 `qwen3.5:4b` 实测 3389983735 字节 ≈ 3.2 GB。
现在从 `/models/{name}/status` 拿真实字节数，加一个 `formatBytes` 助手展示，
下载标签和删除确认里都用真实体积。

### 遇到的问题与解决

- **问题**：`curl -sk https://localhost/api/v1/ollama/health` 返回 `{"detail":"Not Found"}`。
  - **解决方案**：路由前缀是 `/config/ollama` 不是 `/ollama`（见 `app/api/router.py`）。
    排查时差点误判成「接口没了」。
- **问题**：`edit` 工具多次匹配失败——`old_string` 缩进少算了一层。
  - **解决方案**：先用 `read` 看真实缩进再拼 `old_string`；
    重复片段（`size=model.get("size", "")` 出现两次）改用 `replace_all: true`。
