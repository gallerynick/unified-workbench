### 开发内容详述

**1. 抽出成对清理库，两端行为对齐**

原先 start.sh / start.bat 各自内联所有逻辑，新增行为容易只在其中一端落地。本次把清理逻辑抽成同名成对的辅助库 `scripts/prune-cache.sh` 与 `scripts/prune-cache.bat`，沿用仓库既有的 `docker-detect.sh/.bat` 模式，使两端「做什么」在文件层面即可对照。

**2. 清理范围：只动构建缓存与悬空镜像**

- `docker builder prune -f` —— 仅删「无镜像引用」的构建层
- `docker image prune -f` —— 仅删未打标签（dangling）的镜像

**3. 三条明确的「不做」，写入两端脚本头部注释**

- 不加 `--volumes`、不跑 `docker volume prune`。原因：compose 卷在 `docker compose down` 之后会变成无容器引用状态，此时 `volume prune -a` 会把数据库卷一起删掉。
- 不加 `-a` / `--all`。原因：那会连现有镜像仍在引用的缓存层一起清掉，下次 `--build` 失去缓存命中，后端镜像（含 torch 等数 GB 依赖）会被迫重新构建。
- 不动 `frontend/dist`、`node_modules`，仍由 start.sh 的新鲜度判断管理。

**4. 清理时机：放在构建与健康检查成功之后**

- start.sh：新增第 [5/6] 步「清理构建缓存」，原「汇总」顺延为 [6/6]
- start.bat：新增第 [4/4] 步（原为 [3/3]）

放在最后而不是开头，是因为清理在构建之前执行会削弱本次 `--build` 的缓存命中；放在健康检查之后还能保证服务启动失败时不浪费清理动作。

**5. 汇总行兼容新旧两种措辞**

Docker 29.6.2 实测发现两条命令的汇总行格式不同：

- `docker builder prune -f`（buildx）输出 `Total:\t6.257MB`
- `docker image prune -f` 仍输出 `Total reclaimed space: 0B`

因此不能只取最后一行（会拿到 0B 掩盖真实释放量）。.sh 用正则同时匹配两种措辞、逐个解析为人可读容量后按字节求和，再用 awk 格式化输出；.bat 用 `for /f` 分别按 `tokens=1,2` 与 `tokens=1,4` 取两条命令的值。

**6. 新增 --skip-prune 开关**

- `./start.sh --skip-prune` / `start.bat --skip-prune`
- 环境变量 `SKIP_CACHE_PRUNE=1`

清理函数无论有无异常都返回 0，不会因缓存清理失败而中断启动流程。

### 遇到的问题与解决

- 问题：初版正则只匹配 `Total reclaimed space:`，实测清理了 3.259GB 却误报「无待清理的缓存」。
- 解决方案：用 `FROM busybox` 临时镜像构造真实缓存后抓取 `docker builder prune -f` 原始输出，确认 Docker 29.x 汇总行已改为 `Total:\t<容量>`；改为双措辞匹配 + 按字节求和。

- 问题：`docker builder prune` 无 `-q`/`--quiet` 参数（与 `docker image prune -q` 不同），无法静默取字节数。
- 解决方案：改为解析汇总行文本，而非依赖静默模式。

- 问题：无法通过 `./start.sh` 完成端到端部署验证。
- 原因：当前工作树存在另一会话的未完成改动，`src/pages/settings/StorageSettings.tsx(529,20)` 存在 TS2345 类型错误，`tsc -b` 失败，start.sh 在 [2/6] 退出。用 `--skip-build` 可绕过，但会造成前端产物与后端镜像版本不一致的半部署，故未执行。
- 遗留：待该会话修复前端编译后，运行 `./start.sh` 即可看到 [5/6] 步骤输出。
