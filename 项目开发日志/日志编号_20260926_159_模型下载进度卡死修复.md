### 开发内容详述

#### 一、问题现象与证据

用户反馈：下载 `qwen3.5:4b` 时，进度条、速度、已下载量一直停在
「速度 0.09 MB/s / 已下载 3114.1 MB / 总计 3232.9 MB」（约 96.3%），不再变化。

从 Redis 取证，当时存在 **5 个** `model_download:qwen3.5:4b_*` 任务，字段值**完全一致**
（`progress=96.3258441698442`、`downloaded=3265418992`、`total=3389971840`，
换算即 3114.1 MB / 3232.9 MB / 0.09 MB/s，与用户所见完全吻合），
`status` 全部为 `downloading`，而 `updated_at` 距当前已 **13 分钟未更新**；
最早的 `started_at` 比后端容器启动时间早 **2.3 小时**。

结论：后端进程重启后，原先由 `asyncio.create_task` 启动的下载协程随进程一起消失，
但 Redis 中的任务状态仍是 `downloading`。前端 `/download/current` 无条件信任该状态，
于是永久轮询一个背后没有任何协程的「僵尸任务」。

#### 二、根因（四条，均在 `model_download.py` 内）

1. **僵尸任务无兜底**：下载协程进程重启后不会回写状态；`get_download_status` 与
   `get_user_current_download` 无条件信任 `downloading` 键。这是本次卡死的直接原因。
2. **进度样本被静默丢弃**：Ollama `/api/pull` 返回 NDJSON（每行一个 JSON 对象），
   而 `response.aiter_bytes()` 的字节块与 JSON 行并不对齐。旧实现直接对整个块
   `json.loads`，一个块含多行时整体抛错并被 `except: pass` 吞掉，整批进度样本丢失，
   进度看起来像冻结。
3. **速度计算窗口错位**：旧实现用「距上次写入 Redis 的间隔」作分母，节流一旦跳过写入，
   就会把长窗口的增量除进去，速度被严重低估（0.09 MB/s 即由此而来）。
4. **无单飞保护**：每次点击都新建任务，同一模型并发起了 5 个 pull，既互相竞争
   也留下 5 份孤儿键。

另发现一条相邻缺陷：Ollama 拉取失败时以 **HTTP 200 + `{"error": ...}` 正常结束流**
（已实测：`{"status":"pulling manifest"}` 后跟 `{"error":"pull model manifest: file
does not exist"}`）。旧逻辑把「流结束」一律判为「下载完成」，会在模型名无效时误报成功。

#### 三、修复方案

**后端 `model_download.py`（重写）：**

1. **NDJSON 行缓冲解析** `_feed_ndjson()`：把新字节并入 `bytearray` 缓冲区，
   按 `\n` 切分完整行后逐行 `json.loads`，不完整的行留待后续字节；
   单行解析失败仅跳过该行，不影响同块内其他行。流结束时补一个换行解析残余行。
2. **滑动窗口速度**：`_ProgressState.samples` 保存最近 15 秒的
   `(timestamp, downloaded)` 采样点，速度 = 窗口首尾增量 / 时间差，并 `max(0, ·)`。
   采样与写 Redis 节流（0.5s）解耦，节流只影响写入频率，不影响样本完整性。
3. **心跳 + 卡死回收**（新增 `updated_at` / `progress_updated_at` 双时间戳）：
   - 独立 watchdog 协程每 5 秒用 Lua 脚本原子刷新 `updated_at`（只改这一个字段，
     不会与进度写入互相覆盖）；
   - `_is_orphan()` 三层判据：心跳缺失 > 120s → 任务已丢失；
     `downloading` 且零字节增长 > 600s → 上游网络卡死；总时长 > 6 小时 → 超时；
   - **读侧回收**：`get_download_status`、`get_user_current_download`、
     `pause_download`、`_find_active_task` 读取时都走 `_maybe_reap()`，
     命中即就地改成 `error` 并给出原因；
   - **启动侧回收**：新增 `reap_orphaned_downloads()`，由 `main.py` 的
     `lifespan` 调用，无条件把所有仍标记为 `pending` / `downloading` 的任务
     改为 `error`（进程重启后这些协程必然已不存在）。
4. **单飞**：`start_model_download()` 先查同用户同模型的活跃任务，有则直接复用其
   `task_id`，不再并发重复拉取。
5. **失败态正确收敛**：流内 `error` 字段被捕获，流结束时若存在则判为
   `pull_error` → `status=error` + `Ollama 拉取失败: <原文>`，不重试。
6. **协程保活**：新增 `_DOWNLOAD_TASKS` 集合保存后台任务引用
   （`asyncio` 对 Task 只持弱引用，未保存引用可能被 GC）。
7. **暂停语义简化**：暂停即停止当前 pull 流并阻塞等待恢复；恢复后重新发起 pull，
   Ollama 会从已缓存的分片续传，无需维持长连接挂起。

**前端 `ThirdPartyConfigPage.tsx`：**
- 新增 `downloadPhase` / `downloadStartedAt` 状态，在轮询与页面恢复时同步；
- 进度条下方新增阶段文本（连接中 / 拉取清单 / 下载中 / 校验中 / 写入中 / 失败…）
  与「用时」，让用户能区分「还在跑，只是慢」与「真的卡死」；
- 修复 `checkExistingDownload` 中 `status === 'error'` 被误映射为 `'downloading'`
  的问题（原来刷新页面后错误任务会被当成下载中展示）。

### 遇到的问题与解决

- **问题**：容器内 `docker exec` 配合 bash heredoc 执行 Python 时 stdout 为空（退出码 0）。
  **解决**：改用 `base64 -d | docker exec -i ... python -u -` 经 stdin 传入脚本。
- **问题**：`docker cp` 落盘的文件属主为 root，容器内 `workbench`(uid 999) 用户读不到。
  **解决**：同上，走 stdin；写文件用 `write` 工具走宿主机路径后 `docker cp` 覆盖已有文件。
- **问题**：`py_compile` 因容器用户无写权限无法生成 `__pycache__`。
  **解决**：改设 `PYTHONDONTWRITEBYTECODE=1` 并用 `ast.parse` 校验语法。
- **遗留问题 / 待办**：
  1. **上游网络问题（非本代码可修）**：Ollama 容器到模型 CDN
     `dd20bb891979d25aebc8bec07b2b3bbc.r2.cloudflarestorage.com` 不稳定，
     日志可见 `no such host`、`unexpected EOF`、`part N stalled; retrying`，
     单次 pull 曾持续 2h07m 仍无进展。本次修复让这种情况在 10 分钟内收敛为明确的
     error 提示而非永久卡死，但**模型本身仍拉不下来**，需要配置镜像源或更换网络出口。
  2. `redis.close()` 在 redis-py 8.x 中已弃用（应用 `aclose()`）。本仓库其余
     位置（`auth.py` 等）仍统一使用 `close()`，为保持一致本次未改，可统一整理时一并处理。
  3. `README.md` 顶部 version badge 仍为 `1.0.1`，与实际 `v2.0.0` 不一致（非本次范围）。

### 下一步计划
1. **优先**：排查 Ollama 模型下载链路的出口稳定性。`registry.ollama.ai` 的 blob 端点会
   307 跳转到 `dd20bb891979d25aebc8bec07b2b3bbc.r2.cloudflarestorage.com`，长传输偶发
   `EOF` / `part stalled`，这是当前模型实际无法下载到位的原因，与本次代码修复无关。
   **更正**：本条原写「配置 `OLLAMA_REGISTRY_MIRROR` 镜像源」是错的——Ollama 不支持任何
   自定义 registry 环境变量（`OLLAMA_REGISTRY_MIRROR` / `OLLAMA_REGISTRY_URL` /
   `OLLAMA_REGISTRIES` 均不存在，见官方 issue #9409、#13538 的维护者回复），
   blob URL 也是服务端按次生成的签名 URL，无法用 hosts 改指向。
   可用选项：给上述两个域名配稳定出口、给 ollama 容器配 `HTTPS_PROXY`、
   或手动下载 GGUF 后 `ollama create` 导入。
2. 若模型能正常下载，补一轮完整下载冒烟（进度平滑度、速度数值合理性、完成后自动转「已就绪」）。
3. 考虑把暂停 / 恢复 / 取消的按钮与阶段文案做一次体验走查。
