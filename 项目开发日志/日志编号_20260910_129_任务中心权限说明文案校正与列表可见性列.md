### 开发内容详述

#### 一、权限说明文案校正

现有实现（`app/services/task.py` + `app/services/visibility.py`）的准确语义是：

- **列表 / 详情可见条件**：`owner_id == 当前用户` **或** `visibility == PUBLIC`
  **或**（`visibility == RESTRICTED` 且 `restricted_users` 含当前用户）
- **更新 / 删除**：`if task.owner_id != user_id: 403` —— 无 admin 分支，
  管理员与普通成员完全同权
- **创建**：无角色限制，`TaskCreate.visibility` 默认 `Visibility.PRIVATE`

原文案有 4 处失真，逐条修正：

| 原文案 | 问题 | 修正后 |
|---|---|---|
| 「可见范围内的成员可以**查看和处理**任务」 | 非创建者无任何写权限，「处理」不成立 | 「非创建者只能查看自己可见范围内的任务，**不能编辑、调整状态或删除**」 |
| 「私有：仅创建者**和被授权成员**可以查看」 | 私有态不存在授权名单，`restricted_users` 会被 `_normalize_access_flags` 清空 | 「私有：**仅创建者**可以查看」 |
| 「管理员：可以管理自己创建**以及被指定给自己的**任务」 | admin 对被指定给自己的任务同样只读 | 「管理员**不享有额外权限**：只能管理自己创建的任务；对公开或指定给自己的任务同样只读」 |
| 「创建时需设定可见范围」 | 漏了默认值 | 「创建时**可**设定可见范围，**默认为私有**」 |

同时将「指定用户」统一为「受限（指定用户）」——`VISIBILITY_MAP` 的规范标签是
「公开 / 私有 / **受限**」，`VisibilitySetting` 的 Segmented 也显示「受限」，
原文案用「指定用户」会造成与界面标签不一致。

另外把「成员/指定用户权限」这个小节名改为「其他成员」，避免与「指定用户」
这个可见性取值混淆。

#### 二、列表新增可见性列

在「优先级」与「截止日期」之间插入一列：

```tsx
{
  title: '可见性', dataIndex: 'visibility', key: 'visibility', width: 90,
  render: (visibility: string | undefined, record) => {
    const cfg = getVisibilityConfig(visibility ?? 'private');
    const hint = visibility === 'restricted'
      ? `指定用户可见（${record.restricted_users?.length ?? 0} 人）`
      : cfg.description;
    return (
      <Tooltip title={hint}>
        <Tag color={cfg.color}>{cfg.text}</Tag>
      </Tooltip>
    );
  },
},
```

设计要点：

- 复用 `utils/visibility.ts` 的 `getVisibilityConfig`，颜色取 antd 语义色
  （`success` / `default` / `warning`），**未新增任何硬编码色值**，深浅色模式自动适配
- `visibility ?? 'private'` 兜底：`Task.visibility` 在前端类型里是可选的
  （历史数据或旧缓存可能缺该字段），缺省按私有展示，与后端默认值一致
- 受限态在 Tooltip 里额外给出授权人数，非受限态用规范 description

### 遇到的问题与解决

- **问题：`start.sh` 不会构建前端，第一次部署后改动未生效**
  首次执行 `start.sh` 后到容器内核对构建产物，发现新文案字符串全部 NOT FOUND、
  旧文案「被指定给自己的任务」仍在，`TaskManagement-*.js` chunk 时间戳还是 08:44。
  排查 `frontend/Dockerfile` 才发现它**根本不跑 `npm run build`**：

  ```dockerfile
  # 使用本地预构建的 dist 产物（解决容器内网络不可达问题）
  COPY dist /usr/share/nginx/html
  ```

  而 `start.sh` 只做 docker 探测 + `docker compose up -d --build`，没有前端构建步骤。
  因此前端镜像完全取决于 `frontend/dist` 的内容，`dist` 未更新时 `--build` 会命中缓存，
  镜像时间戳停留在 7 小时前，看起来「部署成功」但改动没进去。
- **解决方案**：先 `cd 项目文件/frontend && npm run build`（EXIT=0，`✓ built in 4.65s`），
  再执行 `start.sh`。之后 chunk 重新生成（`TaskManagement-D90uNyuE.js`，07:32 UTC），
  4 条新字符串全部命中。
- **连带发现**：上一条日志（128）的 `TaskModal.tsx` 前端守卫修复同样**未真正部署**，
  直到本次 `npm run build` 才一起进入 `dist`。后端部分此前已正确部署。
- **遗留问题 / 待办**：
  1. `start.sh` 建议补一个前端构建前置步骤（或至少在 `dist` 缺失/过期时提示），
     否则「部署成功」是假象。这是本次发现的流程缺口，影响所有前端改动。
  2. 同类文案问题在**日历模块**也存在：部署产物中
     `CalendarPage-*.js` 仍含「成员/指定用户权限」「仅创建者和被授权成员」，
     与本次修正的任务中心文案口径不一致，建议另开任务统一。
  3. 列表「状态」列的 `Select` 对所有行渲染（含非创建者的公开任务），
     非创建者点击会收到 403 与「更新失败」提示。按用户要求本次**不改权限设计**，
     仅记录；后续可对非 owner 行禁用该选择器。
  4. `README.md` 版本徽标仍为 `version-1.0.1`，实际 `v2.0.0`。
