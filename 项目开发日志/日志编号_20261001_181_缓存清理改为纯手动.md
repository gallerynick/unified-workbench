### 开发内容详述

**1. 关键事实：日志 179 的「72h 保留期」从未生效**

清理前实测（当时构建缓存 10.3GB、可回收 5.489GB）：

| 命令 | 结果 |
|---|---|
| `buildx prune -f --filter until=20h` | **Total: 0B** |
| `buildx prune -f --filter inuse=false` | **Total: 0B** |
| `buildx prune -f --filter bogus=1`（**故意非法**） | **Total: 0B**，exit 0 |
| `buildx prune -f --max-used-space 6GB` | **Total: 0B** |
| **裸 `builder prune -f`** | **Total: 5.489GB ✓** |

**连故意写错的过滤器都返回 `Total: 0B` 且 exit 0**，说明本机 buildx v0.31.2 上过滤器被静默忽略，且**带任何参数时 prune 什么都不做**。

因此日志 179 引入的 `--filter until=72h` 实际是一个**空操作**——它没有「按保留期保护近期层」，只是「什么都没清」。当时我把它当成保护机制，是错的。

**2. 启动流程彻底不碰缓存**

`start.sh` 步骤由 6 步回退为 5 步：

```
[1/5] 环境检查
[2/5] 前端构建
[3/5] 启动服务
[4/5] 健康检查
[5/5] 汇总
```

`start.bat` 回退为 3 步（`[1/3] 环境检查 → [2/3] 前端构建 → [3/3] 启动服务`）。

同步移除：`SKIP_CACHE_PRUNE` 变量、`--skip-prune` 参数、`source .../prune-cache.sh`、`step()` 的 `/6` 编号、以及头部的「为什么必须前置」段落。

**3. 手动脚本重写**

`prune-cache.sh` / `prune-cache.bat` 改为**纯手动、独立执行**（不再被 start 调用）：

| 能力 | 说明 |
|---|---|
| 裸 `builder prune -f` + `image prune -f` | 唯一实测有效形式 |
| 交互确认 | 显示当前缓存大小，回车取消 / y 继续 |
| `--force` / `-f` | 跳过确认；非交互环境必须加 |
| `--help` / `-h` | 用法说明 |
| 自动探测 docker | 复用 `docker-detect.sh` / `.bat` |
| 前后对比 | 清理前后各打印一次 Build Cache 大小 |

脚本注释中明确写入：为什么用裸 prune、过滤器为何不可用、代价是什么。

**4. 手动清理实测结果**

|---|---|---|---|
| 构建缓存 | 10.3 GB | 4.81 GB | **−5.489 GB** |
| Docker 合计 | 26.21 GB | 20.72 GB | −5.489 GB |

服务未受影响：9 个容器全部 healthy，入口校验前端 200 / 后端 200。

**5. 清理的实际代价（重要）**

我原以为「只会清掉旧代、保留新代」。**实际不是**：

| 条目 | 预期 | 实际 |
|---|---|---|
| 新代 `COPY --from=builder` 2.51GB | 保留 | **被删** |
| 旧代 `COPY --from=builder` 2.50GB | 删除 | 删除 |
| 新代 pip / apt 层 | 保留 | 保留 |
| 旧代 pip / apt 层 | 删除 | **保留** |

即：删掉了两个 COPY 大层（含当前代），却留下了旧代的 pip/apt 条目。

更重要的连锁后果：**清理后的下一次完整部署是「从零全量重建」**。实测该次构建 `CACHED` 计数为 **0**、出现 **269 行实际下载**、耗时 **322s**。原因是裸 prune 破坏了缓存记录的父子链，残留条目无法再被复用。

**好消息**：该次全量重建完成后，缓存恢复完整。复测 `buildx build` 得到 **13 处 CACHED、零下载**，说明**代价是「一次性」的**——手动清理后只影响紧随其后的那一次构建，之后恢复正常。

### 遇到的问题与解决

**问题 1：`_du()` 取错列，显示成「当前构建缓存：10」。**
`awk '$1=="Build" && $2=="Cache" {print $4}'` 取到的是 ACTIVE 计数列。
**解决**：改为 `awk '/^Build Cache/ {print $(NF-1)}'`（取倒数第二列 = SIZE），并在注释里写明取错过的原因。

**问题 2：误判「只清旧代」。**
预测与实测不符（见上表）。
**解决**：如实记录在日志与本轮结论中。因无法用过滤器做定向清理（过滤器失效），**「精确只清旧代」在本机不具备可行性**，只能整体清理。
