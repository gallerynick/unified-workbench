### 开发内容详述

#### 一、「模型下载完成」反复弹出：stopPolling 是个空操作

这是 React 闭包陷阱，也是本轮最隐蔽的一处。原写法：

```tsx
const [pollingInterval, setPollingInterval] = useState<NodeJS.Timeout | null>(null);

const stopPolling = () => {
  if (pollingInterval) {          // ← 读的是渲染期闭包里的值
    clearInterval(pollingInterval);
    setPollingInterval(null);
  }
};

const poll = async () => {
  ...
  if (data.status === 'completed') {
    message.success('模型下载完成');
    stopPolling();               // ← 永远清不掉定时器
  }
};

poll();
const interval = setInterval(poll, 1000);
setPollingInterval(interval);    // ← 比 poll 的闭包更晚才生效
```

`poll` 是在 `setPollingInterval(interval)` 之前创建的，它捕获到的 `stopPolling`
里 `pollingInterval` 还是上一次的 `null`。`setInterval` 每次 tick 调用的都是同一个 `poll`
函数对象，闭包不会更新，于是 `clearInterval` 判空直接跳过。

结果：轮询永远停不下来，每秒都拿到 `completed`，每秒弹一次提示。
之前没暴露是因为下载基本走不到 `completed`（卡死在上游），161 把完成路径修通后才显形。

修法：定时器句柄改用 `useRef` 持有，`stopPolling` 直接读写 ref，不经过渲染期闭包。
同时给终态加 `settled` 一次性保护——上一次 `poll` 的网络请求还没返回时，
`setInterval` 仍会再次触发，不加保护会重复弹窗。

顺带修掉一个连带错误：原 `useEffect` 清理函数引用 `stopPolling`，
而 `stopPolling` 定义在 effect 之后，改成 `useCallback` 后 tsc 直接报
`TS2448 block-scoped variable used before its declaration`。清理函数改为直接清 ref，
依赖数组回到 `[]`。

#### 二、模型没下完却报完成：完成判定不看 Ollama 的成功信号

Ollama 的 pull 流在**真正下载完成**时才会发一行 `{"status": "success"}`。
流被 CDN 掐断、重试耗尽、或模型清单异常时，HTTP 连接照样正常关闭，
但不会出现这一行。

原实现只判断「流正常结束且没有内联 `error`」就算成功：

```python
if p.error:
    ... return "pull_error"

await _update_status(redis, task_key, {"status": DownloadStatus.COMPLETED, ...})
return "completed"      # ← 流结束就成功，不管 success 行到没到
```

这就是「下载完成」提示与「测速 0.0 tokens/s」的共同上游：任务被置成 `completed`，
前端弹提示、把模型标记为已下载；但磁盘上的模型其实是不完整的，
Ollama 加载不出来，测速自然拿不到任何有效 token。

（现场已复现：`/api/generate` 对该模型能返回 200 但 `response` 为空、
`done_reason: "length"`，说明权重虽在但内容异常。）

修法：`_ProgressState` 增加 `success` 标记，`_apply_lines` 在解析到含 `success` 的状态行时置位；
`_run_pull` 收尾时三态分流——有 `error` 走 `pull_error`；没 `success` 返回新增的 `interrupted`；
两者都没有才置 `COMPLETED`。`_do_download` 把 `interrupted` 当作连接级异常抛出，
复用既有的重试机制（`MAX_RETRIES=3`、间隔 5 秒），因为 Ollama 会复用已缓存分片，重拉代价很低。

#### 三、测速 0.0 tokens/s：前端读错了 JSON 层级

后端一直把测速指标包在 `details` 里返回，结构如下（已实测确认）：

```json
{"success": true, "message": "测速完成：24.4 tokens/s",
 "details": {"model": "qwen3.5:4b", "tokens_per_second": 24.42,
              "total_tokens": 111, "total_latency_ms": 4544}}
```

前端却在顶层取：

```tsx
const tokensPerSecond = res.data?.tokens_per_second || 0;   // undefined → 0
const totalTokens     = res.data?.total_tokens || 0;        // undefined → 0
const totalLatency    = res.data?.total_latency_ms || 0;    // undefined → 0
```

三个字段全落在 `|| 0` 的兜底分支上，所以提示恒为「测速完成：0.0 tokens/s (0 tokens, 0ms)」。
类型定义里把这三个字段声明成 `TestConnectionResponse` 的顶层可选字段，
把错误结构固化进了 TS，编译器不会报错——这正是它一直没被发现的原因。

修法：类型对齐真实结构（指标移入 `details`，补 `model` / `model_count`），
读数改从 `res.data.details` 取。

### 遇到的问题与解决
1. **`stopPolling` 改成 `useCallback` 后触发 TS2448**：`useEffect` 的清理函数引用了
   定义在其后的 `stopPolling`。清理函数改为直接清 `pollingTimerRef`，不引用具名函数，
   依赖数组恢复 `[]`。
2. **`interrupted` 复用哪条重试路径**：连接级异常走 `_do_download` 的 `except Exception`
   分支（有次数上限与退避），而 `http_error` / `pull_error` / `cancelled` / `timeout`
   是各自独立返回。为了让断流同样受 `MAX_RETRIES` 约束，选择让 `_do_download`
   把 `interrupted` 重新抛成异常，而不是再加一个平行的重试分支——避免两套重试逻辑。
3. **测速读数需要真实响应才能定位**：直接调用 `test_ai_with_config(measure_speed=True)`
   拿到完整响应体，确认指标在 `details` 下，排除了「后端没返回」的可能性。
