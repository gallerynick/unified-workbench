### 开发内容详述

#### 一、症状

两个症状同时出现，且**仅在页面缩放比例不等于 100% 时出现**（用户已确认：「就是缩放
页面之后」）：

1. 调试面板拖不到最右侧
2. 选择元素时高亮框与目标元素错位

#### 二、根因：两套坐标系被混用

页面缩放由 `hooks/usePageZoom.ts` 实现，作用在 `document.documentElement` 上（CSS
`zoom`）。`zoom` 属**布局时缩放**（区别于 `transform: scale`），由此产生坐标分裂：

| 来源 | 坐标系 |
|------|--------|
| getBoundingClientRect()、MouseEvent.clientX / clientY | 缩放后的**视觉坐标** |
| CSS left / top / width、window.innerWidth / innerHeight | 未缩放的**布局坐标** |

两者相差一个 zoom 因子 z。`usePageZoom.ts` 第 8-9 行的注释本身就写明了「布局时缩放，
offsetWidth / clientWidth / getBoundingClientRect 均返回缩放后的值」，上游实现是
正确的（它让所有 portal 浮窗统一跟随缩放，这是收益）；坏在消费方
`DebugModeOverlay.tsx` 把视觉坐标直接当 CSS 长度使用。

**两个症状各自的具体成因：**

- **拖不到右边缘**：`maxX = window.innerWidth - width - EDGE`，其中 `width` 取的是
  `rect.width`（视觉值）。以 z=0.8、1920 宽、面板布局宽度 368px 为例：视觉宽度是
  294.4，于是 maxX = 1920 - 294.4 - 16 = 1609.6（这是布局坐标），换算回视觉只有
  1287.7，面板视觉右边缘落在 1582.1 —— **距视口右边缘还差 337.9px**。
- **高亮错位**：高亮框是 `position: fixed; left: rect.left`。`rect.left` 是视觉坐标，
  而 CSS `left` 按布局坐标解释，再被 zoom 乘一次 → 高亮框相对元素整体偏移且尺寸
  缩放，看起来就是框不住元素。

#### 三、修复：统一存布局坐标，只在边界换算

确立一条单一约定：**`pos` / `hoverRect` / `picked.rect` 一律存布局坐标**（即 CSS
长度的单位），只在「读入 getBoundingClientRect」与「计算视口范围」两个边界处除以 z。
渲染处不再做任何转换。

新增两个助手函数：

- `pageZoomScale()`：读 `document.documentElement.style.zoom`（`usePageZoom` 是唯一
  写入方），解析失败或非正数回退 1。刻意**不调用 `usePageZoom()` 本身**——那会把
  调试面板挂进缩放的引用计数生命周期，而它并不拥有缩放状态。
- `toLayoutRect(r)`：把 DOMRect 的视觉坐标整体换算为布局坐标。

改动共 6 处，全在同一文件：

| # | 位置 | 改动 |
|---|------|------|
| 1 | 模块级 | 新增 `pageZoomScale()` / `toLayoutRect()` |
| 2 | 恢复越界钳制 | `innerWidth/z - PANEL_WIDTH - EDGE`、`innerHeight/z - 120` |
| 3 | 拖拽 onMove | `maxX = innerWidth/z - width/z - EDGE`，且 `x = (clientX - offsetX)/z` |
| 4 | 悬停高亮 | `setHoverRect(toLayoutRect(...))` |
| 5 | 点击锁定 | `rect: toLayoutRect(...)` |
| 6 | 收纳按钮停靠侧 | 视口中心换算为 `innerWidth / z / 2` |

#### 四、刻意不改动之处

- **不动 `usePageZoom`**：它把 zoom 统一施加在 documentElement 上、让所有 portal 浮窗
  跟随缩放，这是正确设计且是收益。问题在消费方假设错了坐标系，改上游会让所有依赖
  缩放的浮窗一起回归。
- **不动 CSS**：`.container` 的 `right/bottom: 16px` 与 `.highlight` 的 `position: fixed`
  本来就是 CSS 长度，缩放下由浏览器自动换算，无需干预。
- **不动 `elementFromPoint(clientX, clientY)`**：`clientX/clientY` 与 `elementFromPoint`
  同处视觉坐标系，互相一致，**选中的元素是正确的，错的只是画出来的框**。
  若也去换算，反而会把选中的元素搞错。
- **未把存储 key 从 `debug-panel-state` 迁移到 v2**：历史上可能存有缩放状态下按视觉
  坐标写入的 `pos`，不迁移意味着最坏情况是面板下次加载位置有偏移；恢复时的越界钳制
  会把越界值拉回视口内，用户重新拖一次即可。迁移则等于让所有人丢位置，代价更高。

#### 六、验证：数值推演

本机无可用浏览器（无 Playwright / Chromium），无法端到端实测。改用数值验证：把新公式
代入多组 zoom × 视口组合，计算面板视觉右边缘与期望值 `innerWidth - EDGE*z` 的缺口。

| zoom | 视口宽 | 新公式缺口 |
|------|--------|-----------|
| 1.0 | 1920 | 0.00 |
| 0.8 | 1920 | 0.00 |
| 1.2 | 1920 | 0.00 |
| 0.8 | 1440 | 0.00 |
| 1.5 | 1280 | 0.00 |

旧公式对照：z=0.8 / 1920 下缺口 337.9px（拖不到右边）；z=1.2 / 1920 下面板视觉右边缘
达 2196.5px，**超出视口 276px 被裁掉**——两个方向都坏，与用户描述一致。

结论依赖两条可确证事实：(1) CSS `zoom` 不改变 `vw` / `innerWidth`（zoom + 100vw 产生
横向滚条是已知问题），故 innerWidth 属视觉坐标；(2) 用户报告的高亮错位本身即证明
getBoundingClientRect 与 CSS left 不同坐标系。
