### 开发内容详述

#### 一、根因：两个数字其实源自同一个缺陷

用户反馈现场是「已下载 3207.3 MB / 总计 3232.9 MB / 用时 34 秒 / 速度一度到几百 MB/s」。
排查后确认，这两个现象是同一个根因的两种表现：**Ollama 续传时会复用本地已缓存的分片**。

Ollama 从 v0.9.6 起，manifest 不再把 blob 地址指向 `registry.ollama.ai`，而是直连
Cloudflare R2 的预签名 URL。已中断的下载会在本地留下 `sha256-*` 缓存分片，
重新拉取时 Ollama 直接复用这些分片，于是它的 `completed` 上报值会在**毫秒级**
从 0 跳到接近 `total`，尽管这期间网络上一个字节都没有传。

实测证据（本次会话中直接验证）：

```text
GET https://registry.ollama.ai/v2/library/qwen2.5/blobs/sha256:c5396...
→ HTTP/2 307
  location: https://dd20bb891979d25aebc8bec07b2b3bbc.r2.cloudflarestorage.com/ollama/.../data?X-Amz-Signature=8b9e8e...
→ HTTP/2 206 Partial Content，remote_ip=198.18.0.29，3.56s 取到 2097152 字节
  首字节 47 47 55 46 03 = GGUF 魔数
```

容器内的 `/root/.ollama/models/blobs/` 下也印证了这一点：
存在一个 `sha256-81fb60c7...-partial`（3389971840 字节）外加 16 个空的 `-partial-N`
分片，而 `ollama list` 是空的 —— 说明这个模型的下载被中断过多次，
每次重启都会复用这些分片。

因此：

- **速度虚高**：旧实现把「本次窗口内 `downloaded` 的增量」除以「窗口内耗时」，
  但增量里包含了上一次就存在的缓存字节，耗时却只有 0.03 秒，
  于是算出 GB/s 量级的假速度。
- **用时失真**：`started_at` 在 `start_model_download()` 创建任务时写一次、之后从不重置，
  但那是**本次任务**的开始时间；而「已下载」里含**上次任务**的缓存字节。
  两个数字口径不一致，才会出现「34 秒下了 3 GB」。

#### 二、速度算法重写（`_apply_lines`）

原实现只有一个 15 秒滑动窗口：入样 → 裁掉窗外样本 → 首尾相减相除。
问题在于它假设「窗口内 `downloaded` 的增量等于窗口内真实下载的字节数」，
这个假设在续传场景下不成立。改为四道防线：

1. **回落清空**：新分片开始、或一次 pull 重试重启时，`completed` 会回落。
   一旦观测到 `downloaded` 小于上次值，整窗清空重锚
   （旧样本属于上一个 blob，留着必然算错）。
2. **重复值不入样**：`completed` 没变时不追加样本。
   否则停滞期间窗口会被无意义的空样本拉长，把首尾增量摊薄成假低速。
3. **锚点跳变剔除**：逐段检查窗口首段的隐含速率，
   超过 `MAX_PLAUSIBLE_SPEED = 250 MB/s` 就把该段弹出并前移锚点，
   直到速率回落到物理合理范围或窗口不足两个样本。
   这就是把「缓存复用跳变」从窗口里挤出去的那一步。
4. **最小跨度**：窗口跨度不足 `MIN_SPEED_WINDOW = 2.0` 秒时不报速度（报 0）。
   防止用 0.03 秒这种极短间隔去相除。

前 2 秒显示 0 是刻意的：那段时间样本还不够，宁可显示 0 也不显示假值。

`MAX_PLAUSIBLE_SPEED` 取 250 MB/s 的依据：千兆有线实际吞吐约 110 MB/s，
250 MB/s 已远超任何真实的网络下载速率，而缓存复用的跳变速率是 GB/s 量级，
两者有约两个数量级的间隔，阈值不会误伤真实高速下载
（已用 120 MB/s 的场景验证过不会被误剔除）。
代价是：如果真的跑出 250 MB/s 以上，该段会被当作跳变剔除 —— 属可接受的取舍。

#### 三、用时修复（两处）

**1. 服务端计算 `elapsed_seconds`，取代前端 `Date.now()` 相减**

旧前端写的是 `Date.now() / 1000 - downloadStartedAt`，
即用浏览器本地时钟去减服务端时间戳。两台机器时钟不一致时，
这个值要么偏大要么偏成负数（`formatDuration` 会把负数兜底成「0秒」，掩盖问题）。

新增 `_with_elapsed()`，在 `get_download_status` 与 `get_user_current_download`
两条读路径返回前统一补上 `elapsed_seconds`，
时钟基准单一且与服务端 `started_at` 严格一致；时钟回拨时钳到 0 而非返回负数。

**2. 未完成任务的 `started_at` 跨任务继承**

任务被取消或出错后重新下载，旧代码会创建一个全新任务、`started_at` 归零，
而「已下载」里还是上次留下的缓存字节 —— 这正是「34 秒 / 3207 MB」的来源。

新增 `_last_incomplete_started_at()`：在同用户同模型的
`cancelled` / `error` 任务里取最近的 `started_at`，新任务沿用该时间，
并把阶段标为「续传中」。这样：

- 「已下载」是跨任务累计的，「用时」也是跨任务累计的，口径一致；
- 只有 `cancelled` / `error` 两种未完成终态会被继承，
  避免把已完成模型的时间轴串到下一次全新下载上。

注意 `_last_incomplete_started_at()` 只在**创建新任务时**调用一次，
同用户同模型的活跃任务仍走 `_find_active_task()` 单飞复用，不会被绕过。

#### 四、前端展示

- `DownloadStatus` 类型补 `elapsed_seconds?`；
- `ThirdPartyConfigPage` 把 `downloadStartedAt` 状态换成 `downloadElapsed`，
  三个赋值点（`checkExistingDownload` 恢复状态、启动下载重置、轮询进度）全部改读
  `elapsed_seconds`；
- 渲染处直接 `formatDuration(downloadElapsed)`，
  不再出现 `Date.now()` 与服务端时间戳混用。

#### 五、顺带修掉的进度爆炸（按 blob 聚合）

修完速度后做端到端验证时，抓到第三个同源缺陷：**`progress` 会在下载末尾炸成几百万个百分点**。
实测一次真实拉取，末尾两个采样点是 `progress: 3506855.3`、`total` 从 397.8 MB 变成 490 字节。

根因同样是 Ollama 的上报口径。直接抓取 `/api/pull` 原始 NDJSON 确认：

```text
{"status": "pulling d502d55c1d60", "total": 675}
{"status": "pulling 58d1e17ffe51", "total": 11357}
{"status": "pulling f02dd72bb242", "total": 59}
{"status": "pulling b0f58c4c1a3c", "total": 561}
{"status": "verifying sha256 digest"}
{"status": "writing manifest"}
{"status": "success"}
```

Ollama 的 `total` / `completed` 是**按单个 blob** 上报的，不是整个模型。一个模型由
manifest、system、template、license 等多个 blob 组成，逐个下载，每个 blob 有自己的
`total` 且 `completed` 从 0 重新开始。旧实现取「最后一条覆盖」，于是 `total` 退化成
最后一个 blob 的大小，`progress = downloaded / total * 100` 就炸了。

改为按 blob 聚合，用 `status` 里的 blob 标识做键：

1. **按 blob 累加**：新增 `_blob_id_from_status()` 从 `status` 文本提取 blob 标识，
   `p.blobs` 记录每个 blob 的 `total` / `completed`，两者都取 `max`（Ollama 会重复上报
   同一 blob 的 total），模型总量与已下载量取所有 blob 之和。
2. **缓存分片视为已就位**：只报 `total` 不报 `completed` 的 blob 是本地缓存命中，
   直接把它的 `completed` 记为 `total`。否则全部命中缓存的模型进度会一直停在 0%。
3. **进度钳到 100%**：`min(100.0, ...)` 兜住浮点误差。

顺带清理：`downloaded` 现在单调不减，原来那套「completed 回落时清空窗口」的分支变成
死代码，连同 `last_completed` 字段一起删掉。

### 遇到的问题与解决

1. **容器内代码与宿主机不同步**：首轮单测 5 个场景全部返回 `None`，
   起初怀疑算法没生效。核对后确认是容器里还是改动前的旧代码
   （`grep` 新符号 0 命中，宿主机 9 命中），`docker cp` 后全部通过。
2. **测试脚本无法落盘**：`docker cp` 写入的文件属 root，
   容器内 `workbench`(uid 999) 用户读不到，报 `Permission denied`。
   改为 base64 解码后经 stdin 传入（`docker exec -i ... python -u -`）。
3. **Python 脚本经 base64 传入时字符串截断**：脚本内含反斜杠 n 的字面量，
   在 heredoc / 多层引号中被提前解析，触发 `SyntaxError: unterminated string literal`。
   改为用数组按行拼接源码，避开嵌套转义。
4. **上游网络问题（非本代码可修）**：Ollama 的 blob 端点 `registry.ollama.ai`
   会 307 跳转到 `dd20bb891979d25aebc8bec07b2b3bbc.r2.cloudflarestorage.com`，
   长传输偶发 `unexpected EOF` / `part N stalled; retrying`。
   本次修复让它收敛为明确的 error 而非永久卡死。
   **更正**：早前记录的「配置 `OLLAMA_REGISTRY_MIRROR`」是错的 ——
   Ollama 不支持任何自定义 registry 环境变量
   （`OLLAMA_REGISTRY_MIRROR` / `OLLAMA_REGISTRY_URL` / `OLLAMA_REGISTRIES` 均不存在，
   见官方 issue #9409、#13538 的维护者回复），
   且 blob URL 是服务端按次生成的预签名 URL，签名覆盖 host，无法用 hosts 或环境变量改指向。
   可用选项只有：给上述两个域名配稳定出口、给 ollama 容器配 `HTTPS_PROXY`、
   或手动下载 GGUF 后 `ollama create` 导入。
