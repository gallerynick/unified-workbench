#### 1. 数据模型（T1.1 / T1.2）

note 表补三列，全部 nullable，旧数据零影响：

    body          JSONB   Tiptap 文档树，与旧版 content 并存
    plain_text    Text    由 body 派生，专供搜索与摘要
    restricted_tags JSONB 受限标签（标签名本身敏感）

新建两表：

    note_link  (source_id, target_id)  uq_note_link_src_tgt
                 FK → note.id ondelete=CASCADE，两侧建索引
    note_draft (owner_id, note_id?)    uq_note_draft_owner_note
                 note_id 可空 = 「尚未关联笔记的新笔记草稿」

**关键决策一：note_link 是双链边的唯一数据源，绝不扫描 JSON。**
body 是任意嵌套的文档树，遍历成本随正文体积线性增长；建独立边表后
反向链接与图谱都是索引查询。设计规格 8.1 明确：只有 type == "wikilink"
的节点建边，note-embed（笔记内嵌卡片）为只读渲染，不计入图谱。

**关键决策二：note-embed 嵌套硬限一层。**
A 内嵌 B、B 内嵌 C 会在渲染层形成递归取数；前端按一层渲染，后端不做
递归展开，超出部分展示为占位。

**关键决策三：note_draft.note_id 可空 + 部分唯一索引。**
「新建笔记未保存草稿」的 owner_id + note_id(NULL) 组合无法用普通唯一约束
保证一人一份（NULL 在唯一约束下互不相等），故在迁移中补一条
CREATE UNIQUE INDEX uq_note_draft_new (owner_id) WHERE note_id IS NULL。

#### 2. 纯文本派生（T1.4）

app/services/note_text.py 的 extract_plain_text(body) 深度遍历 Tiptap 节点树，
只在 _BLOCK_TYPES 集合（paragraph / heading / listItem / taskItem / blockquote /
codeBlock / tableCell）拼接文本，块间以空行分隔。非白名单节点（wikilink /
note-embed / horizontalRule 等）不产文本——它们的语义由独立机制表达。

调用时机：创建时、更新时（且仅当本次请求带 body）。只改 title/tags 的更新
不动 plain_text，避免无谓重算。

#### 3. 迁移的双通道（T1.3）——本次最重要的一处工程判断

排查部署链路时发现：**Alembic 迁移在生产环境不会执行。**

    backend/Dockerfile 的 CMD：python app/startup_migrate.py && uvicorn ...
    app/startup_migrate.py：Base.metadata.create_all(...) + 幂等 inline SQL

create_all 只创建缺失的**表**，从不给已有表**加列**。因此新增的 body /
plain_text / restricted_tags 三列若只写 Alembic 047，线上笔记接口会因
「column does not exist」直接报错。

同时 046 迁移的 docstring 已自证这一点：「线上库由 Base.metadata.create_all
首次建表，未初始化 alembic_version」——Alembic 目前只是版本记录与离线
SQL 校验工具。

所以本次为**每个新增列与索引都写了两份**：

- alembic/versions/047_*.py（186 行）：upgrade 建列、回填、建两表、建
  pg_trgm 扩展与 GIN 三 gram 索引；downgrade 对称回滚。回填逻辑把旧版
  content 按空行切段包成最小 Tiptap 文档写回 body，并同时算出 plain_text，
  json.dumps(..., ensure_ascii=False) 保证中文不被转义
- app/startup_migrate.py（同一批 inline SQL）：3 条 ALTER TABLE ... ADD COLUMN
  IF NOT EXISTS、同样的回填循环、CREATE EXTENSION IF NOT EXISTS pg_trgm、
  CREATE INDEX IF NOT EXISTS ix_note_plain_text_trgm、部分唯一索引

note_link 与 note_draft 两张新表由 create_all 负责首次建表，故 inline SQL
只为它们补「非模型定义的索引」，无需手写 CREATE TABLE。

**Alembic 离线校验通过**：upgrade 与 downgrade 两个方向都能生成完整 SQL。
Docker 未运行、无网络，无法对真实 PostgreSQL 执行，离线 SQL 生成是当前
可达到的验证上限。

#### 4. 双链服务（T1.5 / T1.6）

app/services/note_link.py：

    extract_link_targets(body)      遍历文档树，只取 type == "wikilink"
                                    的 attrs.target_id，去重保序
    rebuild_outgoing_links(db,id,  先 delete 后 insert 全量重建出边；
                        body)      目标 id 非法 UUID 或笔记不存在时静默跳过
    get_backlinks(db, note_id,uid) 按目标反查 source，逐条做可见性过滤，
                                    摘要取 plain_text（回退 content）截 120 字
    get_graph(db, uid, root=?,     root 为空返回全局图谱；否则以 root 为根做
              depth=1)             双向 N 跳 BFS（depth 钳制 1–2），
                                    节点与边都只保留落在最终集合内的部分

**关键决策一：删除出边不依赖数据库触发器，由应用层显式重建。**
保存 body 时先删该笔记全部出边再按新文档重建，语义单一、可测试、
不引入 DB 方言差异。note.id 的 ondelete=CASCADE 覆盖笔记被删除的场景。

**关键决策二：get_backlinks 延迟导入 note 服务。**
note 服务需要调用本模块的 rebuild_outgoing_links，而本模块需要 note 服务的
可见性判定函数；模块级互相 import 会成环，故在函数体内延迟导入
_visibility_get_check。

**关键决策三：图谱 depth 上限 2。**
20 人团队的知识库体量小，但双向 BFS 在大图上会膨胀；1–2 跳覆盖
「当前笔记的直接引用/被引用」与「一层间接关联」，再深意义有限。
FastAPI Query(ge=1, le=2) 在服务层与路由层双重钳制。

#### 5. 搜索与标签过滤（T1.7）

list_notes 的 search 现在覆盖四个字段：title、plain_text、category 用 ilike
模糊匹配，tags 走独立的 _tags_contains_expr。新增 tag 参数做标签精确筛选。

_tags_contains_expr 按方言分支：

    PostgreSQL  Note.tags.contains([value])    JSONB @>，可被 GIN 索引加速
    SQLite      EXISTS (SELECT 1 FROM json_each(tags) WHERE value == :v)

**这里踩过一个真实的方言陷阱，值得记录。**
最初实现用 func.json_each(Note.tags.cast(JSON))，PostgreSQL 侧语法是对的，
但 SQLite 下 json_each 返回空结果——实测 json_each 必须直接收列本身，
写 CAST(tags AS JSON) 反而让函数拿不到内容。因此不做类型转换。

另一个陷阱：SQLAlchemy 的 JSON 类型在 SQLite 上用 json.dumps 默认
ensure_ascii=True 序列化，中文被存成 \uXXXX 转义序列，导致
LIKE '%关键词%' 在 SQLite 上永远匹配不到中文。PostgreSQL 的 JSONB
会规范化为真实 Unicode，同一查询在两边行为不同。这个差异使 SQLite 测试
无法验证 PG 的真实语义，只能保证测试环境自洽；日志中如实标注。

**语义收敛：标签按「元素相等」匹配，不做子串。**
Note.tags.contains([x]) 是 PG 的 @> 包含语义；SQLite 侧 json_each 也只能做
等值比较。两者一致地实现了「标签精确命中」，因此搜索「关键词」不会命中
标签为「标签关键词」的笔记。这个行为差异写在测试 docstring 里，避免后人
误读为 bug。

#### 6. 草稿服务与端点（T1.8 / T1.9）

app/services/note_draft.py 三个函数：get_draft / upsert_draft / delete_draft。
全部以 owner_id 限定——**草稿不做可见性判定**，草稿是个人工作副本，
与笔记的 public / private / restricted 无关。

**关键决策：草稿表的时间戳用服务端生成。**
saved_at 配置 server_default=func.now() 与 onupdate=func.now()（符合项目
既有模型风格）。但 flush 后该属性处于过期状态，Pydantic 的
model_validate(from_attributes) 同步读取会抛 MissingGreenlet——异步会话
里不能在同步上下文里做 IO。解法是 upsert 后显式 await db.refresh(draft)，
而不是把 onupdate 挪回 Python 侧生成时间。

新增 6 个端点（全部统一响应格式 + 尾斜杠约定）：

    GET    /notes/tags                  标签聚合（仅可见笔记，按次数降序）
    GET    /notes/graph                 全局图谱
    GET    /notes/draft?note_id=        读本人草稿
    PUT    /notes/draft                 保存/覆盖本人草稿
    DELETE /notes/draft?note_id=        删本人草稿
    GET    /notes/{id}/backlinks        反向链接
    GET    /notes/{id}/graph?depth=1|2  局部图谱

**路由顺序是本次的显式约束**：/tags、/graph、/draft 必须声明在 /{note_id}
之前，否则 note_id 会吞掉字面量并因 UUID 解析失败返回 422。已在 api/notes.py
的注释中标注，并靠三个端点测试（tags / graph / draft 全部返回 200）验证生效。

标签聚合的实现在应用层展开 tags 计数而非写 SQL 展开数组——复用现成的
可见性过滤，且避免在 PostgreSQL / SQLite 各维护一套 jsonb_array_elements_text
/ json_each 的展开 SQL。20 人团队可见笔记量很小，这个取舍明显更划算。

### 遇到的问题与解决

1. **Alembic 迁移在生产不执行**（最重要）
   - 现象：若只写 047，线上加列不会发生
   - 定位：Dockerfile 的 CMD 直接跑 startup_migrate.py，其中 create_all
     只建缺失表、从不加列；046 的 docstring 已自证
   - 解决：每个新增列/索引写两份——Alembic 047 + startup_migrate.py inline SQL
   - 遗留：Alembic 版本链缺 006/007/008 导致双 head、009 指向不存在的 008，
     建议单独立项清理

2. **startup_migrate.py 当前未纳入版本控制**
   - 该文件在 git 里是 untracked（??），属并行工作流所有，但它是生产实际
     执行的迁移路径，且本次必须改动它才能让 P1 在部署时落地
   - 处理：本次**已修改该文件但未提交**，刻意不把它混进本次提交
   - 遗留（需你决定）：它至今未进版本控制，意味着任何 clone 出的仓库跑
     startup_migrate.py 都会缺 P1 的加列逻辑。建议尽快把它纳入正式跟踪

3. **SQLite 与 PostgreSQL 的 JSON 语义不一致**（见上节第 5 点）
   - json_each 必须直接收列本身，CAST 后返回空
   - SQLite 存 CJK 为 \uXXXX，LIKE 永远匹配不到中文
   - 解决：方言分支 + 日志如实标注，不做「统一语义」的过度工程

4. **contains() 无法用 @compiles 定制 SQLite 方言**
   - Note.tags.contains([x]) 编译为普通 BinaryExpression，运算符是 contains_op，
     没有可挂 @compiles 的专用类（尝试 @compiles(JSONContainsOp) 直接 ImportError）
   - 解决：改为在服务层写 _tags_contains_expr 的方言分支

5. **MissingGreenlet**
   - 见第 6 节；upsert 后加 await db.refresh()

6. **循环外键导致 drop_all 失败**
   - 见第 7 节；teardown 在独立连接上先关 FK
