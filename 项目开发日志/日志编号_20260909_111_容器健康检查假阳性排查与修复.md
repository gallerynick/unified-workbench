### 开发内容详述

#### 一、排查过程与结论

初始现象：db / redis / backend / mediamtx 为 healthy，nginx / frontend / celery / celery-beat 为 unhealthy。但 https://localhost 实测返回 200，服务本身可用 —— 因此怀疑是健康检查配置问题而非服务故障。逐层取证如下。

**线索 1：docker-compose.yml 里这四个服务根本没有定义 healthcheck**，只有 db 和 redis 定义了。说明 unhealthy 来自 Dockerfile 内嵌的 HEALTHCHECK 指令（镜像级配置），而非编排层。

**结论 A：celery / celery-beat —— 纯假阳性，服务完全正常**

两者共用 backend 的 Dockerfile，因此继承了 backend 的健康检查 curl -f http://localhost:8000/api/v1/health。但 celery 容器跑的是 celery worker、beat 容器跑的是 celery beat，**都不监听 8000 端口**，该检查必然失败。

实际运行状态（日志实证）：
- worker：每 10 秒成功消费 check-due-reminders / check-calendar-reminders，succeeded
- beat：持续 Scheduler: Sending due task，调度正常
- celery inspect ping 实测：1 node online，exit=0

**结论 B：frontend —— 纯假阳性，服务完全正常**

健康检查为 wget -q --spider http://localhost:80。实测容器内 getent hosts localhost 返回 **::1（IPv6 优先）**，而 nginx 只绑定 0.0.0.0:80（IPv4），因此连接 ::1:80 被拒。

容器内直连验证：wget http://127.0.0.1:80/ 返回 **HTTP/1.1 200 OK**（nginx/1.25.5）。服务完全正常，仅健康检查的 DNS 解析目标选错。

**结论 C：nginx —— 纯假阳性，且健康检查口径本身也有缺陷（两层问题）**

1. 同 B 的 localhost → ::1 问题
2. 即使改用 127.0.0.1，原检查目标 http://127.0.0.1:80/health 仍失败：80 端口全量 **301 跳转 HTTPS**（Location: https://127.0.0.1/health），而 wget --spider **不跟随重定向**，实测 exit=1

该服务实际健康：https://127.0.0.1:443/health 经 location /health 反代至 backend，实测 exit=0。

#### 二、修复方案

**frontend/Dockerfile**：localhost → 127.0.0.1。实测 exit=0。

**nginx/Dockerfile**：改为 https://127.0.0.1:443/health 并加 --no-check-certificate（跳过自签证书）。实测 exit=0。
选择该口径而非仅探测 nginx 自身，是因为 location /health 反代至 backend /api/v1/health，因此一个检查同时覆盖 nginx 配置正确性与上游连通性 —— 上游挂掉时 nginx 报告 unhealthy 是符合预期的（此时确实无法提供 API 服务）。

**docker-compose.yml**：
- celery 增加真实就绪检查 celery -A app.tasks inspect ping --timeout 5（interval 60s / timeout 20s / start_period 30s）。该命令要求 broker 可达且 worker 在线响应，是 celery worker 的标准探测手段。
- celery-beat 显式 healthcheck: disable: true。理由：beat 无监听端口、无 ping 接口；调度文件 /tmp/celerybeat-schedule 仅在计划变更时写入（实测相邻两次采样 mtime 均无变化），不构成可靠信号；镜像内也无 pgrep / ps（未装 procps）。进程存活由 restart: unless-stopped 兜底，broker 连通性已由 worker 的 inspect ping 覆盖。

#### 三、修复前后对照

| 容器 | 修复前 | 根因 | 修复后 |
|---|---|---|---|
| frontend | unhealthy | localhost 解析为 ::1，nginx 仅监听 IPv4 | 健康检查指向 127.0.0.1 |
| nginx | unhealthy | 同上 + 80 端口 301 且 --spider 不跟随重定向 | 直连 443 的 /health，跳过自签证书 |
| celery | unhealthy | 继承 backend 检查，worker 不监听 8000 | inspect ping 真实就绪探测 |
| celery-beat | unhealthy | 继承 backend 检查，beat 不监听 8000 | 显式禁用（无可靠探测手段） |

### 遇到的问题与解决
- 问题：celery-beat 的调度文件 mtime 采样不可靠。
- 解决：实测相邻两次采样 mtime 完全不变（1788931057 → 1788931057，当前时间已推进 5 秒），确认该文件仅在计划变更时写入，不能作为心跳信号，故改用显式禁用。
- 问题：python:3.11-slim 镜像内无 pgrep / ps / redis-cli / wget。
- 解决：改用镜像内已有的 celery CLI 与 /proc 文件系统；nginx:1.25-alpine 内 curl 与 wget 均可用。
- 问题：python 环境无 pyyaml，无法用脚本校验 compose。
- 解决：改用 docker compose config --quiet 做权威校验，通过。
- 遗留问题 / 待办：无。本次为配置修复，不改变任何运行时行为。
