### 开发内容详述

#### 一、后端：`GET /tasks/` 支持 `owner_id` 筛选

`api/tasks.py` 的 `list_tasks_endpoint` 新增 `owner_id: uuid.UUID | None = Query(None)`，
传给服务层；`services/task.py` 的 `list_tasks` 新增 `owner_id` 参数并追加
`query = query.where(Task.owner_id == owner_id)`。

写法与 `services/announcement.py` 的 `list_announcements` 一致（同样的
`if owner_id is not None:` 守卫）。

**安全语义：`owner_id` 是收窄条件，不是授权条件。** 它始终与可见性过滤
`build_visibility_filter` **AND 叠加**，因此用户只能在自己本就可见的范围内
按创建者筛选，无法借 `owner_id` 看到无权访问的任务。见下文测试第 4 项。

顺手把 `list_tasks` 第一个参数名从 `owner_id` 改为 `user_id`（该参数装的是
当前用户 id，原命名与新增的「创建者筛选」参数撞名，且函数体内有一行
`user_id = owner_id` 的别名转换），去掉了这行别名。

#### 二、前端：`Tabs` + 「我创建的」筛选

`TaskManagement.tsx` 照公告中心范式：

- `type TabKey = 'all' | 'mine'`，`activeTab` 默认 `'all'`
- `TAB_ITEMS = [{key:'all',label:'全部'},{key:'mine',label:'我创建的'}]`
  （提为模块级常量，避免每次渲染重建）
- `handleTabChange`：切 Tab 时 `setPage(1)`，避免停留在越界页码
- `currentUserId = getUserId()`，`activeTab === 'mine'` 时
  `params.owner_id = currentUserId`
- `useCallback` 依赖数组补上 `activeTab` 与 `currentUserId`

`TaskManagement.module.css` 新增 `.tabs { margin-bottom: var(--spacing-xs); }`，
与公告中心一致，间距取 design token。

#### 三、非创建者行的操作可用性

「全部」Tab 会列出他人创建的公开 / 指定任务。这些行原本照常渲染「编辑 / 删除」
按钮和可操作的「状态」下拉，非创建者点击会收到 403 与「更新失败」提示。

对齐公告中心的 `canManage` 范式补齐：

```tsx
const canManage = (task: Task): boolean => task.owner_id === currentUserId;
```

- 「操作」列：不可管理时渲染 `只读` + Tooltip「仅创建者可编辑或删除」
- 「状态」列 `Select` 加 `disabled={!canManage(record)}`，保留可读、禁用可写

**未改动任何权限判定逻辑**：后端 `update_task` / `delete_task` 的
`if task.owner_id != user_id: 403` 仍是唯一权威，前端只是不再展示点不动的按钮。
任务模块管理员无额外权限，因此 `canManage` 没有像公告那样加 `isAdmin()` 分支。

#### 四、连带修复：`listTasks` 前端 API 漏了 `owner_id`

**这是本次最容易漏的一步。** 第一版实现里 `TaskManagement.tsx` 构造的
`params` 带了 `owner_id`，但 `api/tasks.ts` 的 `listTasks` 形参类型只有
`page / page_size / status / priority`。

`npx tsc -b` **完全通过**——因为 `params` 是变量而非对象字面量，
TypeScript 的 excess property check 只作用于直接赋值的字面量，
变量传递时多余属性被结构类型检查放过。结果是 `owner_id` 会被静默丢弃，
「我创建的」Tab 显示与「全部」完全相同的列表，且没有任何报错。

与上一条日志（128）的 Pydantic `extra='ignore'` 属同一 bug 类别：
**契约层少声明一个字段，两端都静默。** 已在 `listTasks` 的形参类型和
`URLSearchParams` 构造处补上 `owner_id`。

### 遇到的问题与解决

- **问题：`listTasks` 不接受 `owner_id` 但 `tsc` 不报错**
  见上文第四节。变量传参绕过 excess property check。
  解决：补形参类型 + 补 `searchParams.set('owner_id', ...)`。
- **问题：回归脚本第一条断言写错，误判为「越权筛选泄露」**
  初次断言 `B 视角 + owner_id=A` 应为 0 行，实际返回 A 的公开任务 1 行。
  排查后确认是**我的断言错了、代码是对的**：`owner_id` 与可见性过滤 AND 叠加，
  B 本就可见 A 的公开任务，故它出现在该筛选结果中；A 的私有任务始终未泄露。
  修正断言为「行数 == 1 且全部 visibility == public」后通过。
- **遗留问题 / 待办**：
  1. `start.sh` 仍不构建前端（129 记录的流程缺口未修）。本次又是先
     `npm run build` 再 `start.sh`，且中途因补 `listTasks` 重新构建过一次。
  2. 日历模块权限说明文案口径不一致（129 记录）。
  3. `README.md` 版本徽标仍 `version-1.0.1`，实际 `v2.0.0`。
  4. 前端各处 `list*({ ...params })` 的调用方都靠人工保证形参同步，
     建议后续统一从 schema 生成或加一层契约测试。
