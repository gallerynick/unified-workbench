### 开发内容详述

**1. 根因（实测确认，非推断）**

用 `apt-get update -o Debug::Acquire::http=true` 抓取了 apt 的实际请求序列：

```
Ign:4 ... trixie/main arm64 Packages      ← 反复重试
Err:4 ...
E: Failed to fetch .../main/binary-arm64/Packages  404  Not Found
```

配合 `GET` 路径日志，apt 的真实尝试顺序是：

```
by-hash/SHA256/<.xz 的 sha256>   ← 首选（压缩率最高）
by-hash/SHA256/<.gz 的 sha256>   ← 次选
by-hash/SHA256/<plain 的 sha256> ← 末选
直连 Packages.xz → Packages.gz → Packages
```

**结论**：这不是「缺文件」问题，而是**大文件传输超时 + 回退链末端必死**：

1. Debian 的 `main/binary-arm64/Packages.xz` 约 **9.6MB**，本机网络下下载会停顿
2. apt 依次降级尝试 xz → gz → 未压缩
3. **Debian 已不再发布「未压缩」索引**——官方源、清华、中科大、阿里云**全部 404**，但 Release 文件仍声明它
4. 于是回退到底时收到秒回 404，apt 视其为致命错误（`E: Failed to fetch`）并中断构建

**为什么「之前不会」**：apt 层此前一直命中构建缓存，根本没联网。缓存一旦被清（日志 179），apt 就必须真正执行，这个长期存在的潜在缺口随即暴露。

**2. 定位过程中被推翻的假设**

| 假设 | 实测结论 |
|---|---|
| 基础镜像从 bookworm 漂移到 trixie | ❌ 该层是 4 周前的，未漂移 |
| 阿里云镜像站同步不完整 | ❌ 官方源、清华、中科大同样 404 |
| 本地 HTTP 代理干扰（报错 IP `198.18.0.60` 属保留段） | ❌ 换 HTTPS 请求官方源同样 404 |
| 只需放宽 apt 超时 | ❌ 实测 `Acquire::http::Timeout=600` + `Retries=5` 仍 FAIL |
| 镜像站的 `.xz` 哈希与 Release 不符 | ❌ 下载校验，md5/sha256 **完全一致** |

**3. 真正的判别实验：换源测速**

| 镜像站 | apt-get update 结果 | 速度 |
|---|---|---|
| **清华 tuna** | **EXIT=0** | 10.1 MB / **2 秒**（5658 kB/s） |
| 官方 deb.debian.org | EXIT=0 | 10.1 MB / 50 秒（202 kB/s） |
| 阿里云 | **EXIT=100 失败** | 传输停顿 |

清华源比官方源快 28 倍且成功，阿里云在本机网络下会停顿。**故换用清华源。**

**4. 改动内容（`backend/Dockerfile`）**

**4.1 Debian 源：阿里云 → 清华**（builder 与 stage-1 两处）
```
http://mirrors.aliyun.com/debian          →  http://mirrors.tuna.tsinghua.edu.cn/debian
http://mirrors.aliyun.com/debian-security →  http://mirrors.tuna.tsinghua.edu.cn/debian-security
```

**4.2 新增 apt 调优** `/etc/apt/apt.conf.d/99-build-tuning`（两处）
```
Acquire::http::Timeout "600";        ← 默认 120s，不足以在慢链路下下完 9.6MB 索引
Acquire::https::Timeout "600";
Acquire::Retries "5";
Acquire::http::Pipeline-Depth "0";   ← 关闭 HTTP 流水线，对有本地代理的环境更稳
```

**4.3 pip 加固**（不改版本，仅放宽容错）
```
--retries 10 --timeout 120
```
torch 的 aarch64 wheel 有 200MB+，慢链路下会下载中断并报 `Wheel 'torch' ... is invalid`。

**4.4 明确未改动**
- **保留 PGDG 与 `postgresql-client-15`**：这是并发会话基于真实功能需求引入的——Debian 13 默认仓库只有 PG17，而 `pg_restore` 17 在初始化时无条件执行 `SET transaction_timeout = 0`，PG15 服务端不识别，恢复会直接失败。
- **未改 torch 版本**：清华 PyPI 有 `torch-2.9.1`，而 pytorch.org 提供的是 `2.14.1+cpu`。换源会降版本，属功能变更，故只做容错加固，不动版本。
- 未改基础镜像 tag（`python:3.11-slim-trixie` 这个 tag 并不存在，无法固定）。

### 遇到的问题与解决

**问题 1：Dockerfile 行续接符被写成两个反斜杠，构建直接解析失败。**
`target backend: failed to solve: dockerfile parse error on line 17: unknown instruction: &&`
**解决**：Dockerfile 只认单个 `\` 作续行；改为单反斜杠后正常。同时修正了注释块中被写成字面量 `\n` 的换行（printf 格式串内的 `\n` 保留不动）。

**问题 2：apt 修复后构建推进到 pip 阶段，torch wheel 下载损坏。**
`ERROR: Wheel 'torch' located at /tmp/pip-unpack-.../torch-2.14.1+cpu-cp311-cp311-manylinux_2_28_aarch64.whl is invalid.`
日志显示当时下载速率仅 176–363 kB/s。**解决**：加 `--retries 10 --timeout 120` 后重跑，构建一次通过。

**问题 3：测速实验本身不可靠。**
用 `curl -r 0-31457280` 做限时测速时只取到 263 字节 / 153 字节，返回的是错误页而非 wheel 数据，未能得到可信带宽数字。
**解决**：放弃带宽对比，改用端到端判别实验（同一容器内跑 `apt-get update` 看 EXIT 与 `Fetched ... in Ns`），该指标直接、可信。
