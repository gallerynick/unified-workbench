### 开发内容详述

**一、缺陷类与规则**

日志 134 暴露的根因是一条链：schema 字段没有上限 → 请求值超过数据库列容量 → asyncpg 抛
DataError（int4 溢出 / varchar 超长）→ 未被捕获 → FastAPI 默认 500 且返回 text/plain →
前端 request.ts 的 response.json() 解析失败 → 兜底成 "Request failed"。

本次采用的修复规则是「校验上限 = 存储上限」：

- 列类型为 String(N) → 字段加 max_length=N
- 列类型为 Integer(int4) → 字段加 le=INT4_MAX（2_147_483_647）
- 有硬件或协议硬约束的字段例外：cpu_cores / cpu_allocated → MAX_CPU_CORES（4096）；
  port / smtp_port → MAX_PORT（65535）

**二、上限常量集中定义**

在 app/schemas/common.py 新增三个常量，供各 schema 复用，避免上限散落在 24 个文件里
将来各改各的：

- INT4_MAX = 2_147_483_647（PostgreSQL Integer 上限）
- MAX_CPU_CORES = 4096
- MAX_PORT = 65535

servers 模块原本自定义的 MAX_CAPACITY = 10_000_000 删除，ram_capacity / disk_capacity 改为
le=INT4_MAX。原来的 10,000,000 是人为业务上限，既无硬件依据，又会在 KB 单位下把一个
约 10 GB 的内存写成 10^13 而错误拒绝——属于「校验上限低于存储上限」的同类缺陷。
前端 ServerFormModal.tsx 的 MAX_CAPACITY 同步改为 2_147_483_647，保持前后端一致。

**三、排查方法**

写脚本同时读取两边的事实，机器比对而不是人眼扫：

- 一侧从 SQLAlchemy Base.metadata 取每张表的列类型与长度
- 另一侧从各 schemas 模块的 Create / Update 类用 Pydantic model_fields 取现有约束
- 按「列有上限而字段无约束」输出偏差清单

第一次跑出来的偏差数偏大，原因是两个误判，修正后才得到准确的 144 条：

1. 跳过规则只认 Literal[X]，不认 Optional[Literal[X]]（ram_unit / disk_unit），
   改递归剥 Optional 后判 Literal
2. 用 cls.__pydantic_decorators__.validators 探测自定义校验器拿不到任何结果，
   导致 status / environment 这类由 @field_validator 管约束的字段被误判，
   改为正则扫描源码里的 @field_validator("name") 与 @field_validator([...]) 提取字段名
3. 补充按注解类型过滤：列是 String 但注解是枚举（Visibility）或 Literal 的，
   不能加 max_length；列是 Integer 但注解不是 int 的，不能加 le

最终偏差清单 144 个字段，涉及 24 个文件。

**四、改写方式**

用脚本做确定性文本改写，逐行区分三种声明形态并分别处理：

- 裸注解无默认值：name: str → name: str = Field(max_length=200)
- 裸注解带默认值：category: str = "默认" →
  category: str = Field(default="默认", max_length=50)
- 已有 Field 调用：quantity: int = Field(default=0, ge=0) →
  quantity: int = Field(default=0, ge=0, le=INT4_MAX)

需要 Field 的文件自动补进 pydantic 导入，用到常量的文件自动补
from app.schemas.common import ... 导入，随后 ruff --fix 整理导入顺序。

**五、跳过与不动的范围**

- @field_validator 管约束的字段（server.status、system.status、system.environment 等）：
  校验器自己负责，不叠加约束
- Literal / Optional[Literal] 字段（server.ram_unit、server.disk_unit）：字面量集合天然有界
- 注解为枚举的字段（form/project/task/topology/vote 的 visibility）：枚举值集合天然有界
- Text 列、JSONB 列：无长度上限，无需约束
- 无表支撑的模型（user_preference 走用户表 JSONB、file_share 的 ReservedSpaceUpdate
  改系统配置、stream_room 的 StreamRoomConfig 存 JSONB、project_proposal_comment 的
  content 为 Text）：没有对应列容量，不适用本规则

### 遇到的问题与解决

1. **首次改写把类型注解一并塞进 default**：把 rhs 整体当成默认值处理，产出
   title: Field(default=str, max_length=200) 这类非法声明。写了一个按规格逐条定位的
   反向脚本精确回滚，再修正拆分逻辑（按第一个 " = " 分隔注解与默认值）后重跑。

2. **回滚脚本过度删空行**：清理失效导入时把合法空行也压掉了，导致原本干净的文件
   出现净删除。已把受影响的 4 个文件 git checkout 还原到 HEAD 重做。

3. **容器 /tmp 被重建清空**：期间 start.sh 重部署重建了 backend 容器，临时脚本丢失，
   重新拷入后再生成规格。

4. **DB 枚举值大小写**：user.role 是 PostgreSQL enum，库里存的是 ADMIN/MEMBER
   （SQLAlchemy Enum 默认按 .name 存储），用 'admin' 比较会抛
   InvalidTextRepresentationError，改为 'ADMIN'::userrole 后正常。
