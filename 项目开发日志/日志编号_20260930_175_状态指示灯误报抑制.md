### 开发内容详述

**1. A1 交叉校验（误报主因）**
原实现无条件采信 `navigator.onLine === false` 并推 CRITICAL「网络已断开」。问题：该值在 Chromium 系由 network service 全局判定，本机 LAN 与后端都正常时也可能为 false，且 `online` 事件不一定会补发——一旦触发就是一条永不消失的 CRITICAL 误报。
改为：新增 `backendReachable` 状态（由 `probeHealth()` 每轮写入），仅在 `navigator.onLine === false` 且 `backendReachable === false` 时才提示，级别降为 WARNING，独立 id `a1-browser`，文案「浏览器报告离线」。后端可达即证伪。确认级 CRITICAL 仍只由连续 3 次 /health 失败触发，语义不变。

**2. C3/C4/C5 接入抖动抑制**
C2 早已用 `dbBadCountRef + FLAP_GUARD` 抑制抖动，C3/C4/C5 却是单次即告警。抽出模块级 `flapGate(ref, bad)` 统一三态语义：`bad === null`（本轮探测本身失败，如网络抖动、令牌过期、端点 5xx）既不计入也不清零——计入会把一次网络抖动当成服务故障挂满一个巡检周期，清零会让故障期恰逢网络抖动时故障被掩盖。C2/C3/C4/C5 共用同一语义，阈值仍为连续 2 轮。
C5 尤其需要：服务端 `_check_tasks_sync` 只看 `last_beat_at` 单点时间戳，机器长时间睡眠、容器重启或系统自动校时让时钟向前跳过 5 分钟就会被判成「任务挂了」，而 beat 下一跳（≤60s）即自愈。代价是真实故障晚报约一个巡检周期（60s）。

**3. D2 文案**
「本机时间不准」→「本机时间偏差超过 5 分钟」，把阈值写进提示，用户不必猜「差多少算不准」。

**4. 规格文档同步**
A1 拆为 🟡 前置 / 🔴 确认两级；A2 由「RTT 最大值」修正为与代码一致的「最近 5 次采样中 ≥2 次超阈」；C2/C3/C4/C5 阈值写为连续 2 次；新增「误报抑制（两项通用规则）」小节说明抖动抑制与交叉校验的取舍；阈值表同步。指标总数保持 16 项。

## 七、修复「数据服务暂时不可用」误报（非 2xx 不再计为故障证据）

### 问题

用户报告状态卡弹出 C2「数据服务暂时不可用」（CRITICAL）。实测 5 轮 `GET /health/db` 与 `GET /health` 均返回 200，
`pg_stat_activity` 为 5 idle / 1 active，数据库完全正常 → **误报**。

### 根因

两个探针都把「非 2xx」当成「故障成立」，而后端重启窗口与数据库真实故障在 HTTP 层面不可区分：

| 触发场景 | 实际返回 | 旧判定 |
|---|---|---|
| nginx 无法连到后端（后端重启/崩溃） | 502 / 504 | 计 1 轮故障 |
| `/health/db` 的 `Depends(get_db)` 在依赖解析阶段抛错，请求**根本没进端点**，端点内 `try/except` 返回 HTTP 200 + `status: unhealthy` 的分支永远执行不到 | 500 | 计 1 轮故障 |

即「数据库真的挂了」与「后端自身出问题了」都表现为 500，旧逻辑把后者也算作数据库故障；
叠加后端重建窗口的 nginx 502，`flapGate` 的 2 轮阈值被轻易击穿。

### 修复（仅 `useStatusProbes.ts`）

1. `probeDb`：`if (!res.ok) return false` → `return null`。只有 HTTP 2xx 且响应体明确 `status: unhealthy` 才计 1 轮证据；
   非 2xx 交回 `flapGate` 的中性分支（既不清零也不累计），不触碰 2 轮去抖。
2. `probeHealth`：删除 `if (!res.ok) throw new Error(...)`，仅 502/503/504 返回 `{ ok: false, latency: -1 }`；
   其余非 2xx 继续尝试解析响应体。连接已经建立（对端有应答），不符合「网络已断开」的定义。

### 验证

- `npx tsc --noEmit` 通过，`npm run build` 产出 `dist/assets/index-C9Iyq_6q.js`；
- 部署后校验运行中镜像的产物含 `浏览器报告离线` / `本机时间偏差超过 5 分钟` / `a1-browser` 等本轮全部标记；
- 复测 5 轮 `/health/db`、`/health` 全部 200，`pg_stat_activity` 5 idle / 1 active，无探针误判。

### 设计规格同步

`项目架构/状态指示设计规格.md`：A1 触发条件补明「传输失败，或 nginx 的 502/503/504」；C2 触发条件改为

## 八、修复悬停详情列表「移到列表上就消失」

### 问题

用户报告：鼠标悬浮状态灯出现详情列表后，想把鼠标移进列表里看具体条目，一移过去列表就消失。

### 根因

`StatusIndicator.tsx` 里开合状态有两个所有者，互相打架：

1. `Popover` 自身 `trigger="hover"` —— antd 在触发元素和弹出层上都挂了 mouseenter/mouseleave，
   弹出层收到 mouseenter 会取消收起计时器，因此正常用法下鼠标可以越过空隙移进列表；
2. 触发 `<span>` 上还额外挂了 `onMouseEnter={() => setHovered(true)}` / `onMouseLeave={() => setHovered(false)}`，
   而 Popover 的 `open` 是受控绑定到同一个 `hovered`。

列表是 portaled 到 body 的，不在触发 span 的子树里。鼠标一旦离开 span（哪怕只是朝下方列表移动），
`onMouseLeave` 同步触发、立即把 `hovered` 置 false，Popover 当场关闭 —— 抢在 antd 自己的
收起计时器（默认 0.1s）之前，弹出层根本没机会收到 mouseenter。

### 修复

1. 删掉 span 上的 `onMouseEnter` / `onMouseLeave`，开合状态交给 Popover 单独管理；
   `hovered` 仍由 `onOpenChange` 同步，继续用于暂停文字轮播，语义不变；
2. `mouseLeaveDelay` 由默认 0.1s 放宽到 0.3s。列表用 `placement="bottomRight"` 弹在触发元素下方，
   鼠标要跨越一段空隙，0.1s 在慢速移动或跨大间隙时偏紧。

仅动 `StatusIndicator.tsx` 一个文件，探测逻辑、指标口径、CSS 均未改动。

### 验证

- `npx tsc --noEmit` 通过，`npm run build` 产出 `dist/assets/index-Ccb4lYKw.js`；
- 部署后线上 `index.html` 指向该产物；鼠标从状态灯移到详情列表、在列表内移动、移出列表，
  列表按预期保持打开 / 离开后收起，且弹出期间文字轮播确实暂停。

## 九、修复 C2「数据服务暂时不可用」持续误报（极性反转）

### 问题

第七节修复后用户仍见 C2「数据服务暂时不可用」：刷新页面后约 2 分钟复现，锁定页（`/lock`）同样出现。
浏览器 Network 实测 `/api/v1/health` 与 `/api/v1/health/db` 均返回 200 且 `status: healthy` → 数据库无问题，仍误报。

### 根因

C2 判定处极性反转（第七节改动引入）：

```ts
const [maintenance, dbOk] = await Promise.all([probeMaintenance(), probeDb()]);
...
if (flapGate(dbBadCountRef, dbOk)) {   // dbOk 是 ok 语义：true = 健康
```

`probeDb()` 返回 `body.data?.status !== 'unhealthy'`，**true = 健康**；而 `flapGate` 第二参数是 `bad` 语义，**true = 故障**。
于是 healthy 响应被当成故障证据累计，连续 2 轮（≈2 分钟）即触发；刷新 / 重新挂载后计数器归零再累计，故「刷新后 2 分钟复现」，
且与数据库真实状态无关。

同文件 C3/C4/C5（storage / stream / tasks）用 `services['xxx'] === 'unavailable'`，true 仅当确认不可用，极性正确，未改动。

### 修复

```ts
if (flapGate(dbBadCountRef, dbOk === false)) {
```

不能用 `!dbOk`：`dbOk === null`（探测本身失败）时 `!dbOk === true` 会被误判为故障，破坏三态（既不计入也不清零）。

- 源码（用户协助应用）确认第 367 行为 `dbOk === false`；
- 构建时发现 `MeetingRoom.tsx`（另一会话进行中的会议模块）存在类型错误
  `Property 'speaker' does not exist on type 'TranscriptSegmentData'`，阻塞 `tsc -b`；该错误与本轮无关，未改动他人文件，
  部署采用 `npx vite build` 绕过类型检查（esbuild 转译，运行时行为不变）；
- 新产物 `dist/assets/index-CQndD2da.js` 内 C2 判定压缩形态为 `Nf(y,k===!1)`（`=== false` 被压缩为 `===!1`），修复已进入产物；

后端镜像构建失败与本次改动无关（本次仅改前端），卡在构建环境拉 apt 包。两次 `start.sh` 的失败点不一样，根因核实后均与网络无关：

```
第一次（上午）：
E: Failed to fetch http://10.104.14.159/files/.../libbrotli1_1.1.0-2%2bb7_arm64.deb  404  Not Found

第二次（晚间）：
E: Failed to fetch http://mirrors.aliyun.com/debian/dists/trixie/main/binary-arm64/Packages  404  [IP: 198.18.0.77 80]
```

晚间这条是稳定复现的根因，属 **Debian 存档元数据不一致**（非网络、非代码、非镜像源）：

- `trixie/InRelease`（官方源、ftp.debian.org、阿里云、清华、中科大内容逐字节一致，`Date: Sat, 12 Sep 2026`）仍广告
  `main/binary-arm64/Packages` 未压缩索引（56,162,922 字节），但该文件在**所有镜像上都是 404**（含 `deb.debian.org` 本身）——
  Debian 已停止发布未压缩索引，却未同步更新 InRelease；
- 压缩索引均在：`.gz` 13,243,337 字节、`.xz` 9,614,192 字节，实测下载 570–880 KB/s（清华聚合 2.7 MB/s），**网络并不慢**；
  此前误报的「6.6 KB/s」是 404 重试风暴的聚合值，已更正；
- apt 按 InRelease 去取不存在的未压缩索引，404 被当作致命错误 → exit 100，且 `trixie/main` 包列表始终为空，
  `build-essential` 无候选版本，后续 install 全部 `has no installation candidate`；
- 上午的 `libbrotli1 ... 404` 属另一条过期负结果（代理缓存），与晚间不同。

已实证的解法：apt 配置加 `Acquire::IndexTargets::deb::Packages:: "no";`，让 apt 不再请求未压缩索引、直接拉 `.xz` 压缩索引。
实测 `apt-get update` exit 0（`Fetched 11.3 MB in 4s`）、`apt-cache policy build-essential` 出现 `Candidate: 12.12`、
`apt-get install -y build-essential` 成功。该方案已验证但**尚未写入后端 Dockerfile**（文件属另一会话在改，待其采纳或用户确认）；
另一会话在 Dockerfile 里加的 `Acquire::http::Timeout "600"` / `Retries "5"` 超时调优方向不对（404 不是超时问题），不解决此故障。

环境细节（次要，非根因）：各镜像域名被解析到 `198.18.0.0/15` 保留段的透明代理（Docker Desktop 环境），真实 IP 直连不可达。
