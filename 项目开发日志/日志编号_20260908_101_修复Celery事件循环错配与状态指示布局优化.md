**布局改造（关键）**

原实现把指示器作为 header 的 flex 子元素插入模块标题与按钮组之间，指示器出现时
占用宽度 → 模块标题（`flex: 1; textAlign: center`）的可用宽度变窄 → 标题整体左移；
指示器消失（无异常）时又恢复，标题来回抖动。

改为「零宽占位 + 绝对定位」两层结构：

    [收起按钮] [模块标题 flex:1] [.anchor width:0] [右侧按钮组]
                                  └─ .inline position:absolute; right:16px

- `anchor`：`position: relative; width: 0; flex-shrink: 0` —— 在 flex 流中占位宽度为
  0，因此指示器出现（0 宽）与消失（不渲染）时模块标题的可用宽度**完全一致**，标题不再移动
- `inline`：`position: absolute; right: 16px; top: 50%; transform: translateY(-50%)`
  —— 叠在按钮组左侧的标题空白区上，不占布局空间
- 标题文案最长 5 个汉字（「设备终端」等），指示器最长 240px，两者不会碰撞
- 文案 `white-space: nowrap; overflow: hidden; text-overflow: ellipsis`，超长省略号
- 登录页 / 锁定页的 `floating` 变体不受影响（`position: fixed` 右下角）

同时重构了组件 DOM：把悬停处理合并到指示器本体上，去掉原来多余的一层触发元素，
使 Popover 的触发元素就是绝对定位的那一层（否则触发元素零尺寸会导致悬停区域失效）。

### 遇到的问题与解决
- **问题：Celery prefork 池 + asyncio.run() 跨事件循环复用连接池**
  - 现象：worker 日志反复报
    `RuntimeError("Task ... got Future ... attached to a different loop")`
    与 `RuntimeError('Event loop is closed')`，约一半定时任务静默失败。
  - 根因：`app/core/database.py` 的 `_engine` 是模块级单例，连接池跨进程常驻。
    prefork 池下每次 `asyncio.run()` 都新建事件循环，asyncpg 连接绑定创建它的那个
    循环；第二次运行时池内残留连接仍指向上一轮已关闭的循环，`greenlet_spawn` 抛错。
    两个 fork worker 交替执行，故表现为「每个 worker 首次成功、第二次失败」。
  - 解决：新增 `isolated_session()`，每次调用独立引擎并在 `finally` 中
    `await engine.dispose()`，天然只绑定当前事件循环。
  - **为何不选其他方案**：
    1. 让 `_engine` 按事件循环为键缓存 —— 会导致旧循环的引擎泄漏未关闭的 TCP 连接，
       10s 周期任务下每小时可泄漏数百个 PostgreSQL 连接，风险高于收益，故否决。
    2. 改 Celery pool 为 `solo` —— 丧失并发，且 `gevent` + asyncpg 需 monkey-patching，
       改动面过大，故否决。
    3. 在每个任务末尾 `await engine.dispose()` —— 需逐个任务记得调用，易遗漏，
       故改为上下文管理器强制释放。
- **问题：Popover 触发元素零尺寸**
  - 绝对定位层若套在零宽容器外，悬停区域会失效。把 className 与 mouse handler 直接
    放到指示器本体上，使其同时充当定位层与 Popover 触发层。
