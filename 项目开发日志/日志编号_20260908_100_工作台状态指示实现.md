### 开发内容详述

**后端（4 项）**

1. `GET /api/v1/health` 的 `data` 新增 `server_time`（ISO8601，Asia/Shanghai，秒精度）。
   原先仅返回 `status` 与 `version`，前端时间偏差探测（D2）需要服务端时间基准。
2. 新增 `GET /api/v1/system/status`（需登录），返回服务级状态：
   `services{database,storage,stream,tasks}` + `server_time`，取值 `ok` / `unavailable`。
   四项判定：
   - database：`SELECT 1`（复用 `/health/db` 逻辑）
   - storage：对 `FILE_STORAGE_PATH` 执行 `makedirs` + `statvfs` + 写入探针，
     走 `asyncio.to_thread` 避免 NAS 卡顿阻塞事件循环
   - stream：MediaMTX `GET /v3/paths/list`（端口 9997，与 nginx `/live/` 的 8889 不同）
   - tasks：读取 system_config 的心跳时间戳，超过 5 分钟视为不可用
3. 新增 Celery 心跳任务 `app.tasks.heartbeat.beat_heartbeat`，每 60s 写入
   `system_config.task_heartbeat`。前端不直接探测 Celery broker，通过心跳新鲜度间接判定，
   避免向浏览器暴露 broker 细节。
4. 新增 `app/utils/timeutil.py`：`TZ_SHANGHAI` / `now_shanghai()` / `now_shanghai_iso()`，
   统一时区偏移量的唯一来源，避免各模块重复硬编码。

### 关键决策与原因
- **B1 与 B2 互斥，B2 优先**：HTTP 访问非 localhost 时 `isSecureContext` 必为 false，
  两者必然同时成立。B2 文案已涵盖功能不可用（比单纯「未启用 HTTPS」更具行动指引），
  B1 仅作为极老浏览器不实现 `isSecureContext` 时的兜底。
- **/system/status 需登录**：存储/流媒体/提醒健康状态暴露给匿名访客无意义，
  反而成为攻击者探测入口。
- **maintenance_mode 只走 site-config，不在 /system/status 重复返回**：单一来源；
  site-config 公开可读，登录页也需读取。
- **心跳用独立引擎**：见「遇到的问题与解决」第 1 条，这是本项目 Celery + asyncpg
  的一个通用坑，独立引擎是免副作用的解法。
- **前端 package.json version 对齐为 2.0.0**：原先为 0.1.0 且与后端 `__version__`
  不同步，若保留则 D1 版本比对会恒为「不匹配」，每次刷新都显示红灯。

### 遇到的问题与解决
- **问题 1：Celery prefork 池下 asyncio.run() 报 "Task got Future attached to a different loop"**
  - 现象：心跳任务首次部署后 `tasks` 恒为 `unavailable`，DB 无 `task_heartbeat` 行。
    worker 日志报 `RuntimeError("Task ... got Future ... attached to a different loop")`。
  - 根因：`app/core/database.py` 的 `_engine` 是模块级单例，连接池跨进程常驻。
    Celery prefork 池下每次 `asyncio.run()` 都新建事件循环，第二次运行时池内残留的
    asyncpg 连接仍绑定上一轮已关闭的循环，greenlet_spawn 抛错。
  - 解决：心跳任务改用本任务内 `create_async_engine` 独立创建的引擎，
    `finally` 中 `await engine.dispose()`，天然只绑定当前循环。已验证修复
    （任务 succeeded in 0.047s，DB 写入成功，`services.tasks` 返回 `ok`）。
  - **遗留问题（未修，超出本次范围，需单独确认）**：同一根因影响既有任务且非本次引入——
    近 10 分钟 worker 日志统计：`check_due_reminders` 成功 8 次 / 失败 6 次，
    `check_calendar_reminders` 成功 8 次 / 失败 6 次，`sync_room_active_status`
    失败 2 次 / 成功 0 次。规律是「同一 fork worker 首次执行成功、第二次失败」，
    两个 worker 交替执行导致约一半定时任务静默失败。影响面：
    10s 周期的提醒可能漏发或延迟一轮；`stream_room.is_active` 未同步会影响直播间状态。
    建议在 `app/core/database.py` 层统一解决（例如任务侧统一使用独立引擎，
    或为任务注册专用 session 工厂），而非逐个任务打补丁。
- **问题 2：MediaMTX 端口与 nginx 配置不一致**
  - 规格文档原写 8889（沿用 nginx `/live/` 的 proxy_pass 端口），实际 MediaMTX API
    在 9997（见 `app/services/mediamtx.py` 的 `MEDIAMTX_API`）。
  - 解决：实现直接复用 `mediamtx.ping()`，沿用服务层既有常量，未硬编码端口。
