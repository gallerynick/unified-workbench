### 开发内容详述

**1. 摸底：确认发行链路现状**

先实测而非假设，得出三个关键事实：

- `version.py` 为 `2.0.0`，`.unified-workbench` 的 `min_version` 为 `2.0.0`，两处已同步
- 但 `git tag` 共 18 个，符合版本格式的只有 `v0.1.0 / v1.0.0 / v1.0.1`——**v2.0.0 从未打 tag**，在更新器眼里尚不存在
- `updater.py` 只有 `check_update`（通过 `git ls-remote --tags` 比较版本），**没有执行更新的函数**；基定文档第 3.2 节写的「执行 git pull + docker compose up」是设计意图而非现状

因此确定走「手动发行」：用户 `git clone` + `./start.sh`，更新手动 `git pull && ./start.sh`。

**2. README 前置条件补齐**

原文只写「Docker Desktop 已安装并运行」，但 `frontend/Dockerfile` 直接 `COPY dist`（容器内不跑 npm），`start.sh` 必须在宿主机执行 `npm install && npm run build`。原 README 会让新用户**必然卡在前端构建一步**。

改为表格化前置条件：Docker Desktop、Node.js LTS 18+（标注为必需并说明原因）、npm、磁盘 ≥25GB、内存 ≥8GB，并补充 Docker Desktop 需在 Settings→Resources 调高内存的提示（后端镜像含 PyTorch，默认内存会被 OOM 杀掉）。

**3. README 补首次启动下载量预期**

实测数字：外部镜像 8.7GB + 构建依赖 2.5GB + npm 包 355MB ≈ 11.5GB，首次使用会议转写 / AI 功能时另下载模型约 5GB（modelscope ASR 3.0GB + ollama qwen2.5:3b 1.9GB），最终磁盘占用约 16GB。写成醒目提示，避免用户以为卡死。

**4. README 停止命令改为 `./stop.sh`**

原文写的是 `docker compose -p unified-workbench down`，与仓库自身约定（启动/重启一律走 start.sh）不一致，且会让用户绕过 `stop.sh` 中停止 Mediamtx 独立容器的逻辑。改为 `./stop.sh`（Windows `stop.bat`），并注明保留数据卷。

**5. README 项目结构补 scripts/ 三项**

补入 `prune-cache.sh`、`prune-cache.bat`（日志 176 新增）、`claim_log_number.sh`，目录注释由「共享脚本（docker 自动探测）」改为「共享脚本」。

### 遇到的问题与解决

- 问题：`updater.py` 中找不到 `perform_update` / `run_update`，与基定文档 3.2 节不符。
- 解决方案：全局 `grep` 确认后端只有 `ls-remote`，无 `git pull` 执行路径；进一步查 compose，backend 服务仅挂载 `data/files`、`data/backups`、`modelscope_cache`，**未挂载源码仓库**，容器内无 `.git`，`git pull` 结构上无法执行。结论写入 CHANGELOG 作为已知差距。

- 问题：模板字符串中 `\d` 被当作转义序列吞掉，CHANGELOG 里的正则渲染成 `^d+\.d+\.d+$`。
- 解决方案：改用双引号字符串 + `\\d` 修正，复核后为 `^\d+\.\d+\.\d+$`。
