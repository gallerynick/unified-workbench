### 开发内容详述

**1. 为什么不合并目录（三个硬约束，写在 service 模块 docstring 里）**

- Ollama 的存储是 blobs / manifests 内容寻址布局，本身不按模型分目录。即使把文件搬到一起，目录遍历依然读不出「哪个模型多少字节」，只能走 HTTP API。
- 后端容器读不到 Ollama 卷（/root/.ollama 权限拒绝，已实测确认）。
- 两个命名卷共享同一块 Docker 虚拟机磁盘，合并后磁盘口径不变。

因此统一化在应用层做，字节一个不动。

**2. 用途类型是元数据，不是目录位置**

ModelScope 缓存目录名就是仓库 ID（/ 替换为 --），这本身是稳定的键。当前 ASR 配置的四个槽位（model / punc_model / spk_model / vad）能算出四个目标目录名，用目录名做连接即可判定「这个模型是干什么的、是否在用」——不需要任何分类目录。

槽位连接失败时才按仓库 ID 关键词兜底推断类型（paraformer / sensevoice / ct-transformer / campplus / fsmn-vad），避免已知模型被标成「未分类」。

**3. 孤儿缓存检测是本清单的核心价值**

配置 4 个槽位、盘上 5 个模型——多出来的 iic/SenseVoiceSmall（940 MB）既不在任何槽位里，也不会被自动清理。本清单把它标为 orphan 并附「清理前请确认」提示。这是原先两个各自为政的卡片都看不到的信息。

**4. 按引擎分组，不合并总数**

两个引擎的管理动作不同（Ollama 走 API、ModelScope 走缓存目录），合并成一个总量没有意义。响应体里 engines[] 各自给出 count 与 bytes，total_bytes 只是各引擎之和，前端分两个 chip 展示。

**5. 职责边界：本清单只读**

下载 / 删除动作仍由第三方配置页持有，避免两处各自实现一份。本清单是同一批数据的另一种展示，口径不会分裂。前端提示语写明「下载与删除请到第三方配置操作」。

**6. 访问与持久化约定**

- 仅管理员（require_admin）：清单含绝对路径、仓库 ID、配置槽位等运维信息，普通成员无查看必要。
- 无持久化：与 api/storage.py、api/monitor.py 边界一致，只返回实时采样。
- 路由无尾斜杠，与 /system/monitor、/system/storage-breakdown 一致。

**7. 阻塞 IO 必须出事件循环**

目录遍历丢进 asyncio.to_thread；Ollama API 走 httpx.AsyncClient 并设 10 秒超时。单引擎失败只影响该引擎，通过 notes[] 返回说明，不影响另一个引擎的展示。

**8. 补一个公开的目录名映射入口**

清单需要按「配置里填的模型名」定位缓存目录。原先只能调用 asr_engine 的私有 _repo_id_for / _model_cache_dir。新增公开函数 cached_model_dir_name(name)，避免跨模块调用私有实现。

**9. 前端**

新增 ModelInventorySection，与既有 BreakdownSection 同款写法：独立组件承载 hook、与外层「权限不足 / 加载中」的早退路径隔离，避免 hooks 顺序违规。表格按用途类型排序（语音链路 → 生成类 → 未分类），状态用 antd PresetColor 的 Tag 表达。样式全部走 design token，无硬编码 hex，无 Emoji 图标。

### 遇到的问题与解决

- 问题：后端镜像无法重建，./start.sh 在 docker compose up -d --build 失败。
- 原因：apt 取包经过网络层的 HTTP 缓存网关（10.104.14.x、198.18.0.22），网关缓存过期缺文件，返回 404。三次重试缺的文件各不相同：先是 libbrotli1 / libp11-kit0，随后是 mirrors.aliyun.com/debian/dists/trixie/main/binary-arm64/Packages。单次构建耗时约 429 秒。
- 与本次改动无关：该 apt 步骤位于 Dockerfile，backend / celery / celery-beat 三个镜像都会命中；本次未修改任何 Dockerfile。
- 已排除的假设：并非构建缓存被清（docker buildx du 显示 5.267GB 缓存仍在）；也非代理变量注入（host 与容器内均无 http_proxy）。
- 根因定位（从运行中的后端容器内直连探测各 apt 源，结果决定性）：
  - mirrors.aliyun.com/debian/dists/trixie/main/binary-arm64/Packages → HTTP 404（0.2s）
  - mirrors.aliyun.com/debian/pool/main/b/brotli/libbrotli1_1.1.0-2+b7_arm64.deb → HTTP 404（0.1s）
  - deb.debian.org/debian/dists/trixie/main/binary-arm64/Packages → HTTP 404（0.5s）
  - apt.postgresql.org/dists/trixie-pgdg/InRelease 与 Packages → HTTP 200

  404 在 0.1~0.5 秒内返回，不是真实镜像的响应耗时，而是网络层的本地缓存网关对未命中内容直接回 404。网关缺少 Debian 13（trixie）内容，而 python:3.11-slim 正是 trixie。apt.postgresql.org 可用，说明只有 Debian 自家仓库受影响。

  网关缓存是逐步填充的：第 1 次卡在 debian 包文件，第 4 次已推进到 pgdg 安装步骤。但第 5 次（单独 build backend）跑了 23 分钟仍未完成，buildx 进程中途被重启过一次。

- 应对：改为定向验证。把新增模块拷入运行中的后端容器，直接调用 build_model_inventory() 走真实链路，端到端结果符合预期（见测试情况）。网络恢复后运行 ./start.sh 即可完成镜像重建与上线。
- 副作用：拷入容器的模块在容器重建后自动消失，不会污染镜像。

- 问题：初版误判 storage.py 注释「与 api/monitor.py、api/status.py 共用同款解析器」有误。
- 结论：经 grep 核实，monitor.py 第 28 行与 status.py 第 45 行确实都是 _bearer = HTTPBearer(auto_error=False)，原注释属实，无需修改。

- 问题：status 字段用三元表达式赋值，mypy 推断为 str，与 Literal 类型不兼容。
- 解决：在 if / else 之前用 status: ModelStatus 声明一次；两处分别标注会触发 no-redef。

- 问题：setInventory(await getModelInventory()) 类型不匹配（TS2345），即 176 号日志遗留的阻断项。
- 解决：request 返回 UnifiedResponse<T>，需取 .data，已对齐既有 BreakdownSection 的写法；同时补上错误态 Alert，避免加载失败时误显示「未找到已下载的模型」。
