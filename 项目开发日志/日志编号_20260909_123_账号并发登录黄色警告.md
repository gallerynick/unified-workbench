### 开发内容详述

**一、F1 判定语义**

「账号在其他设备登录」= 当前用户在过去 30 分钟内，存在非本会话的其他会话，且这些会话涉及**不同 IP** 或**不同设备**至少一项。

三个计数字段由后端算好，前端只做阈值比较：

| 字段 | 含义 |
|---|---|
| other_session_count | 其他会话总数 |
| other_ip_count | 其他会话涉及的不同 IP 数（已剔除当前会话 IP） |
| other_device_count | 其他会话涉及的不同 device_token 数（已剔除当前会话设备） |

判定：`other_ip_count >= 1 ∥ other_device_count >= 1` → warning。

关键性质：

- **同设备多标签页不告警**。新会话与当前会话同 IP、同 device_token，两个去重集合都被剔除，计数为 0。
- **不做抖动抑制**。A2 / C2 用「连续 2 次」抑制服务抖动，但 F1 是安全语义——新登录出现即应提示，延迟反而漏掉攻击窗口。
- **30 分钟窗口**。超过窗口的未撤销会话通常是早先登出、尚未清理的陈旧记录（会话表只有手动撤销，无自动 TTL），不作提示。

**二、后端：/system/status 增加 concurrent 字段**

复用既有的用户级端点。前端本来每 60 秒就在轮询它，不用多一次请求。

- `_current_session()`：按 JWT 的 jti 反查当前会话记录，用于把「自己」排除。token 缺失或 jti 查不到时返回 None，统计退化为「全部未撤销会话」——宁可提示也不漏提示。
- `_count_concurrent()`：按 user_id + 未撤销 + 30 分钟窗口取会话集合，剔除当前会话后按 IP、device_token 分别去重计数。
- 新增 `CONCURRENT_RECENT_MINUTES = 30`，与前端注释双向对齐。

**三、会话 IP 记录修复**

排查 F1 时发现：`user_session.ip_address` 全部是 `172.18.0.9`（nginx 容器 IP）。原因是 uvicorn 未启用 `--proxy-headers`，`request.client.host` 恒为容器网桥 IP。

改法沿用 `api/forms.py` 既有的 `_client_ip()` 模式——读 nginx 写入的 `X-Real-IP`（由 `$remote_addr` 生成，经 nginx 的客户端无法伪造），直连 uvicorn 时退回 `request.client.host`。在 `api/auth.py` 补同名助手，两个登录端点（login、verify-2fa）改用之。

未采用 `--proxy-headers` 的理由：那是全局行为变更（所有端点的 client.host 都会变成真实 IP），且 uvicorn 的 `--forwarded-allow-ips` 默认只信任 127.0.0.1，而 nginx 在桥网段上，需要额外配置。X-Real-IP 方案与项目既有代码一致，零部署变更。

`api/webauthn.py` 还有两处直接取 client.host，本次未动（不在需求范围内）。

**四、前端探测**

`probeServices()` 改名 `probeStatus()`，返回值由 `services` 单字段扩展为 `{ services, concurrent }`——同一个响应体，C3 / C4 / C5 与 F1 共用一次请求。新增常量 `CONCURRENT_MIN = 1`。

### 遇到的问题与解决
- **问题：部署了旧 bundle（第一次）**
  - `start.sh` 只跑 `docker compose up -d --build`，而前端 Dockerfile 是 `COPY dist /usr/share/nginx/html`——拷的是宿主机 dist，容器内不跑构建。
  - 现象：部署成功、容器 Healthy，但线上 bundle 仍是改动前的哈希。
  - 解决：先 `npx vite build` 再 `start.sh`。第二次部署前已补上。
- **问题：curl -L 把 POST 转成 GET，body 丢失**
  - nginx 的 80→443 是 301，curl 按 HTTP 规范对 301 的 POST 降级为 GET，后端报 `body: Field required`。
  - 解决：加 `--post301 --post302 --post303`。
- **问题：验证数据脏，误判代码有 bug**
  - 多次测试残留未撤销会话，导致「首次登录」就看到 `other_session_count=1`，一度怀疑 jti 反查失败、自己没被排除。
  - 直接查库定位到残留会话后确认：逻辑正确，同 IP 与同 device_token 都被正确剔除。
- **问题：本部署下 IP 维度仍无法区分真实客户端**
  - 改用 X-Real-IP 后，新会话 IP 变为 `172.18.0.1`——Docker Desktop 端口映射层呈现的地址，所有客户端看起来一样。
  - 这是平台限制，不是代码问题：macOS Docker Desktop 通过 VM 内的端口代理转发，$remote_addr 不保留真实客户端。
  - 已验证机制本身正确：直连 8000 端口伪造 `X-Real-IP: 10.9.9.9` 后，other_ip_count 立即变 1，F1 触发。
  - 结论：device_token 维度是本部署下可靠的主信号（浏览器级 UUID，跨设备必然不同）；IP 维度在 nginx 直连、Linux host 网络等部署下才有效。本部署中它退化为「无 IP 信号」，不会产生误报，只是漏检。
