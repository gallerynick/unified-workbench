### 开发内容详述

#### 后端

新增 `GET /system/storage-breakdown`（无尾部斜杠），`require_admin` 门禁，
复用 `/system/monitor` 的 Bearer 解析约定，仅登录用户可访问、非管理员 403。

采集逻辑集中在 `app/services/storage_breakdown.py`，六类并行采集后汇总：

| 分类 | 数据源 | 精度 |
|---|---|---|
| 本地模型 / Ollama 模型 | `GET http://ollama:11434/api/tags`，累加各模型 size，附单模型明细 | exact |
| 本地模型 / ModelScope 缓存 | 遍历 `MODELSCOPE_CACHE_PATH` 目录，`models/` 下每个子目录按模型给明细 | exact |
| 用户数据 / 数据库 | `pg_database_size` 当前库 | logical |
| 用户数据 / 缓存 (Redis) | `INFO memory` 的 `used_memory` | logical |
| 文件共享 / 共享文件 | 遍历 `FILE_STORAGE_PATH` | exact |
| 备份 / 备份文件 | 遍历 `FILE_BACKUPS_PATH` | exact |
| 其他 / 应用文件与临时文件 | 残差计算 | residual |

关键口径决策：

1. **精度分级而非混算**。逻辑量（数据库、Redis）代表的是数据体积，不等于磁盘占用
   （不含 WAL、索引膨胀、AOF 物理文件），因此单列为 `logical_reference_bytes`，
   不计入 `measured_total_bytes`，避免与 exact 项相加造成口径污染。前端环图按
   `counted` 取扇形，故汇总前把逻辑项统一置 `counted=False` —— 由此 `counted`
   成为「是否计入合计」的唯一判定，扇形之和、中心合计、占比分母三者天然一致。
2. **残差锚在 Docker 虚拟机卷**。容器内读不到镜像与构建缓存，但能读到自身所在
   卷（`/`）的 `statvfs`。以「该卷已用 − 已归入本功能的已归类占用」为残差，
   得到「其他」的近似值，并在 `anchor` 字段里写明计算式，让用户能自己核对。
3. **两个卷互不交叉**。工作盘（`/data/files` 所在卷）只放文件共享与备份，
   Docker 虚拟机卷只承载镜像/数据卷/容器层。二者分别展示 total/used/free，
   不做合并求和——合并会把宿主机磁盘与虚拟机磁盘混为一谈。
4. **失败降级而非整体失败**。每个采集器各自 `try/except`，单点故障时该分类
   `reachable=false`、`counted=false`，其余分类照常返回，接口不整体 500。
5. **阻塞 IO 全部入线程池**。目录遍历（数万文件量级）经 `asyncio.to_thread`
   执行，避免卡住事件循环。

新增两个配置项 `FILE_BACKUPS_PATH`、`MODELSCOPE_CACHE_PATH`，均在 `config.py`
给出容器内默认值，可由环境变量覆盖。

### 遇到的问题与解决
- 问题：recharts 的 `fill` 是 SVG presentation attribute，不接受 `var(--*)`，
  深色模式下会显示为黑色。
- 解决方案：沿用项目既有的 `resolveCssVar` 做法，把 token 值解析成具体色值再传入。
- 问题：TS 报「React Hook useMemo is called conditionally」。
- 解决方案：把带 hook 的分布区块抽成独立子组件 `BreakdownSection`，与外层
  早退分支解耦。
- 问题：`exactOptionalPropertyTypes` 下 CSS module 的 `string | undefined`
  不能直接赋给 `className: string`。
- 解决方案：统一补 `?? ''`，与项目既有写法一致。
- 问题：写测试时误用 `docker cp` 覆盖容器内文件，文件属主变为 root 导致
  后端 42 次重启。
- 解决方案：重建容器（`./start.sh` 全量重建）恢复正确属主，并确认源文件权限
  归一为 644 后再构建。
- 问题（自查发现）：初版把逻辑项标为 `counted=True`，而 `measured_total_bytes`
  按定义排除逻辑项；前端环图按 `counted` 取扇形，于是扇形角度之和（含数据库、
  Redis）大于中心显示的合计，占比分母与扇形不一致，数据库越大累计占比越会
  超过 100%。
- 解决方案：汇总处统一把逻辑项置 `counted=False`，并把 `counted` 确立为「是否
  计入合计」的唯一判定；前端图例区分「未计入」（不可达）与「参考」（可达但仅作
  参考），表格占比列同步。修复后 `sum(counted) == measured_total_bytes` 精确成立，
  环图扇形之和 / 合计 = 1.000000。
- 遗留问题 / 待办：无。备份目录本机为空，「备份」分类实测为 0 字节，
  待真实备份产生后无需改代码即可正常统计。

### 测试情况
- 测试方式：
  1. 容器内直调 `build_storage_breakdown`，核对六类返回值与口径
  2. 自签 admin 令牌（无 jti，走 user_id 回退分支）经 nginx 与直连 8000 端口
     各打一次 `GET /system/storage-breakdown`
  3. 人工验算残差与合计
  4. `ruff check`、`mypy`、`tsc -b`、`eslint`、`npm run build`
  5. 复核「环图扇形之和 == 中心合计」不变量（本次修复回归）
- 测试结果：通过

    其余计入合计
  - 残差验算：虚拟机卷已用 49,184,940,032 − 已归类 5,088,690,288
    = 44,096,249,744，与接口返回一致
  - 合计验算：1,929,912,432 + 3,158,777,856 + 592,613,376 + 0
    + 44,155,408,272 = 49,836,711,936，与 `measured_total_bytes` 一致
  - 不变量验算：`sum(counted) == measured_total_bytes` 为 True；环图扇形
    （4 项）之和 / 合计 = 1.000000
  - 逻辑量参考：9,805,159 + 8,226,288 = 18,031,447，与
    `logical_reference_bytes` 一致
  - 模型明细：Ollama 1 项（qwen2.5:3b 1840.5 MB）；ModelScope 5 项
    （paraformer 952.7 / SenseVoice 896.5 / punc 1131.8 / campplus 27.6 /

    已计入统计且可定位到具体模型
  - 单次耗时约 34 ms
  - 未带令牌 401；OpenAPI 已注册该路径，`security: HTTPBearer`，
    `Accuracy` 枚举为 `exact / logical / residual`
  - ruff / mypy / tsc / eslint 全部零错误，生产构建成功
