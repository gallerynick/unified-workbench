# 《一站式工作台》开发基准文档 v2.0（最终版）

------

## 1. 项目概述

| 项目         | 内容                                                         |
| ------------ | ------------------------------------------------------------ |
| **名称**     | 一站式工作台 (Unified Workbench)                               |
| **定位**     | 面向 20 人小团队的内网一体化协作与信息管理平台               |
| **核心模块** | 平台包含多个业务模块，具体模块详情见 `项目架构/` 目录下的架构设计文档 |
| **用户规模** | 20 人，年增量 < 10万条记录 / < 500GB 文件                    |
| **访问方式** | 内网为主，支持内网穿透；仅 PC 网页端（预留移动端扩展）       |

**设计理念：**

- **一站式**：团队所有信息集中管理
- **默认私有，自主公开**：用户掌控自己内容的可见性
- **模板驱动**：通过模板辅助结构化数据录入，灵活自定义（非核心模块，跨模块书写规范工具）
- **轻量可控**：简易部署、安全可审计、所有数据位置可指定

## 2. 技术架构基准

### 2.1 技术栈（最终确定）

| 层级         | 技术                                                  |
| ------------ | ----------------------------------------------------- |
| 后端         | Python 3.11+ / FastAPI / SQLAlchemy 2.0 / Alembic     |
| 前端         | React 18 / TypeScript 5 / Ant Design 5                |
| 富文本编辑器 | Tiptap（仅启用：字号、颜色、加粗、下划线、斜体）      |
| 数据库       | PostgreSQL 15+                                        |
| 缓存/队列    | Redis 7                                               |
| 异步任务     | Celery（提醒推送、定时备份、文件导出）                |
| 实时推送     | WebSocket（站内弹窗）                                 |
| 部署         | Windows + Docker Desktop + Docker Compose             |
| 反向代理     | Nginx                                                 |
| 文档导出     | python-docx(Word) / WeasyPrint(PDF) / openpyxl(Excel) |

### 2.2 部署与存储架构

```text
[浏览器] ──HTTPS──> [Nginx] ──> [React 前端]
                       │
                       └─/api──> [FastAPI] ←──> [Redis]
                                    │              │
                                    │         [Celery Worker]
                                    ▼
                              [PostgreSQL]
─────────────────────────────────────────────────────
存储分工（路径在 docker-compose.yml 集中配置）：
  本地SSD（如 D:/Workbench/db_data）
    └─ PostgreSQL 实时数据库文件
  NAS（你指定目录）
    ├─ files/    ← 所有文件、图片（实时）
    └─ backups/  ← 数据库定时备份（频率可调）
```

**部署方式：** 安装 Docker Desktop → 配置 `.env` 路径 → 运行 `start.bat` 一键启动全部服务。

## 3. 功能模块基准

### 3.1 用户与权限模块

**用户管理：**

- 管理员创建账号，无开放注册
- 字段：用户名、密码(bcrypt)、昵称、头像、身份标签、状态(启用/禁用)
- 密码策略：≥8位，含字母+数字
- 认证：账号密码 + JWT；预留 2FA 接口（一期不实现）

**权限模型（管理员 / 普通成员 + 身份标签）：**

| 能力                                          | 管理员 | 普通成员          |
| --------------------------------------------- | ------ | ----------------- |
| 修改团队成员信息（增删用户、改他人资料/标签） | ✅      | ❌                 |
| 系统配置（推送渠道、备份设置）                | ✅      | ❌                 |
| 查看全部审计日志                              | ✅      | ❌（仅看自己相关） |
| 创建/管理自己的内容、文件、项目、记录         | ✅      | ✅                 |
| 访问公开内容                                  | ✅      | ✅                 |
| 创建/编辑模板                                 | ✅      | ✅                 |

**身份标签：** 自定义标签（如"研发""设计"），用于内容可见范围控制。

**内容可见性三态：**

- `私有`：仅创建者可见
- `公开`：所有登录用户可见
- `指定`：指定用户 / 指定身份标签可见

**强制规则：**

- 密钥/数据记录分区 → 强制私有
- 系统可配置某些分区强制公开（如公告区）

------

### 3.2 通用设计模式

所有业务模块遵循以下统一的设计约定，具体模块的详细设计见 `项目架构/` 目录下的对应文档。

**可见性控制：** 所有内容类资源均支持三态可见性（`public` / `private` / `restricted`），默认私有。密钥/数据记录分区强制私有，系统可配置某些分区强制公开（如公告区）。

**数据存储：** 结构化数据使用 PostgreSQL JSONB 存储动态字段，模板定义与填写数据分离。资源主键统一使用 UUID。

**权限隔离：** 普通模块采用 owner_id 行级隔离（仅创建者和管理员可操作），协作模块通过 member_ids / maintainer_ids 机制授权。

**导出能力：** 支持按需导出为 Word / PDF / Excel 格式。

**模块索引：** 各模块的详细设计（功能定义、表结构、API 路由、安全约束）见 `项目架构/` 目录。

## 4. 安全基准

| 项目     | 标准                                                         |
| -------- | ------------------------------------------------------------ |
| 传输     | 全站 HTTPS（内网自签 / 穿透层 TLS）                          |
| 密码     | bcrypt 哈希                                                  |
| 密钥分区 | AES-256-GCM 加密（方案A：主密钥服务器持有，配置文件妥善保管） |
| 查看密钥 | 二次输入登录密码验证                                         |
| 会话     | JWT + 刷新机制 + 闲置超时登出                                |
| 防护     | 登录失败限制、ORM 防注入、前端转义防 XSS                     |
| 文件     | 类型校验、重命名存储、禁止可执行解析                         |

### 权限模型

采用三态 Visibility 枚举控制资源可见性：

| 可见性 | 含义 |
|--------|------|
| `public` | 所有成员可见 |
| `private` | 仅所有者可见（默认值） |
| `restricted` | 仅指定用户和标签可见 |

管理员拥有全权（查看/编辑/删除所有数据），可修改可见性。
14 个模块采用纯私有模式（owner_id 隔离），5 个模块支持完整 Visibility 三态。
详细规则见 `项目架构/` 目录下的权限模型设计文档。

### 通知推送架构

通知系统采用渠道注册表模式：5 个渠道（websocket站内/feishu飞书/email邮件/wecom企业微信），
dispatcher 按用户个人通知配置分发。WebSocket 实时推送，Celery 定时扫描提醒事件。
详细设计见 `项目架构/` 目录下的通知推送架构文档。

### 数据导入导出

支持全量数据导出为加密 ZIP：28 张表分页 JSON + 文件打包，PBKDF2 二层加密。
导入支持版本迁移链、紧急备份与失败回退。详细设计见 `项目架构/` 目录下的数据导入导出设计文档。

### 架构文档索引

`项目架构/` 目录存放系统架构设计文档，涵盖安全设计、权限模型、通知推送、数据导入导出、数据库设计、前端架构、容器化部署、请求链路、任务队列、迁移策略、系统初始化、配置管理等核心架构决策。开发前按需查阅对应文档，新增或删除文档时无需同步修改其他文档的引用。

## 5. 开发规范基准

**代码规范：**

- 后端：PEP8 + `ruff` + `black` + `mypy`
- 前端：ESLint + Prettier + 严格 TypeScript
- 所有 API 用 Pydantic 模型，自动生成 OpenAPI 文档

**后端项目结构：**

```text
backend/app/
├── api/        # 路由
├── core/       # 配置、安全、依赖
├── models/     # 数据库模型
├── schemas/    # Pydantic 模型
├── services/   # 业务逻辑
├── tasks/      # Celery 任务
└── utils/      # 工具
```

**API 规范：** RESTful；统一响应 `{ "code": 0, "msg": "", "data": {} }`

**UI 设计规范：**

- **禁止使用 Emoji 作为图标** — 所有图标必须使用 `@ant-design/icons` 或 SVG 图标，严禁使用 Emoji 表情符号（如 🎤 🖥️ 等）作为 UI 图标，以确保跨平台/跨浏览器的一致性和专业外观。
- **深浅色模式**：所有组件或功能（按钮、浮窗、选中框、互动组件、信息、图标、文字等）都必须适配深浅色模式

## 7. 数据库设计公约

所有数据库表遵循以下统一约定，具体表结构见 `项目架构/` 目录下的数据库设计文档。

### 通用约定

| 项目 | 约定 |
|------|------|
| **主键** | 统一使用 UUID（`uuid.UUID`，`UUID(as_uuid=True)`） |
| **时区** | 统一 Asia/Shanghai，数据库、容器与 Python 三层保持一致 |
| **可见性** | 各内容表通过 `visibility`（`private`/`public`/`restricted`）、`restricted_users`（JSONB）、`restricted_tags`（JSONB）字段实现 |
| **动态数据** | 使用 PostgreSQL JSONB 存储模板定义、填写数据、配置等动态结构 |
| **时间戳** | 统一使用 `DateTime` + `server_default=func.now()`，`updated_at` 加 `onupdate=func.now()` |
| **迁移** | 由 Alembic 管理，启动时 `create_all` 兜底 |

### 表结构索引

完整表结构见 `项目架构/数据库设计概览.md` 及 `项目架构/数据库演进与迁移.md`。
