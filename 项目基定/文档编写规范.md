# 项目文档编写规范

## 适用范围

本规范约束项目中所有基定文档、架构文档、设计规范的编写与维护。开发日志的格式另有单独规定，不在本规范范围内。

## 文档定位

文档是项目规范的唯一权威来源。当文档与代码实现出现分歧时，以文档为准——要么修正代码以符合文档，要么更新文档以反映新的规范决策。不允许文档与代码长期不一致。

## 核心原则

### 1. 清晰、具体、全面

- 每个标题下至少有一段正文，禁止空章节。
- 使用确切数值、具体文件名、完整路径，避免模糊表述（"大概"、"可能"、"若干"之类）。
- 描述系统行为时覆盖正常路径与异常路径。
- 对安全、权限、数据完整性等关键约束必须单独列明，不得隐含在其他段落中。

### 2. 跟随项目

- 文档描述的是项目的**当前状态**，而非历史演变过程。
- 当功能、架构、规范发生变更时，直接更新文档为最新版本，不保留旧描述。
- **禁止写入变更日志、迭代记录、版本对比**——这些信息属于 Git 历史或开发日志，不属于规范文档。
- 新增功能时同步更新相关文档，删除功能时同步清理文档中的残留引用。

### 3. 避免一对一索引

文档之间的引用采用概括性描述，避免硬编码具体文档名或文件数量：

- ✅ `详见项目架构文档中安全设计相关部分`
- ❌ `详见 [安全设计说明](../项目架构/安全设计说明.md)`
- ✅ `系统架构设计文档位于项目架构目录`
- ❌ `共 12 篇：安全设计说明 \| 权限模型设计 \| ...`

原因：文档会增删，硬编码的引用需要逐一手动同步，容易遗漏产生死链。指向目录而非具体文件名，新文档自然纳入索引范围。

## 格式约定

### 标题层级

- `#`：文档标题（全文仅一个）
- `##`：大章节
- `###`：子章节
- 最多使用到 `###`，不嵌套更深层级

### 代码与路径

- 文件名、类名、函数名使用反引号包裹：`app/core/security.py`、`derive_key()`。
- 代码块标注语言类型。
- 配置示例使用反引号包裹键名：`SECRET_KEY`、`--sider-width`。

### 列表

- 技术参数、配置项、规则条款使用无序列表（`-`）。
- 有先后顺序的操作步骤使用有序列表（`1.`）。
- 列表项之间不使用空行分隔，保持紧凑。

### 表格

- 表格用于多维度对比或参数汇总。
- 每个表格上方必须有描述性文字说明表格用途。
- 列数不超过 5 列，超出时考虑拆分或改用列表。

### 禁止事项

- 禁止使用 Emoji 作为装饰或图标。
- 禁止在规范文档中编写变更日志或版更记录。
- 禁止使用"等"字草草收尾——列出即穷举，不确定则核实后补全。
- 禁止跨文档复制粘贴大段相同内容，用引用指向源文档。

## 更新要求

- 任何涉及架构、安全、权限、API、UI 规范的代码变更，必须在对应的规范文档中同步更新。
- 新增文件或目录时，更新 `文件目录及说明.txt`。
- 删除功能模块时，检查所有文档中对该模块的引用并清理。
- 更新后通过 Git diff 自检，确保没有残留的旧描述。

## 与已有风格的一致

基定文档（`项目基定/` 下）使用编号段落风格（"一、二、三"），如 `文件目录及说明.txt`。架构文档（`项目架构/` 下）使用 Markdown 标题层级，如 `数据库设计概览.md`。新文档根据所属目录沿用对应风格，不混用。

## 输出物检查清单

编写或更新文档后自检：

- [ ] 所有标题下均有正文，无空章节。
- [ ] 所有引用的文件名、函数名、路径经核实真实存在。
- [ ] 无具体文档名的硬编码引用（除本文档索引表）。
- [ ] 无变更日志、版更记录、迭代描述。
- [ ] 无 Emoji。
- [ ] 新文件已在 `文件目录及说明.txt` 中注册。
