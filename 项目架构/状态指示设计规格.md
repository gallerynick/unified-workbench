## 一、目标

在 header 与登录/锁定页提供常驻的「使用能力」状态指示，让用户一眼看出当前是否可正常使用、以及受阻原因。

**核心边界规则：**

> 状态指示只回答一个问题——「当前这个用户还能不能用」。
> 服务端运维健康（磁盘容量、备份结果、数据库迁移状态）不进状态指示。

**非目标：** 管理员查看服务端运行健康，正确落点是「系统设置 → 系统状态」页，不在本次范围。

## 三、状态清单

### 3.1 登录页 + 锁定页 + header 通用（10 项）

登录前即可判定，三处统一显示。

| ID | 状态 | 灯 | 判定依据 | 文案 |
|---|---|---|---|---|
| A1 | 后端不可达 | 🟡→🔴 | 🟡 前置：`navigator.onLine === false` 且最近一次 `/health` 失败；🔴 确认：`GET /api/v1/health` 连续 3 次失败（传输失败，或 nginx 的 502/503/504） | 浏览器报告离线 / 网络已断开 |
| A2 | 高延迟 | 🟡 | 最近 5 次采样中 ≥ 2 次 RTT > 800ms | 网络延迟较高 |
| B1 | HTTP 明文传输 | 🟡 | `location.protocol === 'http:'` 且 hostname 非 localhost | 未启用 HTTPS |
| B2 | 非安全上下文 | 🔴 | `!window.isSecureContext` | 非安全环境，直播等能力不可用 |
| B3 | 公网访问 | 🟡 | hostname 不属回环/局域网段（规则见 3.3） | 正在通过公网访问 |
| C1 | 站点维护模式 | 🔴 | `GET /system/site-config` 的 `maintenance_mode` | 系统维护中 |
| C2 | 数据服务不可用 | 🔴 | `GET /health/db` 连续 2 次返回 HTTP 2xx 且 `status: unhealthy` | 数据服务暂时不可用 |
| D1 | 前后端版本不匹配 | 🔴 | 前端构建版本 ≠ `/health` 返回的 `version` | 版本不匹配，请刷新 |
| D2 | 本机时间偏差 | 🟡 | `|本机时间 − server_time| > 5min` | 本机时间偏差超过 5 分钟 |
| D3 | 浏览器能力不完整 | 🟡 | 缺 `WebSocket` / `navigator.mediaDevices` / `Notification` / `PublicKeyCredential` 任一 | 浏览器能力不完整 |

### 3.2 仅 header 显示（6 项）

需要登录态或服务级探测，登录页/锁定页不显示。

| ID | 状态 | 灯 | 判定依据 | 文案 |
|---|---|---|---|---|
| A3 | 实时通道中断 | 🟡 | `useWebSocket().connected === false` | 实时提醒不可用 |
| C3 | 文件服务不可用 | 🔴 | `/system/status` 的 `services.storage` 连续 2 次为 `unavailable` | 文件服务暂时不可用 |
| C4 | 直播服务不可用 | 🟡 | `/system/status` 的 `services.stream` 连续 2 次为 `unavailable` | 直播服务暂时不可用 |
| C5 | 提醒服务不可用 | 🟡 | `/system/status` 的 `services.tasks` 连续 2 次为 `unavailable`（心跳新鲜度 > 5min 判 stale） | 提醒服务暂时不可用 |
| E1 | 即将自动锁定 | 🟡 | 闲置自动锁定倒计时剩余 ≤ 30s | 即将自动锁定 |
| F1 | 账号并发登录 | 🟡 | `/me/concurrent`：30 分钟内其他 IP 数 ≥ 1 或其他设备数 ≥ 1 | 账号在其他设备登录 |

**合计 16 项。**

**误报抑制（三项通用规则）：**

1. **服务级抖动抑制**（C2 / C3 / C4 / C5，前端 `flapGate` + `FLAP_GUARD = 2`）：要求连续 2 轮巡检异常才告警，代价是真实故障晚报约一个巡检周期（60s）。单轮探测本身失败（网络抖动、令牌过期、端点 5xx）既不计入也不清零——计入会把一次网络抖动误判成服务故障并挂一整个周期，清零会让故障期恰逢网络抖动时故障被掩盖。C5 尤其需要：服务端 `_check_tasks_sync` 只看 `last_beat_at` 单点时间戳，机器长时间睡眠、容器重启或系统自动校时让时钟向前跳过 5 分钟就会被判成「任务挂了」，而 beat 下一跳（≤60s）即自愈。
2. **A1 交叉校验**：`navigator.onLine` 在 Chromium 系由 network service 全局判定，本机 LAN 与后端都正常时也可能为 `false`，且 `online` 事件不一定会补发——无条件采信会留下一条永不消失的 CRITICAL 误报。故该信号只有后端 `/health` 也探测失败时才采信，级别降为 🟡 作为前置提示；后端可达即证伪。🔴 仍只由连续 3 次 `/health` 失败触发。

3. **非 2xx 不等于故障**：探测端点返回非 2xx 不能一律当失败。`/health` 只在 502/503/504（nginx 连不上上游，语义即后端不可达）时计失败，其余非 2xx 说明对端已回包、连接是通的，判为可达；`/health/db` 的任何非 2xx 都不计「数据库不健康」。原因：该端点用 `Depends(get_db)`，数据库层异常在依赖解析阶段就抛错，FastAPI 直接返回 500，走不到端点内 `try/except` 的 `unhealthy` 分支——「数据库真挂了」和「后端自身出错」在前端看来是同一个 500。判错会让一次后端重启窗口（nginx 连续 502）被报成「数据服务暂时不可用」，而后端可达性本身应由 A1 负责。

### 3.3 B3 公网访问判定规则

| hostname | 判定 | 是否提示 |
|---|---|---|
| `localhost` / `127.0.0.0/8` / `::1` | 本机访问 | 否 |
| `10/8`、`172.16/12`、`192.168/16` | IPv4 局域网访问 | 否 |
| `fc00::/7`、`fe80::/10` | IPv6 私有 / 链路本地 | 否 |
| 其他 IPv4 / IPv6（**含公网 IP 直连**） | 公网访问 | 是 |
| **域名** | **一律按公网处理** | 是 |

> **穿透的两种访问方式都已覆盖**：走域名（如 `xxx.natapp.cc`）由"域名一律按公网"兜住；走公网 IP 直连（如 `47.96.x.x`）由"其他 IPv4"分支兜住。两者最终都落到同一条 🟡 提示，不需要区分穿透与公网直连——对用户的风险含义相同。
>
> **IPv6 实现注意**：URL 解析后 IPv6 字面量不带方括号（`2400:abcd::1`）。ULA 判定用 `/^f[cd][0-3]/`，链路本地用 `/^fe[89ab]/`，加 `::1` 特判即可，无需引入 IP 解析库。

> **域名一律按公网的理由**：浏览器无法解析 DNS，前端拿不到解析结果，无法区分内网 DNS 域名与穿透域名。本项目为单机 Docker 部署（macOS/Windows + Docker Desktop），内网 DNS 部署概率很低；而穿透部署必然走域名。安全默认是宁可提示也不漏。
>
> **后端无法作为 B3 兜底**：nginx 已设置 `proxy_set_header X-Real-IP $remote_addr` 与 `X-Forwarded-For`，但 uvicorn 未启用 `--proxy-headers`，`request.client.host` 恒为容器网桥 IP（`172.18.0.x`）。读取 `X-Real-IP` 响应头**可以**拿到真实来源 IP（`api/forms.py` 的 `_client_ip()` 与 `api/auth.py` 的同名助手都这么做），所以会话 IP 记录是准确的；但 B3 判定的是「访问用的主机名是否为公网」，那是浏览器侧信息，服务端永远看不到，因此 B3 只能在前端做。

### 3.4 明确不显示的状态（避免"太吵"）

| 类别 | 状态 | 不显示的理由 |
|---|---|---|
| 服务端运维 | 磁盘容量、备份结果、数据库待迁移、Redis 缓存服务 | 用户无法感知或无法行动；Redis 症状分散在登录限流，用户无从理解 |
| 个人偏好 | 2FA 未绑定、恢复码余量、通知权限未授权 | 属个人设置，留安全设置页提示 |
| 局部状态 | 单个直播间推流失败、表单校验失败 | 页面内 `message` 已提示 |
| 已有承载 | 未读通知/公告 | 已有铃铛 |
| 已有承载 | 空闲自动锁定开关 | header 已有图标 |

## 四、探测机制

### 4.1 数据源

| 端点 | 认证要求 | 提供 |
|---|---|---|
| `GET /api/v1/health` | 公开 | `version`、`server_time`（**新增**） |
| `GET /api/v1/health/db` | 公开 | 数据库连通性 |
| `GET /api/v1/system/site-config` | 公开 | `maintenance_mode` |
| `GET /api/v1/system/status` | **需登录** | `services{database,storage,stream,tasks}`、`server_time`（**新增端点**） |
| `GET /api/v1/me/concurrent` | **需登录** | `concurrent{other_session_count,other_ip_count,other_device_count}`（**新增端点，F1 专用**） |

> `maintenance_mode` 只走 `site-config`，不在 `/system/status` 中重复返回（单一来源）。
>
> `/system/status` 需登录的理由：存储/流媒体/提醒的健康状态暴露给匿名访客无意义，反而成为攻击者的探测入口。
>
> **并发统计为何单独开一个端点**：`/system/status` 除了查询数据库，还要做 `os.statvfs` + 真实写入探针、以及 mediamtx 连通性探测，不适合高频调用。并发登录属安全语义，需要秒级响应，因此拆出只含一条按 `user_id` 索引查询的轻量端点 `/me/concurrent`，由前端按 10s 轮询。两端点的统计逻辑共用 `app/services/session_activity.py`，不会出现两套口径。

### 4.2 节奏

| 探测项 | 节奏 |
|---|---|
| B1 / B2 / B3 / D3 | mount 时一次性求值 |
| `/health`（A1 / A2 / D1 / D2） | mount 一次 + 每 60s |
| `/health/db`（C2） | mount 一次 + 每 60s |
| `/system/site-config`（C1） | mount 一次 + 每 60s |
| `/system/status`（C3 / C4 / C5） | 仅登录态，每 60s |
| `/me/concurrent`（F1） | 仅登录态，实时推送 + 每 10s 轮询兜底 |
| A3 | 实时订阅 WebSocket 连接状态 |
| E1 | 订阅现有闲置锁定时钟 |

### 4.3 阈值（常量集中定义于 hook 顶部）

| 项 | 值 |
|---|---|
| A1 前置提示（🟡） | `navigator.onLine === false` 且最近一次 `/health` 探测失败，单轮即提示 |
| A1 确认阈值（🔴） | `/health` 连续失败 3 次 |
| A2 延迟阈值 | 最近 5 次采样中 ≥ 2 次 RTT > 800ms |
| C2 / C3 / C4 / C5 抖动抑制 | 连续异常 2 轮（`FLAP_GUARD`）；探测本身失败既不计入也不清零 |
| D2 时间偏差 | > 5min |
| C5 心跳新鲜度 | > 5min（服务端 `HEARTBEAT_STALE_SECONDS`） |
| E1 锁定预警 | 剩余 ≤ 30s |
| F1 并发会话时间窗 | 30min（服务端 `CONCURRENT_RECENT_MINUTES`，`services/session_activity.py`），按「最后活跃时间」计 |
| F1 活跃时间刷新间隔 | 60s（服务端 `SESSION_ACTIVE_REFRESH_SECONDS`，`core/deps.py`） |
| F1 提示阈值 | 其他 IP 数 ≥ 1 或其他设备数 ≥ 1 |
| F1 轮询兜底周期 | 10s（`CONCURRENT_POLL_MS`），另有 WebSocket 推送触发即时探测 |
| 巡检周期 | 60s |

## 五、后端改动

1. **`GET /api/v1/health`**：`data` 增加 `server_time`（ISO8601，`+08:00`）。
2. **新增 `GET /api/v1/system/status`**（需登录）：

```json
{ "code": 0, "msg": "", "data": {
    "services": { "database": "ok", "storage": "ok", "stream": "ok", "tasks": "degraded" },
    "server_time": "2026-09-08T12:00:00+08:00"
}}
```

| 字段 | 判定方式 |
|---|---|
| `services.database` | `SELECT 1`（复用 `/health/db` 逻辑） |
| `services.storage` | `os.statvfs` + 写入探针，目标 `settings.FILE_STORAGE_PATH` |
| `services.stream` | `http://mediamtx:8889/` 连通性探测（nginx `/live/` 同指此端口） |
| `services.tasks` | 读心跳时间戳，与当前时间比较新鲜度 |

3. **新增 `app/services/session_activity.py`**：并发会话统计的单一实现，被 `/system/status` 与 `/me/concurrent` 共用，避免出现两套口径。

| 成员 | 作用 |
|---|---|
| `CONCURRENT_RECENT_MINUTES = 30` | 统计时间窗，与前端阈值表需双向同步 |
| `get_current_session(db, user, token)` | 按 JWT 的 `jti` 反查当前会话，用于把「自己」从统计里排除 |
| `count_concurrent(db, user, current)` | 返回 `other_session_count` / `other_ip_count` / `other_device_count` |

统计规则：先按 `user_id` + 未撤销 + 「最后活跃时间」距今 30 分钟窗口取会话集合，再剔除当前会话的 `jti`，最后按 IP、`device_token` 分别去重，并从两个集合中移除当前会话自己的值。`token` 缺失或 `jti` 查不到记录时取不到当前会话，统计退化为「全部未撤销会话」——宁可提示也不漏提示。

窗口的时间基准是 `COALESCE(last_active_at, created_at)` 而不是 `created_at`：以创建时间为基准会让登录满 30 分钟的标签页被静默排除（详见 5.4）。

**同设备新开标签页不触发提示**：新会话与当前会话同 IP、同 `device_token`，两个去重集合都被剔除，计数为 0。

**容器部署下 `other_ip_count` 不可靠**：Nginx 本身是容器时，它看到的 `$remote_addr` 是网桥 IP（`192.168.65.x` / `172.18.0.x`），所有浏览器会话的 `ip_address` 记成同一个值，`other_ip_count` 恒为 0。此时 F1 完全依赖 `other_device_count`（`X-Device-Token` 来自 `localStorage`，按 origin 隔离，`localhost` 与局域网 IP 各一个），阈值 `other_ip_count >= 1 || other_device_count >= 1` 仍然成立。若要让「不同 IP」在容器部署下生效，需先让 Nginx 拿到真实客户端 IP（如 `host.docker.internal` 与 `--proxy-headers`）。

4. **新增 `GET /api/v1/me/concurrent`**（需登录，F1 专用）：

```json
{ "code": 0, "msg": "", "data": {
    "other_session_count": 2, "other_ip_count": 1, "other_device_count": 1
}}
```

只调用上面两个函数，不做存储写入探针与推流连通性探测，因此可以支撑 10s 轮询。

5. **新增 `POST /api/v1/auth/logout`**（需登录）：把当前会话的 `is_revoked` 置为 true，幂等返回 `{"revoked": bool}`。

必须存在的理由：原实现的前端登出只清 localStorage，`user_session.is_revoked` 保持 false，后端仍把该会话计入「其他在线会话」，F1 提示永不消失。撤销后 `core/deps.py` 的 `get_current_user` 按 `jti` 反查会拦截该令牌的后续请求，即强制下线。会话不存在或已撤销时同样返回成功，登出不应因重试而报错。

6. **新增 60s Celery beat 心跳任务**：写时间戳到 `system_config`（key 如 `task_heartbeat`），供 `services.tasks` 判定。

### 5.1 F1 并发登录的实时推送（增量）

纯轮询下 F1 的消失要等下一个轮询周期（最长 10s），用户感知为「要刷新才消失」。改为推送 + 轮询兜底：

| 事件 | 位置 | 动作 |
|---|---|---|
| 新登录落库 | `services/auth.py` 的 `_issue_tokens` | 向该用户全部在线连接推 `session_alert` |
| 主动登出 | `api/auth.py` 的 `logout_endpoint` | 同上 |
| 撤销单个会话 | `api/user_sessions.py` 的 `revoke_session` | 同上 |
| 按设备批量注销 | `api/user_sessions.py` 的 `revoke_device` | 同上 |

推送消息为 `core/websocket.py` 的模块级常量 `SESSION_ALERT`，类型 `session_alert`，无负载。前端 `useWebSocket` 收到后调用 `useStatusProbes` 的 `emitConcurrentChange()`，所有 `useStatusProbes` 实例立即执行一次 F1 探测，不等下一个 10s 周期。10s 轮询保留为兜底：推送丢失、连接刚建立、或跨设备场景下仍能收敛。推送失败不影响主流程（`try/except` 吞掉），登出与撤销本身不依赖它。

实测延迟：新登录 → 1.21s，登出 / 撤销会话 → 1.02s。

### 5.2 WebSocket 连接支持同用户多连接（增量）

原 `ConnectionManager._connections` 是 `dict[UUID, WebSocket]`，每个用户只保留一条连接。同一用户开多个标签页时（`MainLayout` 与 `NotificationsWidget` 各实例化一次 `useWebSocket`），新旧连接每 3s 交替互相踢断；更关键的是，另一端登录时本端唯一连接正被另一个标签页抢走，`session_alert` 无法送达，这就是「A 看不到并发提示」的根因。

| 成员 | 改动 |
|---|---|
| `_connections` | `dict[UUID, set[WebSocket]]`，同一用户的多条连接并存 |
| `connect(user_id, ws)` | 只添加，不再关闭旧连接 |
| `disconnect(user_id, ws=None)` | 传 `ws` 只移除该条；不传则清空该用户全部连接 |
| `send_to_user(user_id, msg)` | 遍历该用户全部连接，返回实际送达数 |
| `send_to_user_except(user_id, msg, except_ws)` | 推送时排除发起方自身 |
| `user_connection_count(user_id)` | 单用户连接数 |
| `active_connections` | 返回总连接数（原为用户数） |
| `active_users` | 新增，返回有连接的用户数 |

消息模型不变：`manager.send_to_user` 仍是按用户投递，只是收件人集合从「至多一条」变为「该用户全部在线连接」。直播推流的实际数据走 MediaMTX，WebSocket 只承载 `room_kicked` 之类通知，因此多连接不会造成推流冲突。

### 5.3 登录侧的单设备策略（增量）

新增函数 `_enforce_single_device(db, user, allow_multiple_logins)`，在 `_issue_tokens` 中于本会话落库前调用：读取 `user.preferences` 的 `allow_multiple_logins`（缺省视为开启），关闭时把该用户全部未撤销会话置为 `is_revoked = True`，返回 `(other_session_count, revoked_session_count)` 写入 `LoginResponse`，供前端提示。

三条登录路径（普通登录、TOTP/恢复码二次验证、WebAuthn 二次验证）都汇聚到 `_issue_tokens`，把策略放在这里可保证任何登录方式遵守同一规则，无需在路由层重复实现。

统计范围是全部未撤销会话，不做 30 分钟窗口过滤：这里判断的是「该账号当前还有别的登录」，与 F1 的「最近活跃的其他会话」是两套语义，窗口过滤只在状态指示侧有意义。

详细设计与验证见《安全设计说明》的「单设备登录策略」小节。

### 5.4 会话活跃时间的按请求刷新（增量）

5.1 / 5.2 解决的是「推送送得到」，本节解决「窗口判断得对」——用户报障的第二层根因：localhost 与局域网两个标签页同时打开时，F1 仍然互相看不到对方。

原因：`count_concurrent` 的时间窗原先以 `user_session.created_at` 为基准，而 `last_active_at` 虽声明了 `onupdate=func.now()`，却没有任何请求路径去 UPDATE 那一行，它永远停在登录那一刻。任何登录满 30 分钟的标签页会被静默排除出统计：会话仍在、令牌有效、页面仍在轮询，并发统计再也看不到它。两个都开了半小时的连接因此互相认为对方不在线。

| 位置 | 改动 |
|---|---|
| `services/session_activity.py` | 窗口基准改为 `COALESCE(last_active_at, created_at) >= now - 30min` |
| `core/deps.py` | 新增 `SESSION_ACTIVE_REFRESH_SECONDS = 60`；`get_current_user` 按请求刷新 `last_active_at` |

`get_current_user` 的查询由「两次往返」合并为一次 JOIN（`select(UserSession, User)`）：jti 路径上的查询次数与改造前相同，同时拿到会话行与用户行，刷新时不必再查一次。令牌里无 `jti` 时退回按 `user_id` 查用户，行为与改造前一致。

刷新按 60s 节流：前端 F1 每 10s 轮询一次，若不节流会把写放大到每个请求一次。该值必须明显小于 30 分钟的窗口，否则正在使用的标签页仍会被误判为已离开。`last_active_at` 为空时窗口回退到 `created_at`（`COALESCE`），避免老数据或外部插入的空值整行漏统计。

持久化依赖 `core/database.py` 的 `get_db` 在请求结束后统一 `commit`；刷新发生在依赖解析阶段、端点处理之前，因此随请求一起落库。

不做心跳包：WebSocket 的 30s ping 只能证明网络存活，浏览器被直接关闭时 TCP 不一定可靠断开，会话存活判断必须落在数据库上。详见《安全设计说明》的「会话活跃时间与并发窗口」小节。
