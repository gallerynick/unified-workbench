# 数据导入导出设计

## 概述

数据迁转模块（路由 `/settings/transfer`）用于全量数据的导出与导入，覆盖全部业务表与用户上传文件。导出将数据库序列化为分页 JSON，连同文件目录打包为 **PBKDF2 派生 AES-256 加密 ZIP**；导入则执行解密、版本校验、紧急备份、清空覆盖、版本迁移、文件还原的完整编排，并在任何失败节点自动回退。模块仅对管理员开放，导入前还需二次输入登录密码验证。

设计目标：数据在磁盘上始终加密（防止直接解压）；导入操作可回滚（降低误操作损失）；版本可迁移（跨版本数据平滑升级）。

## 导出设计

导出按"数据表 → 用户文件 → 清单 → 加密打包"四阶段执行，全程在服务端临时目录完成，最终仅交付加密 ZIP。

### 导出内容与目录结构

导出服务位于 `项目文件/backend/app/services/data_export.py`，核心函数 `export_all(db, passphrase, progress_callback)`。导出产物结构：

```text
export.zip (AES-256 加密)
├── manifest.json          # 元数据清单
├── tables/<name>.json     # 每张表一个 JSON 文件（分页读取后合并）
└── files/<relative>       # FILE_STORAGE_PATH 下所有用户文件
```

### 表导出范围与拓扑排序

`EXPORT_TABLE_ORDER` 定义了 28 张导出表，按外键依赖排列（先父表后子表），保证导入时无外键冲突：

user → user_tag → system_config → tag → announcement → budget → subscription → calendar_event → contact → content → form → form_response → inventory → note → notification → project → reminder → secret_category → secret → servers → systems → services → stream_room → task → template → topology → vote → vote_record。

- `TABLE_MODEL_MAP` 提供表名到 SQLAlchemy Model 的映射。
- `SKIP_TABLES = {"user_notification_config"}`：临时性/可重建数据不导出（user_session、file_shares 亦不在此列表）。全库 31 张业务表中有 3 张不参与导出。
- 每张表以 1000 行/页分页读取（`page_size = 1000`），datetime 序列化为 ISO 字符串、UUID 转字符串、bytes 转 hex。

### manifest.json

`export_all` 阶段 3 生成 `manifest.json`：

```json
{
  "app_id": "unified-workbench",
  "version": "1.0.1",
  "exported_at": "ISO8601 UTC 时间",
  "tables": ["user", ...],
  "total_rows": 0,
  "file_count": 0
}
```

`version` 取自 `app/version.py` 的 `__version__`，用于导入时的版本兼容判定。

### 文件复制

`Phase 2` 遍历 `settings.FILE_STORAGE_PATH`，将全部文件按相对路径复制到 ZIP 的 `files/` 目录，保留目录层级。

### 加密打包

`Phase 4` 使用 `pyzipper`：

- `pyzipper.AESZipFile(zip_path, "w", compression=ZIP_DEFLATED, encryption=WZ_AES)`。
- `setpassword(key)` 设置由 `derive_key(passphrase, pepper, salt)` 派生的 AES-256 密钥。
- `setencryption(pyzipper.WZ_AES, nbits=256)` 强制 256 位。

### 导出任务追踪

- `start_export(db, passphrase)`：启动异步导出，返回 `export_id`（UUID），状态存入内存字典 `_export_tasks`。
- `get_export_status(export_id)` / `get_export_path(export_id)`：查询进度与结果。

### 导出 API

`项目文件/backend/app/api/data_export.py`（挂载于 `/api/v1/transfer`）：

- `POST /transfer/export`：`start_export_endpoint`，表单字段 `password`（管理员密码短语），`Depends(require_admin)` 保护。
- `GET /transfer/export/{export_id}/status`：`get_export_status_endpoint`。
- `GET /transfer/export/{export_id}/download`：`download_export_endpoint`，返回 ZIP 文件并将 salt 通过响应头 `X-Export-Salt` 返回，salt 独立于 ZIP 分发。

## 导入设计

导入服务位于 `项目文件/backend/app/services/data_import.py`，总编排函数 `import_all(db, zip_path, passphrase, salt_hex)`。

### 完整流程

1. **获取 pepper**：`get_or_create_pepper(db)`（从 `data_export` 复用），与服务端保持一致。
2. **解码 salt**：`bytes.fromhex(salt_hex)`，非法格式直接失败。
3. **读取 manifest**：`read_manifest(zip_path, passphrase, pepper, salt)` 用 `derive_key` 派生密钥打开 `pyzipper.AESZipFile` 读取 `manifest.json`，密码或 salt 错误时抛 `ValueError`。
4. **版本校验**：`validate_version(manifest_version)`。
5. **紧急备份**：`_backup_tables(db, backup_dir)` 将当前库全部表导出到临时目录，作为回退点。
6. **清空数据库**：`truncate_all_tables(db)` 按 `EXPORT_TABLE_ORDER` 逆序对每张表执行 `TRUNCATE TABLE "<name>" CASCADE`（子表优先，避免外键冲突）。
7. **逐表导入**：从 ZIP 读取 `tables/<name>.json`，`_parse_datetimes` 还原时间对象，调用 `import_table_data` 完成迁移与批量写入（每批 500 行）。
8. **文件提取**：`copy_imported_files(zip_path, passphrase, pepper, salt)` 将 `files/` 下的条目映射到 `FILE_STORAGE_PATH`。
9. **清理**：删除加密 ZIP。
10. **异常回退**：任一步失败则调用 `_restore_from_backup(db, backup_dir)`，先 TRUNCATE 再按序重灌备份 JSON；`stats.rollback` 标记回退结果。

### 版本兼容矩阵

`validate_version(manifest_version)`（`data_import.py`）结合迁移链 `MIGRATION_CHAIN`（`data_migrations/__init__.py`）实现：

| 数据版本 vs 当前版本 | 行为 |
| --- | --- |
| manifest_version == __version__ | 直接导入，无需迁移 |
| manifest_version < __version__ | 逐版本执行迁移链升级（0.2.0 → 1.0.0 → 1.0.1） |
| manifest_version > __version__ | 拒绝导入，抛"数据来源版本高于当前版本" |

- 迁移链：`data_migrations/__init__.py` 中 `MIGRATION_CHAIN = [("0.2.0", "app.services.data_migrations.v0_2_0"), ("1.0.0", "...v1_0_0"), ("1.0.1", "...v1_0_1")]`，`apply_migration_chain` 对介于源版本与目标版本之间的迁移模块逐个调用其 `upgrade(table_name, records)`。迁移文件：`v0_2_0.py`、`v1_0_0.py`、`v1_0_1.py`。

### 导入 API

`项目文件/backend/app/api/data_import.py`（挂载于 `/api/v1/transfer`）：

- `POST /transfer/import`：`start_import_endpoint`，表单含 `password`、`salt`、`file`（ZIP），`Depends(require_admin)`。
- `GET /transfer/import/{task_id}/status`：`get_import_status_endpoint`，注释明确 task_id 为不可猜测 UUID 即访问凭据，无需管理员权限。
- `POST /transfer/import/preview`：`preview_import_endpoint`，解密读取 manifest 后返回 `zip_version`、`current_version`、`can_import`、`version_note`、`exported_at`、`total_tables`、`total_rows`、`file_count`、`app_id`，不执行任何写入。

## 前端实现

前端由数据迁转页面承载导出、预览、二次验证与结果展示的完整交互链路。

### 数据迁转页面

`frontend/src/pages/settings/DataManagement.tsx`（路由 `/settings/transfer`，`BASE = '/api/v1/transfer'`）：

- **导出流程**：`handleExport` 以 FormData 提交密码启动导出，轮询 `/transfer/export/{id}/status`（1 秒间隔），完成后 `handleExportDownload` 下载 ZIP 并读取 `X-Export-Salt` 响应头存入 `exportSalt`，展示"请妥善保存 Salt 密钥"并支持复制与重复下载。
- **导入流程**：`handleImportClick` 提交文件、密码、salt 到 `/transfer/import/preview` 获取预览元数据；`can_import` 为 true 时弹出 `Modal.confirm`，展示数据版本对比（不一致时高亮"将自动迁移"）、导出时间、数据表数、数据行数，并警告"导入将完全覆盖现有数据且不可撤销"。
- **管理员二次验证**：确认后弹出"管理员密码验证" `Modal`，调用 `api/secrets.ts` 的 `verifyPassword`（后端 `POST /auth/verify-password`）验证通过后才执行 `doImport`。
- **结果与强制登出**：轮询 `/transfer/import/{id}/status`（2 秒间隔），成功后 `handleRefreshWorkbench` 执行 `localStorage.clear()` + `sessionStorage.clear()` + 跳转 `/login`，强制重新登录（避免旧会话引用已变更的数据）。
- 失败弹窗依据 `detectRollback` 展示回退状态："已自动回退到导入前的数据"或"回退失败，请手动恢复"。

## 安全约束

- 导出/导入端点仅管理员可用（`require_admin`）。
- 解密需同时持有 ZIP + salt + 密码短语 + 服务端 pepper，四要素缺一不可。
- salt 通过 HTTP 头独立传输，不写入 ZIP，避免自加密闭环。
- 导入前强制二次密码验证（`verifyPassword`）。
- 导入期间先做全库紧急备份，任何异常自动回退，回退失败时显式告警。
- 上传 ZIP 落临时文件，导入结束或异常时清理；密码短语与 salt 不持久化存储。
