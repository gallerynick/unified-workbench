# 任务队列与缓存

> 本文档描述基于 Celery + Redis 的异步任务体系与 Redis 缓存应用：Celery 应用配置、Beat 定时调度、异步执行模式、登录限流与连接管理。适用于排查定时任务不执行、理解异步边界与 Redis 使用场景。

## 概述

系统使用 Celery 处理两类异步工作：**定时任务**（Celery Beat 调度 + Worker 执行）与**异步作业**（业务代码通过 `shared_task` 提交）。两者共用 Redis 作为 broker 与 result backend（分别使用不同 db 编号，见 `配置管理体系`）。所有任务定义位于 `app/tasks/` 包，通过 `celery -A app.tasks` 启动。

容器层面：

- `celery` 容器：`celery -A app.tasks worker --loglevel=info`，执行任务。
- `celery-beat` 容器：`celery -A app.tasks beat --loglevel=info --schedule=/tmp/celerybeat-schedule`，调度文件放 `/tmp`（`working_dir: /tmp` + `PYTHONPATH=/app`）。

## 核心设计

### Celery 应用配置

`app/tasks/__init__.py` 创建应用：

```python
celery_app = Celery(
    "unified_workbench",
    broker=settings.REDIS_URL,        # redis://redis:6379/0
    backend=settings.REDIS_URL,
    include=[
        "app.tasks.reminder",
        "app.tasks.backup",
        "app.tasks.calendar_reminder",
        "app.tasks.stream_room",
        "app.tasks.file_share_cleanup",
    ],
)

celery_app.conf.update(
    task_serializer="json",
    accept_content=["json"],
    result_serializer="json",
    timezone="Asia/Shanghai",
    enable_utc=True,
    task_track_started=True,
    task_time_limit=3600,          # 单任务最大 1 小时
    worker_max_tasks_per_child=1000,
)
```

要点：

- **broker 与 backend 相同**，均为 `settings.REDIS_URL`（`.env` 中 `REDIS_URL=redis://redis:6379/0`；`.env.example` 另有 `CELERY_BROKER_URL`/`CELERY_RESULT_BACKEND` 历史字段，当前实现未使用，统一走 `REDIS_URL`）。
- 序列化全部 JSON，避免 pickle 安全问题。
- 时区 `Asia/Shanghai` + `enable_utc=True`：任务内部使用 `datetime.now(UTC)` 或 `datetime.now()` 需与表列类型（`DateTime` vs `DateTime(timezone=True)`）匹配，详见 `数据库演进与迁移` 的时区章节。
- 任务超时 1 小时，单 worker 进程最多处理 1000 个任务后回收（防内存泄漏）。

### Beat 调度表（6 个定时任务）

`app/tasks/__init__.py` 中 `celery_app.conf.beat_schedule`：

| 调度名 | 任务 | 间隔 |
|--------|------|------|
| check-due-reminders | `app.tasks.reminder.check_due_reminders` | 10s |
| check-calendar-reminders | `app.tasks.calendar_reminder.check_calendar_reminders` | 10s |
| scheduled-backup | `app.tasks.backup.scheduled_backup` | 86400s（每天） |
| sync-room-active-status | `app.tasks.stream_room.sync_room_active_status` | 60s |
| cleanup-temporary-rooms | `app.tasks.stream_room.cleanup_temporary_rooms` | 300s |
| cleanup-expired-shares | `app.tasks.file_share_cleanup.cleanup_expired_shares` | 300s |

各任务行为：

- `check_due_reminders`（`app/tasks/reminder.py`）：查询 `ReminderStatus.PENDING` 且 `trigger_time <= now` 的提醒，逐个调用 `dispatch_reminder`（`app/services/notification/dispatcher.py`），按发送结果标记 `SENT`/`FAILED`。
- `check_calendar_reminders`（`app/tasks/calendar_reminder.py`）：扫描 `reminder_enabled=True` 且未提醒的日历事件，计算 `start_time - reminder_minutes` 到达后通过 `WebSocketChannel`（`app/services/notification/websocket_channel.py`）推送；已过期事件仅标记 `reminded=True`。
- `scheduled_backup`（`app/tasks/backup.py`）：读取 `system_config` 的 `backup_config`，`enabled=false` 直接返回；否则 `create_backup(backup_dir)` + `cleanup_old_backups(backup_dir, max_backups)`（`app/services/backup.py`），默认保留 7 份。
- `sync_room_active_status`（`app/tasks/stream_room.py`）：调 `mediamtx.get_active_paths()`（`app/services/mediamtx.py`）轮询 MediaMTX 活跃路径，批量更新 `stream_room.is_active`（将 UUID 列 cast 为 String 与路径比较）。
- `cleanup_temporary_rooms`（`app/tasks/stream_room.py`）：删除超过 `TEMP_ROOM_TTL_MINUTES`（默认 30 分钟）TTL 且非活跃的 `TEMPORARY` 类型房间。
- `cleanup_expired_shares`（`app/tasks/file_share_cleanup.py`）：两阶段清理文件分享。Phase 1 每 300s：过期超 10 分钟且未标记的分享删除物理文件 + 标记 `is_deleted`；Phase 2 每 300s：标记删除超 7 天的记录硬删除。

### 异步执行模式：shared_task + asyncio.run + get_session_factory

Celery worker 运行在同步进程内，而业务代码（数据库访问、通知发送）是 async。统一模式是：**任务函数（同步）→ asyncio.run → async 实现 → get_session_factory 创建独立 AsyncSession**：

```python
from celery import shared_task
import asyncio

from app.core.database import get_session_factory

@shared_task
def check_due_reminders():
    asyncio.run(_check_due_reminders_async())

async def _check_due_reminders_async():
    session_factory = get_session_factory()
    async with session_factory() as db:
        ...
        await db.commit()
```

要点：

- 每个任务独立创建 SessionFactory（复用应用级 AsyncEngine 连接池），不共享请求级会话。
- `get_session_factory()` 来自 `app/core/database.py`，与请求路径共用同一套引擎配置（`pool_size=20`），任务上下文会自动惰性初始化引擎。
- 任务内自行控制事务边界（`flush` + `commit`）。

### Redis 缓存应用

#### 登录失败计数（限流）

`app/services/auth.py`：

- 常量：`MAX_LOGIN_ATTEMPTS = 5`，`LOCKOUT_DURATION = 3`（秒）。
- `_check_login_rate_limit(username, ip)`：读取 `login_attempts:{username}`，达到上限抛 `HTTPException(429, "登录失败次数过多，请 {ttl} 秒后重试")`。
- `_record_login_failure(username)`：登录失败时 `INCR` 并 `EXPIRE key LOCKOUT_DURATION`。
- `_clear_login_attempts(username)`：登录成功后 `DEL`。
- Redis 不可用时所有限流函数静默跳过（try/except 吞异常），保证可用性优先。

#### 会话撤销（DB 而非 Redis）

系统不存在 `KickUserSession` 之类的 Redis 结构。会话撤销走数据库：登录时写入 `user_session` 表（jti + 设备信息），撤销时置 `is_revoked=True`，`get_current_user` 在 JWT 解码后查询该表做黑名单检查。详见 [请求处理链路](请求处理链路.md)。

#### 计数 / 限流延伸

当前 Redis 直接用途集中在登录限流；消息队列通过 broker 天然复用 Redis。如需扩展（接口频控、点赞防抖、房间在线人数），可沿用 `login_attempts` 的 key 前缀模式接入同一 Redis 连接。

### Redis 连接管理

限流函数采用**短连接模式**：

```python
import redis.asyncio as aioredis

redis = aioredis.from_url(settings.REDIS_URL)   # 每次调用创建新客户端
key = f"login_attempts:{username}"
attempts = await redis.get(key)
await redis.close()                              # 用完立即关闭
```

要点：

- 使用 `redis.asyncio`，与 async 上下文匹配。
- 每次 `from_url` 新建客户端、用完 `close()`，通过 redis-py 客户端内部的连接池复用底层 TCP 连接；对低频限流操作开销可接受。
- Celery broker/backend 由 Celery 自身管理连接，不受上述短连接模式影响。
- 若未来高频使用 Redis，应改为模块级懒加载的单例客户端 + 显式关闭钩子。

## 配置示例

任务定义模板（新增定时任务三步）：

```python
# 1. 在 app/tasks/xxx.py 定义 shared_task
@shared_task
def my_periodic_task():
    asyncio.run(_my_async())

async def _my_async():
    sf = get_session_factory()
    async with sf() as db:
        ...

# 2. 在 tasks/__init__.py 的 include 中追加模块
# 3. 在 beat_schedule 中追加条目
celery_app.conf.beat_schedule["my-task"] = {
    "task": "app.tasks.xxx.my_periodic_task",
    "schedule": 300.0,
}
```
