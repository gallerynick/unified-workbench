# 数据库演进与迁移

> 本文档描述数据库 Schema 的演进机制：Alembic 配置、迁移链、命名与幂等策略、create_all 与迁移的关系、回滚与常见陷阱。适用于新增表、修改字段、排查迁移失败。

## 概述

数据库为 PostgreSQL 15，通过两套机制保证表结构演进：

1. **Alembic 迁移**：`backend/alembic/` 下管理 34 个迁移文件，串成一条线性迁移链，适合对既有数据做增量变更（加列、加表、改类型）。
2. **create_all 兜底**：backend 容器启动时执行 `Base.metadata.create_all`（见 `backend/Dockerfile` CMD），新环境无需迁移即可建全表。

两者的关系与冲突处理见下文"实际迁移 vs create_all"。

## 核心设计

### Alembic 配置（env.py）

`backend/alembic/env.py`：

- 使用**异步引擎**：`async_engine_from_config` 创建连接，`run_migrations_online` 内 `asyncio.run(run_async_migrations())`。
- **模型导入**：显式 `from app.models import (...)` 全部模型（Announcement、Budget、CalendarEvent、Content、FileShare、Form、Inventory、Note、Notification、Reminder、Secret、SecretCategory、StreamRoom、Subscription、SystemConfig、Tag、Task、Template、Topology、User、UserTag、Vote），确保注册到 `Base.metadata`，`target_metadata = Base.metadata`。
- **数据库 URL 来源**：不在 `alembic.ini` 硬编码，`config.set_main_option("sqlalchemy.url", settings.DATABASE_URL)`，从环境变量（.env → Pydantic Settings）读取，保证与运行时一致。
- `alembic.ini` 仅配置 `script_location = alembic` 与日志。

共 34 个文件。头尾两个 revision id 是十进制序号（`001`），中段因手工创建使用 `0xx_description` 命名，而 `c6b2e4425e8c_replace_file_management_with_file_sharing` 是 Alembic 自动生成的哈希 revision（位于 `018` 与 `019` 之间）。

### 命名规范

- 目标格式：`0xx_description.py`（如 `020_create_server_tables.py`、`030_add_calendar_reminder.py`）。
- revision id 与文件名中的数字一致（`020` ↔ `revision: str = "020"`）。
- 例外：自动生成的哈希 revision（`c6b2e4425e8c_...`），文件名带描述后缀，revision 为哈希串。
- 每个文件内 `down_revision` 指向前一个 revision，形成线性链，无分支（`branch_labels = None`）。

### 幂等策略

为兼容"部分迁移已手动执行"或"create_all 已建表"的环境，增量变更广泛使用幂等写法：

- **ADD COLUMN IF NOT EXISTS**（PostgreSQL 原生支持，用在 `op.execute` 的裸 SQL 中）：

```python
# 030_add_calendar_reminder.py
op.execute("ALTER TABLE calendar_event ADD COLUMN IF NOT EXISTS reminder_enabled BOOLEAN DEFAULT FALSE")
op.execute("ALTER TABLE calendar_event ADD COLUMN IF NOT EXISTS reminder_minutes INTEGER DEFAULT 15")
```

- **DROP COLUMN IF EXISTS** / **DROP CONSTRAINT IF EXISTS**：

```python
# 022_server_unified_refactor.py — 删除旧 CheckConstraint（IF EXISTS 兼容无此约束的情况）
```

- **ALTER TABLE IF EXISTS**（表可能不存在时防错，见 `031_remove_reminder_event_type.py`）。
- `op.add_column` 本身无 IF NOT EXISTS，`029_add_user_contact_fields.py` 用 try/except 实现同效幂等。

### 实际迁移 vs create_all

关键事实：**当前部署采用 create_all 优先**。

- `backend/Dockerfile` 启动命令先执行：

```
python -c "from sqlalchemy import create_engine; ...; Base.metadata.create_all(engine)"
```

  再启动 uvicorn。因此**新环境建表由 create_all 完成，不经过 alembic 迁移，数据库中没有 `alembic_version` 表或版本落后**。
- Alembic 迁移文件此时**只对增量字段变更生效**。若在 create_all 之上运行 `alembic upgrade head`，大量历史迁移（建表类）会因表已存在而失败，这是预期现象。
- **正确做法**：对已用 create_all 初始化且没有 `alembic_version` 的环境，先 `alembic stamp head` 将版本指针直接打到最新（不执行任何迁移），此后 `upgrade head` 只运行新增的增量迁移。
- 对全新环境若想走纯迁移路线（不依赖 create_all），需先执行全部迁移到 head；两条路线只选其一，避免 create_all 与迁移同时建同名对象。

### 回滚策略

每个迁移文件实现 `downgrade()`：

- 建表类迁移的 downgrade 为 `op.drop_table`（如 `033_user_session.py`：`op.drop_table("user_session")`）。
- 枚举类型迁移的 downgrade 会 drop 枚举（`001_initial_tables.py` 用 `sa.Enum(name=...).drop(op.get_bind(), checkfirst=True)`）。
- 大重构迁移的 downgrade 尽量完整还原（如 `c6b2e4425e8c` 的 downgrade 重建 folder/file/content_file 三表；`022_server_unified_refactor` 的 downgrade 恢复 CheckConstraint）。
- 回滚执行：`alembic downgrade <revision>` 或 `alembic downgrade -1`（回退一步）。
- 注意：部分迁移的 downgrade 无法完全还原数据内容（仅还原结构），大数据量回滚前应备份。

### 迁移陷阱：sa.Enum 与 PostgreSQL

PostgreSQL 15 中 `CREATE TYPE ... AS ENUM` **不支持 `IF NOT EXISTS` 语法**（`001_initial_tables.py` 中曾直接写 `CREATE TYPE IF NOT EXISTS userrole AS ENUM (...)`，这在 PG 中会语法报错）。实践中规避方式：

1. **DO 块 + 异常捕获**（`010_create_module_tables.py`）：

```python
op.execute(f"DO $$ BEGIN CREATE TYPE {type_name} AS ENUM {type_values}; EXCEPTION WHEN duplicate_object THEN NULL; END $$;")
# 列定义使用 create_type=False，不重复建类型
sa.Column("status", sa.Enum("active", "closed", name="votestatus", create_type=False), ...)
```

2. **String + CheckConstraint 替代**（`020_create_server_tables.py` 对 server_type 使用 `VARCHAR(20) + CheckConstraint`；模型层 `app/models/*.py` 的 `Enum(..., create_type=False)` 配合迁移中手工建类型）。

3. 模型层统一 `create_type=False`，类型的生命周期完全交由迁移文件控制，避免 create_all 与迁移双重建类型。

### 时区统一

三层时区一致性约定：

- **数据库层**：db 容器 `TZ=Asia/Shanghai`（`docker-compose.yml`），表列既有无时区的 `DateTime`（多数业务表）也有 `DateTime(timezone=True)`（`user_session`）。
- **容器层**：backend/celery/celery-beat 均 `TZ=Asia/Shanghai`。
- **应用层**：`app/core/config.py` 无时区项；`security.py` 使用 `datetime.now(UTC)` 计算 JWT exp；`tasks/reminder.py` 用 `datetime.now(UTC)` 查 `Reminder.trigger_time`（无时区列，PG 会按 session 时区解释）。Celery `timezone="Asia/Shanghai"` + `enable_utc=True`。

注意：对无时区 `DateTime` 列，比较基准是数据库会话时区（Asia/Shanghai），写入 `datetime.now(UTC)` 的值会按 UTC 存储再被当作本地时间读取，可能偏移。新增列建议使用 `DateTime(timezone=True)`（如 `user_session`）并在任务/服务中统一 `datetime.now(UTC)`。

## 配置示例

新增迁移的标准流程：

```bash
# 生成迁移（在 backend 目录、容器内或宿主机可用时）
alembic revision -m "add_xxx_column" --rev-id 034

# 已用 create_all 初始化、无 alembic_version 的环境先 stamp
alembic stamp head

# 仅执行新增增量迁移
alembic upgrade head
```

迁移文件幂等列操作示例：

```python
def upgrade() -> None:
    op.execute("ALTER TABLE IF EXISTS reminder ADD COLUMN IF NOT EXISTS channels JSONB")
```
