# 通知推送架构

## 概述

通知推送链路覆盖"触发 → 分发 → 渠道发送 → 持久化 → 前端呈现"五个环节。触发源有两类：用户创建的定时提醒（reminders 表）与日历事件提醒（calendar_events 表）。触发后由统一分发器按每个用户的**个人通知配置**选择渠道，而非使用提醒记录上自带的渠道字段。站内实时推送走 WebSocket，历史通知写入 `notification` 表供前端轮询与中心页展示。

## 渠道注册表

渠道的权威定义由后端注册表与前端常量共同维护，二者 id 一一对应，是分发与配置的唯一事实来源。

### 后端权威常量源

`项目文件/backend/app/core/channel_registry.py` 是推送渠道的唯一权威常量源：

- `ChannelDef`（frozen dataclass）：包含 `id`、`label`、`config_keys`。
- `ALL_CHANNELS`：定义四个渠道，`websocket`（站内通知）、`feishu`（飞书 Webhook）、`email`（SMTP）、`wecom`（企业微信 Webhook）。
- `DEFAULT_CHANNELS = ["websocket"]`：默认仅站内通知。
- `CHANNEL_MAP` / `VALID_CHANNEL_IDS` / `get_channel()` / `get_all_channel_ids()`：供配置校验与查询。

各渠道实现位于 `backend/app/services/notification/` 目录，均继承 `base.py` 中的 `NotificationChannel` 抽象基类：

| 文件 | 渠道类 | 发送方式 |
| --- | --- | --- |
| `websocket_channel.py` | `WebSocketChannel` | 通过 `core/websocket.py` 的 manager 推送 |
| `feishu_channel.py` | `FeishuChannel` | Webhook 机器人 |
| `wecom_channel.py` | `WeComChannel` | Webhook 机器人 |
| `email_channel.py` | `EmailChannel` | SMTP |
| `dingtalk_channel.py` | `DingTalkChannel` | Webhook 机器人 |

### 前端渠道常量

`frontend/src/constants/channels.ts` 提供与后端一一对应的前端常量：

- `NOTIFICATION_CHANNELS`：四个渠道的 id 与中文标签。
- `CHANNEL_OPTIONS`：渠道选项数组，供表单下拉框渲染。
- `CHANNEL_TAG_MAP`：id 到标签的映射，用于 Tag 展示。
- `DEFAULT_CHANNELS`：默认渠道。

前后端各维护一份常量源，增删渠道需同步修改 `core/channel_registry.py` 与 `constants/channels.ts`。

## 分发器

`项目文件/backend/app/services/notification/dispatcher.py` 的 `dispatch_reminder(db, reminder)` 实现按用户分发：

- `_get_user_channels(db, user_id)` 读取 `UserNotificationConfig` 的 `enabled_channels`，并将 `websocket` 始终隐式置于首位。即"站内通知不可关闭，外部渠道按个人配置"。
- 对每个目标用户逐一取出渠道，按渠道构造对应的 Channel 实例并调用 `channel.send(user_ids, title, content)`。
- 分发依据是**用户的个人通知配置**（`user_notification_config` 表），而非 reminder 记录上的 `channels` 字段。
- 返回 `{ "user_id:channel_id": success_bool }` 字典，供调用方决定提醒状态。

## WebSocket 实时推送

站内实时通知以 WebSocket 承载，由连接管理、端点认证与心跳保活三部分组成，保证在线用户即时收到消息。

### 连接管理

`项目文件/backend/app/core/websocket.py` 定义 `ConnectionManager`：

- `connect(user_id, websocket)`：接受连接并按 `user_id` 绑定；同一用户已有连接时先关闭旧连接，保证单点在线。
- `disconnect(user_id)`：移除连接。
- `send_to_user(user_id, message)`：向指定用户发送 JSON；发送异常时主动断开。
- `broadcast(message)`：向所有在线用户广播。
- 模块级单例 `manager` 供全局复用。

### 认证与心跳

`项目文件/backend/app/api/ws.py` 的 `websocket_endpoint` 暴露 `/ws` 端点：

- 认证：通过 query 参数 `token` 传入 JWT，服务端用 `settings.SECRET_KEY` 解码并校验 `sub` 为合法 UUID，失败则以 `4001` 关闭。
- 握手成功后发送 `{"type": "connected"}`。
- 心跳：客户端每 30 秒发送 `"ping"`，服务端回复 `"pong"`（`frontend/src/hooks/useWebSocket.ts`），连接断开后前端 3 秒自动重连。

## 定时提醒链路

- 数据模型：`app/models/reminder.py`，`Reminder` 含 `title`、`content`、`trigger_time`、`target_users`、`status`（PENDING / SENT / FAILED 等）、`creator_id`。
- 定时任务：`app/tasks/reminder.py` 的 `check_due_reminders`（Celery `shared_task`），由 `app/tasks/__init__.py` 中 `celery_app.conf.beat_schedule` 的 `check-due-reminders` 条目调度（周期 10 秒）。
- 扫描逻辑：`_check_due_reminders_async` 查询 `status == PENDING` 且 `trigger_time <= now` 的提醒，逐个调用 `dispatch_reminder`；全部渠道成功或部分成功均置为 `SENT`，全部失败置为 `FAILED`。

## 日历事件提醒链路

- 数据模型：`app/models/calendar_event.py` 的 `CalendarEvent` 含三个提醒字段：`reminder_enabled`（是否启用）、`reminder_minutes`（提前多少分钟）、`reminded`（是否已发送过，用于幂等去重）。
- 定时任务：`app/tasks/calendar_reminder.py` 的 `check_calendar_reminders`（Celery `shared_task`），beat_schedule 的 `check-calendar-reminders` 条目周期 10 秒执行（源码注释描述为每分钟扫描一次）。
- 扫描逻辑：查询 `reminder_enabled == True` 且 `reminded == False` 的事件，计算 `reminder_time = start_time - timedelta(minutes=reminder_minutes)`；未到提醒时间跳过，事件已开始则仅标记 `reminded = True`，否则通过 `WebSocketChannel` 推送并置 `reminded = True`。

## 通知持久化

- 数据模型：`app/models/notification.py` 的 `Notification`（`__tablename__ = "notification"`），字段含 `user_id`、`message`、`type`（info / reminder 等）、`read`、`created_at`。
- WebSocket 渠道在 `dispatcher.dispatch_reminder` 中分发时同步 `db.add(Notification(...))` 落库，保证离线用户也能在中心页看到。
- CRUD：`app/api/notifications.py` 提供：
  - `GET /notifications/` 分页查询（`list_notifications_endpoint`，支持 `unread_only`）。
  - `PUT /notifications/{notification_id}/read` 单条已读（`mark_as_read_endpoint`）。
  - `PUT /notifications/read-all` 全部已读（`mark_all_as_read_endpoint`）。
- 业务逻辑位于 `app/services/notification_crud.py`，均以 `current_user.id` 限定操作范围。

## 前端呈现

前端呈现分三层：实时 Hook 维持连接与状态，铃铛组件提供顶栏入口，通知中心与个人配置页承载完整功能。

### 实时推送 Hook

`frontend/src/hooks/useWebSocket.ts` 的 `useWebSocket()`：

- 建立 WebSocket 连接并发送 30 秒心跳，解析 `type === "notification"` 消息，与 15 秒轮询的历史通知做去重合并。
- 提供 `markAsRead` / `markAllAsRead` / `unreadCount`。
- 额外处理 `room_kicked` 消息（直播间被踢场景）。

### 通知铃铛

`frontend/src/components/NotificationBell.tsx`：顶栏 `Badge`（`unreadCount`）+ 铃铛图标，点击展开 Dropdown 展示最近 10 条通知，提供"全部已读"与"查看全部"入口，点击通知按标题关键字跳转 `/votes`、`/forms`、`/announcements` 等页面。`layouts/MainLayout.tsx` 中挂载。

### 通知中心

`frontend/src/pages/notifications/NotificationsCenter.tsx`：`/notifications` 路由的完整通知列表页，支持已读/未读标记。

### 个人通知配置页

- 前端：`frontend/src/pages/settings/UserNotificationConfig.tsx`，路由 `/settings/notifications`，每用户独立配置启用的渠道、飞书/企微 Webhook 地址、SMTP 参数。
- 后端：`app/api/user_notification_config.py`（挂载于 `/auth` 前缀）与 `app/models/user_notification_config.py`（`UserNotificationConfig`，`user_id` 唯一），字段包括 `enabled_channels`（JSONB）、`feishu_webhook_url`、`wecom_webhook_url`、`email_enabled`、`smtp_host`、`smtp_port`、`smtp_user`、`smtp_password`、`smtp_use_tls`。

## 安全约束

- WebSocket 必须携带有效 JWT，失败即关闭连接（code 4001）。
- 通知的查询与已读操作均绑定 `current_user.id`，不能跨用户操作。
- 渠道 Webhook 地址与 SMTP 密码存储于用户个人配置，仅本人可读写。
- 站内通知始终隐式启用，不可被配置关闭，保证关键提醒可达。
