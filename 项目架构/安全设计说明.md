# 安全设计说明

## 概述

本系统为面向小团队的内网协作平台，安全设计遵循《项目基定/开发基准文档.md》第四章的安全基准。整体安全策略围绕四条主线展开：账号凭证安全（bcrypt 密码哈希）、会话安全（JWT + 刷新 + 会话撤销）、数据安全（密钥分区 AES-256-GCM、导出数据 PBKDF2 二次加密）以及可审计性（审计日志只增不改不删）。

系统面向 20 人规模的内网环境，威胁模型以内网误操作、共享机器上的凭证窃取、导出文件泄露为主要场景，因此安全设计偏向"默认最小权限 + 关键操作二次验证"。

## 密钥派生体系

系统存在两套独立的密钥派生/加密体系，分别服务导出数据与密钥分区，二者算法与密钥来源互不共享。下文分别说明。

### 导出密钥派生（PBKDF2 + Pepper + Salt）

全量数据导出采用 PBKDF2 派生加密密钥，核心逻辑位于 `项目文件/backend/app/services/data_export.py`。

- `derive_key(passphrase, pepper, salt)`：将用户密码短语与服务端 pepper 拼接后，执行 `hashlib.pbkdf2_hmac("sha256", combined, salt, 600000, dklen=32)`，得到 32 字节的 AES-256 密钥。迭代次数为 600000，兼顾暴力破解成本与导出耗时。
- Pepper 管理：`get_or_create_pepper(db)` 从 `system_config` 表读取 `data_export_pepper` 配置项，不存在时由 `os.urandom(32)` 生成 32 字节随机值并以十六进制存储。Pepper 不随导出文件分发，始终留在服务端，构成服务端持有的秘密要素。
- Salt 管理：每次导出由 `os.urandom(32)` 生成随机 salt，通过响应头 `X-Export-Salt` 独立于 ZIP 返回给客户端（见 `api/data_export.py` 的 `download_export_endpoint`）。

因此，解密一份导出数据需要同时持有四要素：ZIP 文件本身、导出时生成的 salt、用户设定的密码短语、服务端 pepper。该设计避免了"鸡生蛋"问题（salt 不加密进 ZIP），也确保即使 ZIP 文件泄露，无密码短语与服务端 pepper 也无法解密。

### 密钥分区加密（AES-256-GCM）

密钥保险箱模块使用 `项目文件/backend/app/core/encryption.py`：

- `generate_key()`：生成 32 字节 hex 编码的随机主密钥。
- `encrypt_data(data, key)`：使用 AESGCM 对 JSON 序列化数据加密，输出格式为 `nonce(12字节) + ciphertext + tag(16字节)`。
- `decrypt_data(encrypted, key)`：按 `nonce + ciphertext + tag` 结构解密，密钥错误或数据损坏时抛出 `InvalidTag`。

GCM 模式同时提供机密性与完整性校验，适用于密钥值这类不允许被篡改的敏感数据。

## 密码存储策略

用户密码采用 bcrypt 哈希存储，逻辑位于 `项目文件/backend/app/core/security.py`：

- `hash_password(password)`：使用 `bcrypt.gensalt()` 生成随机盐并哈希，盐值内嵌于哈希串中，无需单独存储。
- `verify_password(plain_password, hashed_password)`：使用 `bcrypt.checkpw` 校验。
- `validate_password_strength(password)`：强制密码长度不小于 8 位且同时包含字母与数字。

密码哈希以 `password_hash` 字段存储于 `user` 表（`app/models/user.py`），数据库中永不保存明文密码。

## 会话与认证设计

会话层由 JWT 双令牌、jti 会话撤销与 FastAPI 依赖链三部分协作构成。本节按三层分别说明。

### JWT 双令牌机制

认证基于 JWT，相关函数均在 `core/security.py`：

- `create_access_token(user_id, role)`：生成 access_token，有效期 30 分钟（`settings.ACCESS_TOKEN_EXPIRE_MINUTES`），payload 包含 `sub`（用户 ID）、`role`、`type: "access"`、`jti`（每次登录唯一）与 `exp`。
- `create_refresh_token(user_id)`：生成 refresh_token，有效期 7 天（`settings.REFRESH_TOKEN_EXPIRE_DAYS`），payload 包含 `type: "refresh"`。
- `decode_token(token)`：统一校验签名与过期时间，算法固定为 HS256。

### jti 会话撤销机制

`app/models/user_session.py` 定义 `UserSession` 模型，每次登录创建一条会话记录，`jti` 字段唯一标识该会话。认证依赖 `app/core/deps.py` 的 `get_current_user` 在每次请求时查询 `UserSession` 中是否存在与当前 token 的 `jti` 匹配且 `is_revoked == True` 的记录，命中则直接返回 401"会话已被撤销"。该机制支撑了设备终端管理与登出后的立即失效（`api/user_sessions.py` 提供会话列表与撤销端点）。

### 认证依赖链

`deps.py` 提供三个核心依赖：

- `get_current_user`：从 Authorization header 解析 Bearer token，校验签名、jti 黑名单、用户存在性，返回 `User`。
- `get_current_user_optional`：无 token 时返回 `None` 而非 401，用于公开接口的渐进式鉴权。
- `require_role(*roles)` / `require_admin`：角色检查依赖工厂，不满足时返回 403。

## 传输安全

全站强制 HTTPS。浏览器到 Nginx 之间由 Nginx 终止 TLS（内网使用自签名证书或穿透层 TLS，见 `项目文件/nginx/` 配置）。Nginx 将 `/api` 反向代理至 FastAPI 后端，前端静态资源与 API 同源，避免混合内容问题。WebSocket 连接使用 `wss://` 协议（`frontend/src/hooks/useWebSocket.ts` 根据页面协议自动选择 `wss:` 或 `ws:`）。

## 密钥保险箱安全

- 存储：密钥值经 AES-256-GCM 加密后落库，`secret` 表不保存明文。
- 访问控制：密钥模块强制私有，仅所有者可见（详见 [权限模型设计](./权限模型设计.md)）。
- 查看验证：查看或复制密钥值前必须二次输入登录密码。后端提供 `POST /auth/verify-password`（`api/auth.py` 的 `verify_password_endpoint`），前端 `api/secrets.ts` 的 `verifyPassword` 调用该接口；导入数据迁转等危险操作同样复用该验证（见 [数据导入导出设计](./数据导入导出设计.md)）。

## 闲置超时登出

前端通过 `frontend/src/hooks/useIdleTimer.ts` 实现闲置登出：

- `IDLE_TIMEOUT_MS = 5 * 60 * 1000`，即 5 分钟无操作。
- 监听 `mousemove`、`keydown`、`click`、`scroll`、`touchstart` 事件重置计时器。
- 超时后 `handleLogout` 依次执行：`clearTokens()`（清除 localStorage 中的 access/refresh token）、`sessionStorage.clear()`、调用 `POST /auth/logout` 通知后端，最后 `window.location.replace('/login')` 强制跳转登录页。

该 hook 由 `layouts/MainLayout.tsx` 挂载，覆盖所有登录态页面。

## 导出安全

导出数据的安全性分两层（详见 [数据导入导出设计](./数据导入导出设计.md)）：

1. 第一层：管理员设定导出密码短语。
2. 第二层：服务端使用 `PBKDF2(passphrase + pepper, random_salt, 600000)` 派生 AES-256 密钥，配合 `pyzipper` 的 WZ_AES 256 位加密对 ZIP 整体加密（`data_export.py` 的 `export_all` 中 `pyzipper.AESZipFile` + `setencryption(pyzipper.WZ_AES, nbits=256)`）。

双层加密保证即使导出文件被直接获取，未持有密码短语也无法解压查看。

## 审计日志

审计日志表 `audit_log` 由迁移文件 `backend/alembic/versions/002_p1_tables.py` 与 `005_p4_indexes.py` 创建，遵循"只增不改不删"原则：

- 只允许 INSERT，不允许 UPDATE / DELETE（数据库层面不提供修改入口）。
- 记录操作人、时间、操作类型、操作对象、IP 及变更前后 diff 等信息。
- 管理员可查看全部日志，普通成员仅能查看自身相关日志。

该约束保证任何敏感操作（登录、删除、权限变更、查看密钥等）都有不可抵赖的追溯记录。

## 安全约束汇总

| 项目 | 约束 |
| --- | --- |
| 密码 | bcrypt 哈希；≥8 位且含字母+数字 |
| 导出密钥派生 | PBKDF2-HMAC-SHA256，600000 次迭代，32 字节密钥 |
| Pepper | `system_config.data_export_pepper`，`os.urandom(32)` 生成，服务端持有 |
| 密钥分区 | AES-256-GCM，nonce 12 字节 + ciphertext + tag |
| 会话 | access_token 30 分钟 + refresh_token 7 天；jti 唯一标识可撤销 |
| 传输 | 全站 HTTPS / WSS |
| 闲置超时 | 前端 5 分钟无操作自动登出 |
| 导出 | pyzipper WZ_AES 256 位 + PBKDF2 派生密钥 |
| 审计日志 | 只增不改不删 |
