# 安全设计说明

## 概述

本系统为面向小团队的内网协作平台，安全设计遵循《项目基定/开发基准文档.md》第四章的安全基准。整体安全策略围绕四条主线展开：账号凭证安全（bcrypt 密码哈希）、会话安全（JWT + 刷新 + 会话撤销）、数据安全（密钥分区 AES-256-GCM、导出数据 PBKDF2 二次加密）以及可审计性（审计日志只增不改不删）。

系统面向 20 人规模的内网环境，威胁模型以内网误操作、共享机器上的凭证窃取、导出文件泄露为主要场景，因此安全设计偏向"默认最小权限 + 关键操作二次验证"。

## 密钥派生体系

系统存在两套独立的密钥派生/加密体系，分别服务导出数据与密钥分区，二者算法与密钥来源互不共享。下文分别说明。

### 导出密钥派生（PBKDF2 + Pepper + Salt）

全量数据导出采用 PBKDF2 派生加密密钥，核心逻辑位于 `项目文件/backend/app/services/data_export.py`。

- `derive_key(passphrase, pepper, salt)`：将用户密码短语与服务端 pepper 拼接后，执行 `hashlib.pbkdf2_hmac("sha256", combined, salt, 600000, dklen=32)`，得到 32 字节的 AES-256 密钥。迭代次数为 600000，兼顾暴力破解成本与导出耗时。
- Pepper 管理：`get_or_create_pepper(db)` 从 `system_config` 表读取 `data_export_pepper` 配置项，不存在时由 `os.urandom(32)` 生成 32 字节随机值并以十六进制存储。Pepper 不随导出文件分发，始终留在服务端，构成服务端持有的秘密要素。
- Salt 管理：每次导出由 `os.urandom(32)` 生成随机 salt，通过响应头 `X-Export-Salt` 独立于 ZIP 返回给客户端（见 `api/data_export.py` 的 `download_export_endpoint`）。

因此，解密一份导出数据需要同时持有四要素：ZIP 文件本身、导出时生成的 salt、用户设定的密码短语、服务端 pepper。该设计避免了"鸡生蛋"问题（salt 不加密进 ZIP），也确保即使 ZIP 文件泄露，无密码短语与服务端 pepper 也无法解密。

### 密钥分区加密（AES-256-GCM）

密钥保险箱模块使用 `项目文件/backend/app/core/encryption.py`：

- `generate_key()`：生成 32 字节 hex 编码的随机主密钥。
- `encrypt_data(data, key)`：使用 AESGCM 对 JSON 序列化数据加密，输出格式为 `nonce(12字节) + ciphertext + tag(16字节)`。
- `decrypt_data(encrypted, key)`：按 `nonce + ciphertext + tag` 结构解密，密钥错误或数据损坏时抛出 `InvalidTag`。

GCM 模式同时提供机密性与完整性校验，适用于密钥值这类不允许被篡改的敏感数据。

## 密码存储策略

用户密码采用 bcrypt 哈希存储，逻辑位于 `项目文件/backend/app/core/security.py`：

- `hash_password(password)`：使用 `bcrypt.gensalt()` 生成随机盐并哈希，盐值内嵌于哈希串中，无需单独存储。
- `verify_password(plain_password, hashed_password)`：使用 `bcrypt.checkpw` 校验。
- `validate_password_strength(password)`：强制密码长度不小于 8 位且同时包含字母与数字。

密码哈希以 `password_hash` 字段存储于 `user` 表（`app/models/user.py`），数据库中永不保存明文密码。

## 会话与认证设计

会话层由 JWT 双令牌、jti 会话撤销与 FastAPI 依赖链三部分协作构成。本节按三层分别说明。

### JWT 双令牌机制

认证基于 JWT，相关函数均在 `core/security.py`：

- `create_access_token(user_id, role, jti=None)`：生成 access_token，有效期 30 分钟（`settings.ACCESS_TOKEN_EXPIRE_MINUTES`），payload 包含 `sub`（用户 ID）、`role`、`type: "access"`、`jti` 与 `exp`。`jti` 缺省时自动生成新 UUID（首次登录）；传入既有 jti 时复用，使一次登录的多次凭证轮换始终对应同一条会话行。
- `create_refresh_token(user_id, jti)`：生成 refresh_token，有效期 7 天（`settings.REFRESH_TOKEN_EXPIRE_DAYS`），payload 包含 `type: "refresh"` 与它所属会话行的 `jti`。
- `decode_token(token)`：统一校验签名与过期时间，算法固定为 HS256。

### jti 会话撤销机制

`app/models/user_session.py` 定义 `UserSession` 模型，每次登录创建一条会话记录，`jti` 字段唯一标识该会话（唯一约束）。认证依赖 `app/core/deps.py` 的 `get_current_user` 在每次请求时查询 `UserSession` 中是否存在与当前 token 的 `jti` 匹配且 `is_revoked == True` 的记录，命中则直接返回 401"会话已被撤销"；`jti` 有值但查不到任何行时同样返回 401"会话已失效，请重新登录"——不能退回按 `sub` 查用户放行，否则登出与「仅允许一处登录」的强制下线都会被一次刷新绕过（见下一小节）。该机制支撑了设备终端管理与登出后的立即失效（`api/user_sessions.py` 提供会话列表与撤销端点）。

### 刷新令牌与会话行的绑定

一次登录 = 一条会话行 = 一个 jti。access_token 每 30 分钟过期，靠 refresh_token 续期；续期时必须复用原 jti，并且必须校验会话行仍存在且未撤销。

复用 jti 而不是新建会话行、也不是更新 `jti` 列，原因如下：

- 新建会话行会让一次登录变成 N 条行，设备终端管理列表与 F1 并发计数都会重复计；
- 更新 `jti` 列需要写库，且 `jti` 有唯一约束，轮换期间新旧令牌短暂共存会留下窗口；
- 复用 jti 零额外写，会话行仍是「一次登录」的唯一标识，登出与单设备下线按行生效即可覆盖整个令牌生命周期。

因此 `services/auth.py` 的 `refresh_access_token` 做三件事：拒绝不带 `jti` 的历史刷新令牌（401"请重新登录"）；按 `jti` 校验会话行存在且 `is_revoked == False`（否则 401"会话已失效，请重新登录"）；用同一 `jti` 换发新的 access_token 与 refresh_token。

缺这个校验的后果是真实存在的：旧实现里 `create_refresh_token` 不带 jti、`refresh_access_token` 不查会话行，被登出或被「仅允许一处登录」踢下的设备只要刷新一次就拿到新 jti 的 access_token，其 jti 在库里查不到，又被 `get_current_user` 的 `sub` 兜底放行——`is_revoked` 形同虚设，F1 的并发统计也同时失真。

### 认证依赖链

`deps.py` 提供三个核心依赖：

- `get_current_user`：从 Authorization header 解析 Bearer token，校验签名、jti 黑名单、用户存在性，返回 `User`。
- `get_current_user_optional`：无 token 时返回 `None` 而非 401，用于公开接口的渐进式鉴权。
- `require_role(*roles)` / `require_admin`：角色检查依赖工厂，不满足时返回 403。

### 会话活跃时间与并发窗口

`user_session.last_active_at` 记录该会话最后被使用的时间，由 `core/deps.py` 的 `get_current_user` 按请求刷新，节流间隔 `SESSION_ACTIVE_REFRESH_SECONDS = 60` 秒。并发登录提示（状态指示 F1）的「最近活跃的其他会话」窗口以 `COALESCE(last_active_at, created_at)` 为基准，长度 `CONCURRENT_RECENT_MINUTES = 30`。

这一刷新是必需的：模型上 `last_active_at` 声明了 `onupdate=func.now()`，但没有任何业务路径去 UPDATE 那一行，它会停在登录那一刻。若窗口以 `created_at` 为基准，登录满 30 分钟的标签页会被静默排除——会话仍在、令牌有效、页面仍在轮询，并发统计却再也看不到它，两个都开了半小时的连接因此互相认为对方不在线。

刷新按 60s 节流的原因：前端 F1 每 10s 轮询一次 `/me/concurrent`，若不节流，写会放大到每个请求一次。节流值必须明显小于 30 分钟的窗口，否则正在使用的标签页仍会被误判为已离开。

不做心跳包：WebSocket 的 30s ping 只能证明网络存活，浏览器被直接关闭时 TCP 连接不一定可靠断开，会话存活判断必须落在数据库上。

持久化依赖 `core/database.py` 的 `get_db` 在请求结束后统一 `commit`；刷新发生在依赖解析阶段、端点处理之前，随请求一起落库。

## 传输安全

全站强制 HTTPS。浏览器到 Nginx 之间由 Nginx 终止 TLS（内网使用自签名证书或穿透层 TLS，见 `项目文件/nginx/` 配置）。Nginx 将 `/api` 反向代理至 FastAPI 后端，前端静态资源与 API 同源，避免混合内容问题。WebSocket 连接使用 `wss://` 协议（`frontend/src/hooks/useWebSocket.ts` 根据页面协议自动选择 `wss:` 或 `ws:`）。

## 密钥保险箱安全

- 存储：密钥值经 AES-256-GCM 加密后落库，`secret` 表不保存明文。
- 访问控制：密钥模块强制私有，仅所有者可见（详见 [权限模型设计](./权限模型设计.md)）。
- 查看验证：查看或复制密钥值前必须二次输入登录密码。后端提供 `POST /auth/verify-password`（`api/auth.py` 的 `verify_password_endpoint`），前端 `api/secrets.ts` 的 `verifyPassword` 调用该接口；导入数据迁转等危险操作同样复用该验证（见 [数据导入导出设计](./数据导入导出设计.md)）。

## 闲置超时登出

前端通过 `frontend/src/hooks/useIdleTimer.ts` 实现闲置登出：

- `IDLE_TIMEOUT_MS = 5 * 60 * 1000`，即 5 分钟无操作。
- 监听 `mousemove`、`keydown`、`click`、`scroll`、`touchstart` 事件重置计时器。
- 超时后 `handleLock` **不退出登录**，而是锁定工作台（token 保留，供解锁时验证）——调用 `LockContext` 的 `lock()`，由 `pages/LockPage.tsx` 承接。

该 hook 由 `layouts/MainLayout.tsx` 挂载，覆盖所有登录态页面。

### 主动登出

真正退出登录只发生在用户主动操作时（右上角菜单「退出登录」、维护/调试模式的「退出登录」按钮），统一走 `frontend/src/utils/auth.ts` 的 `logout()`：

1. 携带当前令牌调用 `POST /api/v1/auth/logout`，服务端把本次会话的 `is_revoked` 置为 true；
2. `core/deps.py` 的 `get_current_user` 按 `jti` 反查撤销标记，该令牌后续请求立即被拦截（强制下线）；
3. 再 `clearTokens()` 清除本地令牌并跳转登录页。

第 1 步不可省略：若只清 localStorage 而 `is_revoked` 保持 false，该会话仍会被计入「其他在线会话」，并发登录提示（状态指示 F1）永不消失。撤销请求失败（如断网）时仍继续清本地令牌，保证用户不会被卡在无法登出的状态。

登出与撤销同时向该用户其余在线连接推送 `session_alert`（`core/websocket.py`），使 F1 提示立即消失而非等待下一个 10s 轮询周期。推送只是体验优化，失败不影响登出结果，详见 [状态指示设计规格](./状态指示设计规格.md) 的 5.1 节。

### 单设备登录策略

是否允许同一账号多处同时在线，由用户偏好 `user.preferences.allow_multiple_logins` 决定（布尔，缺省视为开启），在「安全设置 → 登录策略」中切换。

开关关闭时，新登录视为「替换式登录」：`services/auth.py` 的 `_enforce_single_device` 在本会话落库前把该用户全部未撤销会话置为 `is_revoked = True`，被下线设备的令牌因 `jti` 反查失败而立即失效。登录响应携带两个计数供前端提示：

- `other_session_count`：登录前该账号已有的其他会话数（不含本次）；
- `revoked_session_count`：本次因关闭该开关而被下线的会话数。

策略放在 `_issue_tokens` 而非路由层，因为普通登录、TOTP/恢复码二次验证、WebAuthn 二次验证三条路径都汇聚到此处，可在一个位置保证一致性。

存储与接口：

- 存储：复用 `user.preferences` 的 JSONB 列，无需新增表或列，不涉及迁移。
- 接口：`GET /api/v1/users/me/preferences` 返回该字段；`PUT` 接收 `allow_multiple_logins`（可空）。
- 可空的必要性：个性化页（缩放与主题）调用 `PUT` 时不传该字段，后端只合并实际传入的键。若把默认值写回，改一次页面缩放就会悄悄把单设备策略打开。
- 实现方式：直接改 ORM 属性并 `flag_modified`，而非拼 jsonb SQL——`text()` 里的 `:patch::jsonb` 会被 SQLAlchemy 识别为 PostgreSQL 类型转换符，导致 `:patch` 不被当作绑定参数，UPDATE 直接语法错误。

提示时机：登录成功后前端按 `revoked_session_count > 0` 显示「已按仅允许一处登录下线其他设备」，否则按 `other_session_count > 0` 显示「已在其他 N 个设备登录」。两个字段缺省按 0 处理，兼容旧后端响应。

## 导出安全

导出数据的安全性分两层（详见 [数据导入导出设计](./数据导入导出设计.md)）：

1. 第一层：管理员设定导出密码短语。
2. 第二层：服务端使用 `PBKDF2(passphrase + pepper, random_salt, 600000)` 派生 AES-256 密钥，配合 `pyzipper` 的 WZ_AES 256 位加密对 ZIP 整体加密（`data_export.py` 的 `export_all` 中 `pyzipper.AESZipFile` + `setencryption(pyzipper.WZ_AES, nbits=256)`）。

双层加密保证即使导出文件被直接获取，未持有密码短语也无法解压查看。

## 审计日志

审计日志表 `audit_log` 由迁移文件 `backend/alembic/versions/002_p1_tables.py` 与 `005_p4_indexes.py` 创建，遵循"只增不改不删"原则：

- 只允许 INSERT，不允许 UPDATE / DELETE（数据库层面不提供修改入口）。
- 记录操作人、时间、操作类型、操作对象、IP 及变更前后 diff 等信息。
- 管理员可查看全部日志，普通成员仅能查看自身相关日志。

该约束保证任何敏感操作（登录、删除、权限变更、查看密钥等）都有不可抵赖的追溯记录。


## WebAuthn（生物特征认证）

系统支持 WebAuthn 协议作为 2FA 的第二种验证方式（与 TOTP 认证器并列），使用户可通过指纹/面容/安全密钥完成二次验证。相关实现位于 `app/services/webauthn_service.py` 与 `app/api/webauthn.py`。

### 凭据存储

`user_webauthn_credential` 表存储每个用户已注册的 WebAuthn 凭据，字段包括：

- `credential_id`：base64url 编码的凭据 ID，唯一索引。
- `public_key`：base64url 编码的 COSE 格式公钥，用于服务端验证签名。
- `counter`：认证器计数器，防止重放攻击。
- `transports`：认证器传输方式（internal/usb/nfc）。

### 注册流程

1. `POST /auth/webauthn/register/start`：后端生成 challenge、rp 配置与 allowed credentials，返回给浏览器。
2. 浏览器调用 `navigator.credentials.create()` 完成硬件注册，返回 attestationObject 与 clientDataJSON。
3. `POST /auth/webauthn/register/finish`：后端验证 attestation statement（`webauthn.helpers.parse_registration_credential_json` + `parse_attestation_statement`），校验 origin 与 RP ID，存储凭据。

### 验证流程

1. `POST /auth/webauthn/authenticate/start`：后端生成 challenge 与 allowCredentials 列表（从数据库读取该用户所有凭据 ID）。
2. 浏览器调用 `navigator.credentials.get()` 完成生物特征验证，返回 assertion。
3. `POST /auth/webauthn/verify-lock`（锁定页）或 `POST /auth/webauthn/verify-login`（登录页）：后端使用 `webauthn.helpers.decode_credential_public_key` 解码公钥，根据 kty（EC2/OKP/RSA）构造 `cryptography` 库的公钥对象，调用 `verify_signature` 验证签名，更新计数器。

### 安全要点

- **Origin 校验**：注册与验证均校验 `client_data.origin` 是否匹配 `WEBAUTHN_ORIGIN` 配置，防止跨站攻击。
- **RP ID 校验**：验证时校验 `authenticator_data.rp_id_hash` 是否等于 `sha256(rp_id)`。
- **计数器校验**：每次验证后更新 `counter`，防止凭据被克隆重放。
- **密钥类型**：支持 EC2（P-256/P-384/P-521）、OKP（Ed25519）、RSA 三种 COSE 密钥类型。

## 安全约束汇总

| 项目 | 约束 |
| --- | --- |
| 密码 | bcrypt 哈希；≥8 位且含字母+数字 |
| 导出密钥派生 | PBKDF2-HMAC-SHA256，600000 次迭代，32 字节密钥 |
| Pepper | `system_config.data_export_pepper`，`os.urandom(32)` 生成，服务端持有 |
| 密钥分区 | AES-256-GCM，nonce 12 字节 + ciphertext + tag |
| 会话 | access_token 30 分钟 + refresh_token 7 天；jti 唯一标识可撤销 |
| 传输 | 全站 HTTPS / WSS |
| 闲置超时 | 前端 5 分钟无操作自动登出 |
| 导出 | pyzipper WZ_AES 256 位 + PBKDF2 派生密钥 |
| 审计日志 | 只增不改不删 |
