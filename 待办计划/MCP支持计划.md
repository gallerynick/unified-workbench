## 一、背景与目标

### 现状

- 集中式审计日志（`audit_log` 表）在迁移 `002_p1_tables.py` 中创建了表结构，但 ORM Model、Service、API、前端均未实现，是一张从未被使用的僵尸表

### 目标

- **Phase 1**：清理集中式审计日志的遗留物，完全转变到模块级日志模式
- **Phase 2**：设计 MCP 服务规格，明确身份模型、安全边界、工具契约
- **Phase 3**：实现 MCP 服务

## 三、Phase 2: MCP 设计规格

### 已确认的设计决策

| 决策点 | 结论 |
|--------|------|
| 身份模型 | **代用户模式**（MCP 持有用户 JWT，复用现有权限模型） |
| 安全边界 | 涉及密码/生物验证/二次验证的操作一律不允许；灰色地带（无密码但高风险）需二次确认 |
| MCP 日志 | 新增 `mcp_log` 表，记录 AI 操作，前端 MCP 页面展示 |
| 审计模式 | 模块级日志（各模块自己的业务记录），不建集中式审计 |

### 安全边界分类

**禁止操作（涉及密码/生物验证/二次验证）：**
- 查看/复制密钥值（`POST /auth/verify-password`）
- 开启/关闭 2FA
- WebAuthn 注册/认证
- 数据导出（需管理员密码短语）
- 数据导入（需验证密码）
- 数据重置（需管理员验证密码）

**需二次确认（灰色地带，无密码保护但风险高）：**
- 删除项目/删除内容
- 修改他人资源（如果用户有权限）
- 批量操作（群发通知、批量修改）
- 系统配置修改（管理员）

### 待设计

- MCP 服务架构（FastMCP 集成方式）
- 工具粒度（按模块 / 按能力 / 按端点）
- `mcp_log` 表结构
- 二次确认机制设计
