## 一、需求与范围

在「系统设置」下新增「资源监视」页，实时呈现运行环境的资源占用：

1. 各 CPU 核心的实时占用
2. 内存占用（含缓存/缓冲分层）
3. 压力分析（多维度 + 综合等级 + 成因）
4. 占用归因（系统级信号 + 本容器进程 Top N）
5. 可视化图表（趋势、拆分、罗列）

**硬约束**：所有组件与设计必须严格符合《UI设计规范.md》并保证全站风格统一。

## 二、监视范围决策（已定稿）

### 2.1 候选方案对比

| 方案 | 做法 | 归因能力 | 安全影响 | 结论 |
| --- | --- | --- | --- | --- |
| A | 容器内 `/proc` + `psutil` + cgroup | 系统级信号 + 本容器进程 Top N | 无（零特权） | **采用** |
| B | A + 挂载 `docker.sock` 查 Docker Engine API | 各服务分表 | 等于宿主机 root，首次越权口 | **不采用** |
| C | 宿主机侧车 agent | 宿主全量 | 无，但新增部署单元 | **不采用** |

### 2.2 关键事实依据

- 后端运行于 Docker 容器（`python:3.11-slim`，非 root 用户 `workbench`），`docker-compose.yml` 中**未挂载** `docker.sock`，全栈无 `privileged` / `cap_add` / `host_pid`
- `/proc/stat`、`/proc/meminfo`、`/proc/loadavg` **不隔命名空间**，容器内取到的是整机真实值，故每核心 / 内存 / 负载零特权可取
- `/sys/fs/cgroup` 非 root 可读，容器配额与限流零特权可取
- 进程级磁盘 IO 不可取：非 root 无法读取其他进程的 `/proc/<pid>/io`（内核限制）
- `api/status.py` 既有边界约定：运维指标不进用户界面，属管理员视角，落在系统设置页 —— 本功能位置符合既有约定

### 2.3 两个口径同时显示

| 口径 | 来源 | 展示位置 |
| --- | --- | --- |
| 运行环境 | `/proc` | 概览卡 + 全部趋势图（主视角） |
| 本容器配额 | `/sys/fs/cgroup`（v2 主路径，v1 兜底） | 独立卡片，与运行环境并排显示 |

两个口径同时可见，不做切换开关。

## 三、后端设计

### 3.1 新增依赖

`psutil>=5.9`（纯 Python wheel，`Dockerfile` 无需改动）。

### 3.2 模块划分

| 文件 | 职责 |
| --- | --- |
| `app/services/monitor/metrics.py` | 纯函数：压力计算、cgroup 解析、历史降采样。**不依赖 psutil**，便于单测 |
| `app/services/monitor/sampler.py` | 采样器单例 + 环形缓冲 + psutil 采集 |
| `app/schemas/monitor.py` | Pydantic 响应模型（自动生成 OpenAPI） |
| `app/api/monitor.py` | 单端点，`require_admin` |
| `app/tests/test_monitor_metrics.py` | 纯函数单测 |

### 3.3 采样架构

- 进程内单例，由 `app.main.lifespan` 启动时拉起、关闭时取消
- 间隔 1 秒；同步采集包进 `asyncio.to_thread()`，不阻塞事件循环
- 历史为内存环形缓冲 `deque(maxlen=600)`，即 **10 分钟**
- **不落库**：资源指标是瞬时态，持久化既无审计价值，也会与「审计日志只增不改不删」的语义混淆。故**无 alembic 迁移**
- 启动时**预热**：`psutil.cpu_percent()` 首次调用必然返回 0，不预热则首条数据失真；进程对象同样需跨采样复用以取到真实 CPU 差值
- 磁盘/网络为累计计数器，后端算好**速率**（bytes/s、ops/s）再下发，前端不做差值

### 3.4 API 契约

`GET /api/v1/system/monitor?minutes=5&processes=20`

- 无尾斜杠，与 `/system/status`、`/system/check-update` 保持一致，符合《API路由尾部斜杠规范.md》
- 鉴权：`require_admin`（普通成员 403）
- `minutes` 默认 5，上限 10（受环形缓冲 10 分钟限制）
- `processes` 默认 20，上限 50
- 统一响应 `{ code, msg, data }`

`data` 结构：

- `host`：运行环境 —— `cores`、`cpu`（total / per_core / breakdown）、`memory`（total / used / cached / buffers / free / available / used_percent）、`swap`、`load`（1/5/15）、`disk` 速率、`net` 速率
- `container`：本容器 —— `cpu`（has_limit / quota_cores / used_cores / used_percent / throttled_count / throttled_seconds）、`memory`（has_limit / limit / current / used_percent / oom_kill_count / max_events）
- `pressure`：`index`、`level`、`level_label`、`dimensions[]`、`causes[]`
- `processes`：`CPU Top10 与 内存 Top10 的并集`，去重后按 CPU 降序，最多 20 条。避免「只按 CPU 排序导致高内存进程永远不可见」
- `history`：并行数组（`t` / `cpu_total` / `cpu_user` / `cpu_system` / `cpu_iowait` / `memory_used_percent` / `memory_cached_percent` / `memory_buffers_percent` / `memory_free_percent` / `load1` / `load5` / `load15` / `disk_read_bps` / `disk_write_bps` / `net_sent_bps` / `net_recv_bps`），超过 300 点时等距降采样并保留首尾两点
- `meta`：`in_container`、`platform`、`machine`、`sample_interval_seconds`、`history_seconds`

### 3.5 压力规则（写死，不做玄学）

| 维度 | 公式 |
| --- | --- |
| CPU | `max(cpu_total, iowait)` —— iowait 是 CPU 忙于等 IO，同样算压力 |
| 内存 | `(total - available) / total × 100` —— `available` 已排除可回收缓存 |
| 负载 | `load1 / 核心数 × 100` —— 1.0 即每核满载 |
| 交换 | swap 已用占比（无 swap 时不列为维度） |

- 综合压力 = 各维度**取最严重**，并返回触发项名称作为成因
- 等级：`<60 正常 / 60–80 偏高 / 80–95 紧张 / >95 过载`
- 容器限流单独作为 note 展示，**不计入**综合指数 —— 它是「原因」不是「总量」

## 四、前端设计

### 4.1 新增文件

| 文件 | 职责 |
| --- | --- |
| `src/hooks/useChartColors.ts` | 图表取色（token 解析，深浅色自适应） |
| `src/api/system-monitor.ts` | API 封装与类型 |
| `src/pages/settings/ResourceMonitor.tsx` | 页面 + 内联子组件（沿用 `FormResponses.tsx` 先例） |
| `src/pages/settings/ResourceMonitor.module.css` | 页面样式 |
| `src/router.tsx` | 懒加载 + `settings/monitor` 路由 |
| `src/layouts/MainLayout.tsx` | 系统设置菜单项，图标 `DashboardOutlined` |
| `src/config/routeTitles.ts` | 面包屑标题 |

**命名用「资源监视」**，不用「服务器监控」：`/servers` 服务器管理在本项目是静态台账（hostname / IP / 硬件规格），叫「服务器监控」会与它混淆。

### 4.2 页面结构（自上而下）

参照 macOS 活动监视器 CPU 标签页的信息层级：

1. **页头** —— `Title level={4}`「资源监视」
2. **概览卡 ×4**（运行环境）—— CPU 总占用 / 内存 / 负载 / 磁盘与网络
3. **压力分析面板** —— 综合压力环 + 四维度条 + 成因 `Alert`
4. **运行环境与容器配额** —— 两列并排：左为运行环境标识，右为本容器配额 / 限流 / OOM
5. **CPU 使用率** —— 环形图按 5 段拆分（使用者 / 系统 / I/O 等待 / 虚拟化 / 闲置）+ 图例数值，macOS 同构
6. **CPU 使用率趋势** —— 单系列面积图（不再按核分线，从源头消除色循环）
7. **各核心占用** —— 下方罗列，每核一条水平条（核心号 + 进度条 + 百分比）
8. **内存使用率** —— 分层面积图（已用 / 缓存 / 缓冲 / 空闲）
9. **系统负载** —— load1/5/15 折线 + 核心数参考线
10. **磁盘与网络 IO** —— 磁盘读写 + 网络收发速率
11. **进程占用** —— Top 进程表（PID / 进程名 / 用户 / 状态 / CPU% / 内存 / 占比），客户端可排序

### 4.3 各核心显示：单一渲染路径

**不做任何核数分支**。用 CSS 自适应网格：

`grid-template-columns: repeat(auto-fill, minmax(280px, 1fr))`

- 2 核自然铺成两列，16 / 64 核自动折成多列
- 容器 `max-height` + 垂直滚动，任意核数都不撑高页面
- 条色按占用分三档：`<60%` 蓝 / `60–80%` 橙 / `>80%` 红 —— 仅需 3 档色，彻底消除 12 色调色板色循环问题

### 4.4 轮询

- 2 秒轮询（沿用 `StatusIndicator` 轮询范式，不新增 WebSocket / SSE）
- `visibilitychange`：标签页不可见时暂停，避免后台空转
- `useEffect` + `cancelled` 标志防卸载后 setState（沿用 `StorageSettings.tsx` 范式）

### 5.1 三处取舍记录

1. **卡片 8px 而非 18px** —— 见上表，以 token.css 组件级 token 与全站既有页面为准。
2. **图表配色来源** —— `FormResponses.tsx` 的 `CHART_COLORS` 硬编码 hex 与 AGENTS.md「不得新增硬编码 hex 色值」冲突。改为沿用 `pages/notes/GraphView.tsx` 已确立的 `resolveCssVar` 模式（运行时 `getComputedStyle` 解析，随 `isDark` 重算），抽为共享 `useChartColors`。不改动 GraphView 与 FormResponses。
3. **「紧张」级状态色** —— success / warning / error / info 均有深色变体，`--color-orange` 无深色变体。沿用 `--color-orange` 并在深浅色下实测对比度；标签用 `<Tag>` + token 取色，不引入 antd 预设色板（避免第二套色源）。

## 六、已知边界（页面如实标注，不装作全能）

1. **macOS / Windows Docker Desktop 上「运行环境」= Docker VM**，不是物理机。后端返回 `in_container: true` 与机器标识，前端文案按「运行环境」表述。
2. **当前 compose 未给后端设资源限制**，容器卡片会显示「未设配额」+ 绝对占用值而非占比。想要配额占比需自行在 compose 加 `deploy.resources.limits` —— 不在本次范围，卡片上留提示。
3. **不做进程级磁盘 IO**：非 root 读不了他人的 `/proc/<pid>/io`（内核限制），磁盘只看聚合值。
4. **进程列表只有本容器内的进程**（bridge 网络下看不到其他容器的进程），页面写明范围。

## 七、非目标

服务级统计（需 docker.sock）/ 进程 kill 等操作能力（监视 ≠ 控制，越权风险）/ 历史持久化 / 告警推送 / 多主机聚合 / 移动端适配深化。
