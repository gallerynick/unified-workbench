### 2.2 本地 AI 替换：Ollama → llama.cpp

#### 2.2.1 结论与依据

**Ollama 本质是 llama.cpp + Go 封装 + GPU 兼容包。** 其镜像内 `/usr/lib/ollama` 含
`libllama.so` / `libggml.so` / `LLAMA_CPP_VENDORS_LICENSE`。
换成 llama.cpp **不损失任何 CPU 推理能力**，只剥离封装层与显卡包。

选用镜像：`ghcr.io/ggml-org/llama.cpp:server`（官方维护）
- 支持 `linux/arm64`
- **纯 CPU，零 GPU 库**
- 仅含 `llama-server` 单一可执行文件
- 层实测：27.6 + 243.6 + 12.5 = **283.7 MB（压缩）**

#### 2.2.2 体积对比

| 指标 | Ollama | llama.cpp server | 实测/预估 |
|------|--------|-----------------|----------|
| 镜像压缩包 | 2.79 GB | 297 MB | 实测 |
| 镜像磁盘占用 | 6.99 GB | **1.18 GB** | 实测（预估 0.7 GB 偏低） |
| 其中 GPU 库 | 3.55 GB | **0** | 实测 |
| 模型权重（3B Q4） | 1.93 GB | **2.10 GB** | 实测（GGUF 略大于 Ollama blob） |
| **本地 AI 合计** | **8.92 GB** | **3.28 GB** | 实测 |

**净省 5.64 GB**（原预估 6.3 GB，差额来自镜像 1.18 而非 0.7、GGUF 2.10 而非 1.9）。

#### 2.2.3 服务定义（router 模式）

**关键：不指定 `-m` 模型参数，llama-server 即进入 router 模式，动态载入/卸载模型。**

```yaml
llama-cpp:
  image: ghcr.io/ggml-org/llama.cpp:server
  command: >
    --host 0.0.0.0 --port 8080
    --models-dir /models
    --models-max 1
    --sleep-idle-seconds 300
  volumes:
    - ./data/gguf:/models
  ports:
    - "8080:8080"
```

#### 2.2.4 能力替代 ①：查已加载模型（原 `GET /api/ps`）

`GET /models` 返回：

```json
{
  "data": [{
    "id": "Qwen2.5-3B-Instruct-Q4_K_M.gguf",
    "path": "/models/Qwen2.5-3B-Instruct-Q4_K_M.gguf",
    "status": { "value": "loaded", "args": ["llama-server", "-c", "8192"] }
  }]
}
```

`status.value` 状态机：`unloaded` / `loading` / `loaded` / `sleeping` / `downloading`

**状态映射（对齐现有前端三态）：**

| 前端状态 | llama.cpp 状态 | 语义 |
|---------|---------------|------|
| `not_downloaded` | 不在 `/models` 列表 | 未下载 |
| （新增）`downloading` | `downloading`（含 progress） | 下载中 |
| `downloaded` | `unloaded` / `sleeping` | 有文件，未占内存 |
| `ready` | `loaded` | 已载入内存 |

单模型模式（非 router）退化方案：
- `GET /health` → 200 `{"status":"ok"}` = 已就绪；503 `{"error":{"code":503,"message":"Loading model"}}` = 载入中
- `GET /props` → `model_path` + `is_sleeping`

#### 2.2.5 能力替代 ②：卸载释放内存（原 `keep_alive: 0`）

**手段 ①：显式卸载 API**

```
POST /models/unload
{ "model": "Qwen2.5-3B-Instruct-Q4_K_M.gguf" }
→ { "success": true }
```

现有 `unload_ai_model()` 打的是 `/api/generate` + `keep_alive: 0`（副作用式 hack），
换为显式 API。

**手段 ②：空闲自动休眠（Ollama 不具备）**

`--sleep-idle-seconds N`：空闲 N 秒后自动把模型与 KV cache 从内存卸载；
任何新请求自动触发重新载入。

**关键细节** —— 以下端点不触发重载、不重置空闲计时器：

`GET /health`、`GET /props`、`GET /models`、`GET /metrics`

**这消除了现有「状态轮询意外唤醒模型」的隐患，并原生实现了「模型自热备」语义。**

| 能力 | Ollama | llama.cpp |
|------|--------|-----------|
| 手动卸载 | `keep_alive:0`（副作用式） | `POST /models/unload` 显式 |
| 自动卸载 | 仅靠 keep_alive 计时 | `--sleep-idle-seconds` |
| 自动重载 | 有请求即载 | 有请求即载 |
| 卸载后状态可查 | `/api/ps` 变空 | `status.value` |
| 轮询是否唤醒 | 有风险 | **不会**（豁免端点） |

#### 2.2.6 能力替代 ③：模型下载管理（原 `ollama pull`）

**模型来源三选一：**
1. `LLAMA_CACHE` 缓存
2. `--models-dir ./models` 直接放 GGUF
3. **`--models-preset ./my-models.ini`（推荐，支持 `hf-repo` 直连 HuggingFace）**

```ini
version = 1

[*]
c = 8192
n-gpu-layers = 0

[Qwen2.5-3B-Instruct-Q4_K_M]
hf-repo = Qwen/Qwen2.5-3B-Instruct-GGUF:Q4_K_M
load-on-startup = false
```

两个 preset 专属选项直接对应现有需求：
- **`load-on-startup`** —— 「模型自热备」开关的原生实现
- `stop-timeout` —— 请求卸载后等待秒数，默认 10

**热加载（避开重启坑）：**
用 `-hf` 加缓存后须知「服务必须重启」；但 preset 不会 ——
`GET /models?reload=1` 会刷新模型列表，未运行的模型按来源新增或更新。

**进度与事件：**
- `GET /models` → `status.progress`
- `GET /models/sse` → 推 `model_status`（`loading`/`loaded`/`sleeping`）与 `model_remove` 事件

#### 2.2.7 完整 API 映射表

| 功能 | Ollama | llama.cpp router |
|------|--------|-----------------|
| 列模型 | `GET /api/tags` | `GET /models` |
| 查已载入 | `GET /api/ps` | `GET /models` → `status.value` |
| 载入 | 发请求隐式触发 | `POST /models/load` 显式 |
| 卸载 | `keep_alive:0` hack | `POST /models/unload` 显式 |
| 自动卸载 | ✗ | `--sleep-idle-seconds` |
| 下载 | `POST /api/pull` | preset `hf-repo` + `?reload=1` |
| 下载进度 | 自行解析 NDJSON | `status.progress` + `/models/sse` |
| 删除 | `DELETE /api/delete` | `POST /models/unload` + 删文件 |
| 对话 | `/v1/chat/completions` | `/v1/chat/completions`（完全一致） |
| 健康检查 | `GET /api/tags` | `GET /health`（更轻） |

### A.1 标点模型降配 — 潜在 853 MB

FunASR 别名表（`name_maps_from_hub.py`）中只有两个标点模型：

| （实时变体） | `punc_ct-transformer_zh-cn-common-vad_realtime-vocab272727` | 纯中文 | 275.4 MB | — |

**待决策点：是否存在中英混说场景？**
- 无 → 可换 `ct-punc-c`，省 853.5 MB

### A.2 ASR 引擎技术选型

| 方案 | 主模型 | 标点 | 模型总量 | 运行时依赖 |
|------|--------|------|---------|-----------|
| S0 现状 | seaco-paraformer | ct-punc-large | **3014 MB** | funasr + torch |
| S1 标点降配 | seaco-paraformer | ct-punc-c | 2159 MB | funasr + torch |
| S2 全 ONNX | paraformer-large-onnx 227 MB | ct-punc-c-onnx 270 MB | **525 MB** | funasr-onnx |
| **S3 SenseVoice ONNX** | SenseVoice-onnx 230 MB | **不需要** | **259 MB** | funasr-onnx |
| S4 sherpa-onnx | SenseVoice / paraformer | 内建 | 相近 | sherpa-onnx（C++） |
| S5 纯在线 ASR | — | — | 0 | httpx |

**S3 关键依据（已核实）：**
1. `iic/SenseVoiceSmall-onnx` = **230.04 MB**（`model_quant.onnx`）
2. 官方 README：`use_itn=True` 时「输出结果包含标点与逆文本正则化」—— **标点管线可整体取消**
3. `funasr-onnx` 源码含 `sensevoice_bin.py`，`__init__.py` 导出 `SenseVoiceSmall`
4. 同团队新一代模型，覆盖普通话/粤语/英语/日语/韩语，附带情感识别与音频事件检测
5. 缓存中已有其 PyTorch 版（原判为孤儿，现复用为生产模型），说明历史上评估过该路线

**S3 模型账：** SenseVoice 230 + fsmn-vad ONNX 0.5 + cam++ 28 = **258.5 MB**
