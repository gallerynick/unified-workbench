# 存储占用分模块统计实施计划

> 状态：**实施中**
> 创建日期：2026-09-30
> 关联：《开发基准文档》第4章（安全基准）、《项目基定/UI设计规范.md》
> 需求来源：管理员需要一个按模块/部分拆分的存储占用统计（本地模型、用户数据、文件共享、临时文件、应用文件、备份等）

---

## 一、需求与设计决定

### 1.1 需求

管理员视角的存储占用分布统计，按业务分类拆分：本地模型、用户数据、文件共享、
临时文件、应用文件、备份。

### 1.2 已确认的决定

| 决定 | 内容 |
|------|------|
| D1 测量机制 | **能统计的全统计，不能统计的归「其他」并加说明**。不引入宿主机采集器、不挂 Docker socket，全部在后端容器内完成 |
| D2 备份口径 | 程序已知 `FILE_BACKUPS_PATH`，读得到就计入；读不到（未配置/挂载缺失/网络盘断开）计 0 并注明原因。容器内不主观推断源路径是否为 NAS |
| D3 两个文件系统都计入 | 工作盘与 Docker 虚拟机卷都属工作台实际存储；「其他」给出真实数值，锚在 Docker 虚拟机卷已用空间 |
| D4 不做历史趋势 | 沿用 `app/api/monitor.py` 的边界约定：资源指标是瞬时态，不落库 |
| D5 不做清理动作 | 清理构建缓存/删旧备份属破坏性操作，另立需求 |

### 1.3 分类 → 数据源 → 精度

| 分类 | 数据源 | 精度 | 本机实测 |
|------|--------|------|---------|
| 本地模型 · Ollama | `GET http://ollama:11434/api/tags`，Σ `size` | exact | 1.93 GB |
| 本地模型 · ModelScope 缓存 | 遍历 `/home/workbench/.modelscope`（命名卷已挂进后端容器） | exact | 3.0 GB |
| 用户数据 · 数据库 | SQL `pg_database_size` | logical | 9.6 MB |
| 用户数据 · 缓存 | Redis `INFO memory` | logical | — |
| 文件共享 | 遍历 `/data/files` | exact | 565 MB |
| 备份 | 遍历 `FILE_BACKUPS_PATH`；不可达则 0 并标注 | exact | 0 B |
| 其他（不可分解） | `Docker 虚拟机卷已用 − 已归类的磁盘字节数` | residual | ≈18.1 GB |

**精度语义**：
- `exact` — 字节数来自实际磁盘统计或权威接口，可直接相加
- `logical` — 逻辑数据量，不含 WAL/索引膨胀等磁盘开销，不可与 exact 项混算精确总量
- `residual` — 残差值，为卷级已用空间扣除已归类项，包含非工作台资源，无法进一步分解

### 1.4 「临时文件」的处理（明确的方案边界）

应用自身临时目录（`tempfile.mkdtemp`，备份/导出/导入用）易失、随任务清理，且落在容器
overlay 层；真正的临时大头是 Docker 构建缓存（本机 7.97 GB，可回收 5.26 GB），但它在
Docker 守护进程侧，**应用容器内无 API 可读**（`docker builder du` / `docker system df`
是 CLI 专用）。因此「临时文件」不给独立数字，并入「其他」并在 `note` 中点名构建缓存与
`docker builder prune`。

### 1.5 两个文件系统的不对称处理

| 卷 | 是否归类 | 原因 |
|----|---------|------|
| Docker 虚拟机卷 | 是，归类并算残差 | Docker Desktop 为该部署专建的虚拟机，卷内资源基本都属工作台 |
| 工作盘（macOS 宿主） | 否，只展示容量 | 已用空间绝大部分是宿主机本身而非工作台；只取其中的 `files`/`backups` 精确计入 |

`files` 与 `backups` 住在工作盘，**不参与** Docker 卷残差计算，两个卷互不交叉。

## 二、API 契约

`GET /api/v1/system/storage-breakdown`

- 无尾斜杠（与 `/system/monitor`、`/system/status` 一致）
- `require_admin`
- 实时采样，不落库

响应结构（示例）：

- `generated_at` / `elapsed_ms` — 统计时间与耗时
- `categories[]` — 每项含 `key` `group` `name` `bytes` `source` `accuracy` `reachable` `counted`，可选 `path` `note` `anchor` `details`
- `measured_total_bytes` — 已计入分类之和（代表工作台整体占用）
- `disks[]` — 两个文件系统各自的 total/used/free 与测量路径

**容错约定**：每个采集器独立 `try/except`，单个失败只让该分类 `reachable: false`
（`counted: false`），不影响整体返回。

## 三、后端实现

| 文件 | 动作 | 内容 |
|------|------|------|
| `backend/app/schemas/storage.py` | 新增 | Pydantic 响应模型 |
| `backend/app/services/storage_breakdown.py` | 新增 | 分类采集器 + 目录遍历 + 残差计算 |
| `backend/app/api/storage.py` | 新增 | `GET /system/storage-breakdown` |
| `backend/app/api/router.py` | 修改 | 注册 storage_router |

### 关键实现要点

1. **目录遍历**：`os.scandir` 递归（快于 `os.walk`），`st_blocks * 512` 优先、`st_size` 兜底（贴近 `du` 语义）；经 `asyncio.to_thread` 执行，避免阻塞事件循环
2. **超时保护**：单个目录遍历上限 20s，超时返回已遍历部分并标注
3. **Ollama**：`httpx.AsyncClient` 调 `GET /api/tags`，30s 超时；Ollama 服务不可达时该分类 `reachable: false`，不影响其他分类
4. **数据库**：复用 `get_db` 注入的 `AsyncSession` 执行 `pg_database_size(current_database())`
5. **Redis**：`redis.asyncio.from_url` 取 `INFO memory` → `used_memory`
6. **残差计算**：`statvfs('/')` 取 Docker 虚拟机卷已用；减去已归类且确实住在该卷的 exact 项（Ollama + ModelScope）；结果为负时取 0 并标注

## 四、前端实现

| 文件 | 动作 | 内容 |
|------|------|------|
| `frontend/src/api/storage.ts` | 新增 | 类型定义 + `getStorageBreakdown()` |
| `frontend/src/pages/settings/StorageSettings.tsx` | 修改 | 新增「存储占用分布」区块 |
| `frontend/src/pages/settings/StorageSettings.module.css` | 修改 | 新增区块样式 |

### UI 组成

1. **环形图**（recharts Pie）— 各分类占比；「其他」为最大区块之一，直观提示大头在 Docker 侧
2. **明细表** — 分类 / 大小 / 占比 / 数据源与口径；`exact`·`logical`·`residual` 用 Tag 区分
3. **两块容量 Progress** — 工作盘、Docker 虚拟机卷，各自独立不求和
4. **说明区** — 「其他」的 `anchor` 与 `note`，含可复制的宿主机命令
5. 手动刷新 + 60s 自动刷新 + 上次统计时间与耗时

### 规范约束

- 禁止 Emoji 图标，使用 `@ant-design/icons`
- 深浅色模式双适配
- 颜色尺寸一律引用 `token.css` design token（`var(--token-name)`），无硬编码 hex
- 图表颜色经 `resolveCssVar` 解析为具体值（recharts 的 SVG attribute 无法解析 `var(...)`）

## 五、验收标准

1. `npx tsc -b` 零错误、`npm run build` 通过
2. 后端 `ruff check` 与 `mypy` 通过
3. 重建后 `GET /api/v1/system/storage-breakdown` 返回 200 且结构完整
4. 非管理员访问返回 403
5. 各分类数值与宿主机 `docker system df` / `du -sh` 实测相符（exact 项）
6. 深色/浅色模式均无样式破图，无硬编码色值

## 六、非目标

- 不做历史趋势与持久化
- 不做清理动作（清理构建缓存、删除旧备份）
- 不引入宿主机采集器、不挂 Docker socket
- 不给「其他」伪造更细的分解
