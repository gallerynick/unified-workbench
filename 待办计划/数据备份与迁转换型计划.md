## 二、设计

### 2.1 职责分工

| | 数据备份 | 数据迁转 |
|---|---|---|
| 用途 | 同机日常保险 | 跨机迁移 / 换机部署 |
| 数据范围 | DB + 文件（全量） | DB + 文件（全量） |
| 密钥来源 | 服务端自动派生（backup_pepper） | 用户输入 passphrase |
| 创建时人工介入 | 无 | 需要输入 passphrase |
| 恢复时人工介入 | 管理员密码（授权闸门，非解密密钥） | passphrase + salt |
| salt | 固定，服务端自持 | 随机，随包分发 |
| 版本要求 | 不校验（同机版本天然一致） | 必须同版本，否则拒绝 |
| 恢复前快照 | 自动 | 自动 |
| 完整性校验 | SHA256 写入 manifest，恢复前自动校验 | 沿用现有（pyzipper 自带） |

### 2.2 备份加密模型

- 新增 `backup_pepper` 存 `system_config` 表（首次使用时 `os.urandom(32)` 生成，与 `data_export_pepper` 同模式）
- 密钥派生：`key = PBKDF2("backup" + backup_pepper, fixed_salt, 600000)`，`fixed_salt` 为硬编码常量（不是秘密，不入库）
- 每次备份用同一密钥 → 任一备份均可被服务端解密
- 创建流程：pg_dump -Fc → 复制 FILE_STORAGE_PATH → 写 manifest（含 SHA256 校验和）→ pyzipper AES-256 打包 → `backup_YYYYMMDD_HHMMSS.zip`
- 恢复流程：`require_admin` + "/auth/verify-password" 验证管理员身份 → 校验 manifest SHA256 → pg_dump 快照当前库 → 解密 → DROP/CREATE DATABASE → pg_restore → 文件解压 → 失败则回退快照
- 备份文件命名从 `.sql.gz` 改为 `.zip`（加密），`list_backups` 的 glob 模式同步更新

**设计边界**：backup_pepper 存在 DB 里，意味着备份场景限定为「同机恢复」（库存在、pepper 可得）。全新库 / 换机场景必须走数据迁转。这是有意为之，不是缺陷。

### 2.3 数据迁转改造

- **保留**：加密全链路（passphrase + 随机 salt + pyzipper AES-256 + pepper + salt 走响应头）、`require_admin` + 二次密码验证、`validate_version` 同版本校验、紧急备份与自动回退、内存任务追踪
- **删除**：`EXPORT_TABLE_ORDER` / `TABLE_MODEL_MAP` / `SKIP_TABLES` + 28 个 model import、`_version_gt`、`_parse_datetimes`、`truncate_all_tables`、`_backup_tables`、`_restore_from_backup`、`import_table_data`、`copy_imported_files`
- **删除整个目录**：`app/services/data_migrations/`（4 个文件）+ `MIGRATION_CHAIN` + `test_data_migrations.py`
- manifest 简化：去 `total_rows`，加 `table_count`

## 五、风险与注意事项

1. **backup_pepper 存 DB** → 全新库无法解密备份。设计如此：换机走迁转。但需要在备份页面提示「备份仅可用于本机恢复」
2. **服务端持密钥的安全边界**：拿到备份文件 + 拿到 DB 或 .env 的人即可解密。备份文件不应离开本机（区别于迁转包）
3. **恢复期间需断连**：用 `DROP DATABASE ... WITH (FORCE)`（PG13+，项目 PG15）
4. **pg_dump 耦合 PG15**：项目固定 postgres:15-alpine，风险低
5. **pepper 语义**：迁转导入后目标库 pepper 被替换，目标库原有旧加密包将解不开。可接受（导入本就是完全覆盖语义）
6. **备份期间数据库快照**：pg_dump 持快照，数据量 <10 万行，无压力
