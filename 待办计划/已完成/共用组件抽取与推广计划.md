# 共用组件抽取与推广计划

> 状态：**已完成**（T1-T5 ✅ / T6 B1 通用 CRUD ✅ / B2 内容类 ✅ / B3 设置类 ✅ 已实施并部署；B4 复杂模块评估结论：不抽取，理由见盘点清单）
> 创建日期：2026-08-30
> 背景：用户提出「共用组件应该在其他地方都是这样子的，不单单在新建待办浮窗和新建交流浮窗这两处」

---

## 一、背景与目标

当前项目中「新建待办」「新建交流」等浮窗在多处重复实现（待办任务 Tab、提案详情页等），
表单字段与提交逻辑各自维护一份，后续改动一处容易漏改另一处。

**目标**：确立「共用组件」模式并推广到各处——项目模块内复用的弹窗/表单抽取为共享组件，
一处修改、多处以一；再推广到整个前端（服务器、资产、联系人等其他模块的重复表单）。

**模式约定**：
- 项目模块共用组件放 `frontend/src/pages/projects/components/`（新目录）
- 组件自洽：数据加载、编号生成、校验、提交内聚在组件内，调用方只传最小 props
- 支持 props 定制差异（如 `initialProposalId` 预关联），避免「一个组件一个用法」

## 四、执行顺序与依赖

1. **T1 TodoModal（样板）** → 确立模式与组件目录约定 ← 本计划首个待办
2. **T2 MeetingModal** → 验证模式在第二个组件可复制
3. **T3-T5** → 项目模块内逐步推广
4. **T6** → 跨模块推广（确认范围后另立计划）

依赖：T1 先行，T2-T5 无相互依赖可并行（各自独立抽取）；T6 依赖模式成熟后再启动。

## 五、验收标准（整体）

1. 每个被抽取的浮窗在全部调用方渲染一致，行为（编号/关联/消息提示）不回归
2. `npx tsc -b` 零错误、`npm run build` 通过、部署后冒烟通过
3. 组件目录约定清晰（项目模块 components/ 子目录、全局 components/）
4. 无重复实现残留（grep 可验证同一表单只有一份）
5. 深浅色模式、无 Emoji 图标、design token 引用不变

## 六、风险与注意事项

- 组件 props 设计需兼顾两处差异（预关联 vs 选择器），避免过度参数化
- 富文本描述（Tiptap）与附件上传逻辑在各表单中差异较大，抽取时保留差异点
- 事件移交表单动态渲染较复杂，抽取时注意不要破坏
- 跨模块推广（T6）范围大，建议单独出盘点清单计划，避免一次改动过大
